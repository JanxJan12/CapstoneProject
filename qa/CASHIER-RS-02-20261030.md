# CASHIER-RS-02 — Receipts & Sales targeted implementation

**Date:** 30 October 2026 (Asia/Manila). **Result:** bounded Cashier frontend changes complete; local checks pass; authenticated browser acceptance blocked by unavailable browser access host. No hosted business record, migration, RPC, RLS rule, database schema, or other module was changed.

## Executive summary

Receipts & Sales remains the authorized Cashier-owned financial-record workspace. The visible summary now has only page transaction count and completed recorded amounts split into Cash and GCash, with explicit scope wording. The redundant one-choice Cashier filter is gone. Detail uses recorded historical `order_items.line_total`, presents recorded meal choices/modifiers, hides zero discount, and warns if item lines disagree with recorded subtotal. The audit timeline no longer substitutes the current session's name for historic recording, verification, or rejection actors. Shift/terminal options load once per Cashier session instead of on every history filter or page request. List, server pagination, filtered CSV, detail, reprint, and exact linked-order navigation remain connected to their existing APIs.

## Financial data contract

History list and filtered CSV still use `get_cashier_transaction_history`, which joins the signed-in Cashier's transaction to its order, payment, and shift. The RPC's active-profile and dual Cashier ownership predicates, 1–100 limit/0–10,000 offset bounds, deterministic sort, and pre-page count/filter semantics were not changed. Page figures are computed from the current 50 returned rows: only `Completed` transaction amounts (`orders.grand_total`) enter completed total and Cash/GCash splits; `Voided` rows remain in the page count but contribute zero to those amounts. No refund or physical drawer payout is inferred. The header's matching count comes from the RPC over *all filtered rows*, while the four summary figures explicitly cover the visible page. CSV fetches the same RPC filters across pages, up to the existing 5,000-row cap.

For selected detail, `get_cashier_sale` remains the authorized read path, with the existing exact cashier/transaction/payment/shift link checks. The original `order_items.line_total` is preferred. If the optional line snapshot is absent, the UI can calculate from *recorded* unit price and quantity; an invalid present snapshot is displayed as unavailable. A cent-level item/subtotal disagreement produces a non-destructive warning. Delivery fee, discount, tax, grand total, and payment evidence remain recorded values. Historical GCash and the shared thermal receipt component were not changed. Zero discount is omitted from detail; positive historical discounts remain visible.

## Audit attribution and workflow

The transaction event says “Recording Cashier account” with its recorded ID in Audit details. Payment verification uses `payment.verifiedBy` only as an account ID; missing identity says “Verifier unavailable.” Rejection follows `payment.rejectedBy` when present and otherwise says “Reviewer unavailable.” An order timeline `Account <UUID>` becomes “Recorded account,” while its ID remains technical evidence; other recorded actor text is retained. These labels do not assert a person's name from the current signed-in session. Original timestamps and event descriptions remain.

Receipt search, method/status/date/customer/order/receipt/shift/terminal filters, 50-row pagination, empty/error states, details, completed-only reprint, and linked order navigation remain. Shift choices are now fetched once when Cashier identity/name changes; a shift-option failure is shown separately from history list failure. The existing 500-shift dropdown limit is unchanged and remains a long-history limitation. No restaurant-wide search or Manager reporting view was introduced.

## Cross-module safety, risks, and next acceptance

The changes are confined to Cashier Transactions/Receipts & Sales and QA. Orders remains its operational view; POS cash-only controls, Kitchen handoff, Manager reports, Customer checkout, Rider flow, shift settlement formula, and receipt print CSS are untouched. The current RPC, RLS, and financial formulas are untouched. The legacy pure export adapter retains its internal Cashier filter for compatibility; the active server-filtered CSV still derives owner scope from the authenticated RPC.

**Outstanding risks:** the dropdown shows at most 500 shifts; offset CSV can see same-count row churn; recorded verifier IDs are not resolved to historic display names under Cashier permissions; an invalid legacy line snapshot is shown unavailable; live responsive/accessibility behavior and signed-in cross-Cashier isolation remain unverified. A history search by order number still uses the advanced Order field because changing primary RPC search requires a separately reviewed backend contract. None of these limits justify altering stored financial records.

**Recommended next action:** use a safely verified authenticated Cashier browser to capture desktop and narrow-screen before/after acceptance of summary scope, filters, date/shift combinations, selected detail, neutral audit labels, original receipt reprint, linked Orders navigation, and same-filter CSV. Use a second authorized Cashier account in an isolated acceptance environment for cross-owner denial. Keep physical 80 mm printing as a separate hardware gate.
