# Cashier Order List and Transaction History: data lineage and schema audit

**Date:** 2026-10-30 (Asia/Manila)  
**Scope:** current working-tree Cashier implementation and read-only hosted PostgreSQL project `zhzluhqvysvsadwuugpa`. No application interaction, database mutation, source edit, or migration was performed. This report is the only new file. The working tree was already dirty.

## Executive decision

These workspaces are **not redundant database tables**. Order List is an operational projection of `public.orders` plus items, status events, payment status, and rider assignment. Transaction History is meant to be a receipt and financial audit projection rooted in `public.cashier_transactions`, linked by foreign keys to the same orders, payments, and shifts. Normalized sharing is appropriate. The present **screen** history is materially incomplete: it hydrates only the authenticated cashier's **completed sales in the currently open shift**, whereas CSV export fetches **all of that cashier's transactions** from `public.cashier_transactions`. Preserve both business capabilities while clarifying navigation; do not remove either workspace until the history query and acceptance coverage are corrected.

### Evidence and method

I traced the active page/hooks/store/API source and the corresponding SQL migrations, then queried hosted `pg_class`/`pg_attribute` for exact column types, `pg_constraint` for PK/FK/unique keys, `pg_proc` for current RPC signatures/bodies, `information_schema.views`, `pg_policies`, and aggregate counts. Hosted introspection is authoritative for current shape; migrations are provenance, not assumed to have replayed identically. Code references below are repository-relative `file:line`; the hosted SQL inspection is reproduced in the appendix. No authenticated Cashier browser journey or receipt print was run, so UI outcomes are code-backed, not runtime-accepted.

## Hosted tables and actual columns

Notation: `D` direct Supabase `from()` read; `R` read inside hosted RPC; `W` mutation inside hosted RPC. **O** = Order List path; **T** = Transaction History path. A shared Cashier provider loads data for both pages, so `T` denotes actual detail/filter/list/export dependencies, not merely network traffic while the page is mounted. Columns listed after `Uses` are the fields selected, filtered, joined, or changed by these paths. All column/type lists below came from hosted `pg_attribute` and include columns outside the workspaces, so omissions in `Uses` are intentional. `numeric(p,s)` and varchar lengths are hosted types.

### `public.orders` — shared; order lifecycle and commercial order snapshot

**Columns:** `id uuid`, `order_number varchar(50)`, `customer_id uuid`, `processed_by uuid`, `order_channel order_channel`, `fulfillment_type fulfillment_type`, `customer_name varchar(150)`, `customer_contact_number varchar(20)`, `delivery_address text`, `landmark text`, `geolocation text`, `current_status order_status`, `subtotal numeric(10,2)`, `delivery_fee numeric(10,2)`, `grand_total numeric(10,2)`, `notes text`, `confirmed_at timestamptz`, `created_at timestamptz`, `completed_at timestamptz`, `cancelled_at timestamptz`, `table_number varchar(20)`, `discount_type varchar(40)`, `discount_reference varchar(100)`, `discount_amount numeric(12,2)`, `tax_amount numeric(12,2)`, `customer_request_id uuid`.

**Keys:** PK `id`; unique `order_number`; FK `customer_id→public.profiles.id`, `processed_by→public.profiles.id`. **Uses:** O-D selects `id, order_number, customer_id, processed_by, order_channel, fulfillment_type, customer_name, customer_contact_number, table_number, delivery_address, landmark, current_status, subtotal, delivery_fee, grand_total, notes, confirmed_at, created_at, completed_at, cancelled_at`; O-R also reads order/payment joins and discount/tax fields via sale/online-payment RPCs; O-W edits customer name/contact/table/address/notes and status/cancelled/release fields via RPCs. T-R current-shift sale/detail reads the sale's order ID/number, channel/type, customer fields, address/landmark/table, status, subtotal, discount/tax/grand total, notes and timestamps; T-D export embedded read is `order_number, customer_name, grand_total`. The hosted sale RPCs omit `delivery_fee` even though the direct Order List query includes it. `customer_id` and `completed_at` are directly fetched for O but unused in its mapping; `geolocation` and `customer_request_id` are not used here. Evidence: `supabaseOrderService.ts:320-393,443-511`; `cashierSaleHydrationApi.ts:368-612`; `transactionExportApi.ts:32-40`; hosted `get_cashier_sale`/`get_current_shift_cashier_sales` bodies; operational edit DDL `20260903160000_secure_cashier_order_operational_edit.sql:144-173`.

### `public.order_items` — shared, legitimate order line snapshots

**Columns:** `id uuid`, `order_id uuid`, `menu_item_id uuid`, `quantity integer`, `unit_price numeric(10,2)`, `line_total numeric(10,2)`, `special_instructions text`, `created_at timestamptz`, `item_name varchar`, `modifiers jsonb`. **Keys:** PK `id`; FK `order_id→public.orders.id`, `menu_item_id→public.menu_items.id`. **Uses:** O-D selects **all** listed columns, joins by `order_id`, sorts `created_at`; mapped item uses `id, menu_item_id, item_name, quantity, unit_price, special_instructions, modifiers` (`supabaseOrderService.ts:366-380,515-530`). T-R sale RPC reads all item columns for receipt/basket; the screen detail uses item name/quantity/unit price/modifiers (`TransactionDetailDrawer.tsx:115-163`), and reprint uses those plus order-level totals (`ReceiptContent.tsx:81-109`). `line_total` is selected in both read paths but the rendered item totals are calculated as unit price × quantity, so the stored line total is not the displayed source (`OrderExpandedContent.tsx:50-65`; `TransactionDetailDrawer.tsx:153-156`). The item name and price are historical sale snapshots, not inherently an anti-pattern; their agreement with the current menu is not required.

### `public.payments` — shared payment state, reached through RPCs

**Columns:** `id uuid`, `order_id uuid`, `payment_method payment_method`, `amount numeric(10,2)`, `gcash_reference_number varchar(100)`, `proof_image_path text`, `status payment_status`, `verified_by uuid`, `verified_at timestamptz`, `rejection_reason text`, `created_at timestamptz`, `updated_at timestamptz`, `cash_received numeric(12,2)`, `rejection_notes text`, `rejected_by uuid`, `rejected_at timestamptz`. **Keys:** PK `id`; unique `order_id`; FK `order_id→public.orders.id`, `verified_by/rejected_by→public.profiles.id`. **Uses:** O-R `get_cashier_online_payments` returns `id, order_id` via order join, `amount, payment_method, gcash_reference_number, proof_image_path, status, verified_by, verified_at, rejection_reason, rejection_notes, rejected_by, rejected_at, created_at, updated_at` for online orders; own current-shift sale RPC additionally returns `cash_received`. O cancellation RPC reads `status` and blocks verified/pending payment; it does **not** write payment rows. T-R sale RPC returns `id, order_id, payment_method, amount, gcash_reference_number, proof_image_path, status, cash_received, verified_by, verified_at, rejection_reason, created_at, updated_at`; transaction export obtains method/reference via `get_cashier_sale`. ### Related tables intentionally outside these page paths

`public.paid_order_cancellations` exists in hosted schema, but neither audited page reads/writes it; paid cancellation is a separate Manager workflow. `public.menu_items` is an FK target of `order_items.menu_item_id` but neither page joins its current catalog record. The shared provider also loads menu availability for other Cashier workflows (`CashierStore.tsx:506`); this is provider-wide fetching, not an Order List or Transaction History business dependency. `auth.users` is the profile FK target, not queried by these pages. No `public` SQL views exist in the hosted database (`information_schema.views` returned zero rows); neither workspace uses a view.

### Row ownership and access boundary

Hosted `pg_policies` shows an active Cashier can SELECT staff orders, order items and order status history across Cashiers, while `cashier_transactions` and `cashier_shifts` direct SELECT is limited to rows with that cashier's ID. `profiles` direct SELECT is limited to one's own row (Manager has a separate policy); no direct `payments` SELECT policy was returned. The read RPCs check active Cashier identity, and `get_cashier_sale(uuid)` additionally restricts `tx.cashier_id=auth.uid()` in its hosted body. Thus an order may be visible in Order List yet have no corresponding receipt in that Cashier's Transaction History. The foreign keys express entity ownership: order owns its items, payment, status events and assignments; transaction references exactly one order/payment/shift/cashier; shift references a cashier. `cashier_transactions.order_id` and `.payment_id` are individually unique, and `payments.order_id` is unique. These are normalized relationships, not cross-workspace copies. Authorization behavior was inspected from policy/function definitions, not exercised with a signed-in account.

## Findings and recommendations

1. **High — Transaction History screen is not historical.** Hosted `get_current_shift_cashier_sales` filters to an open shift and `completed`, while `cashierPersistence.ts:8-17` discards prior financial cache on reload. The page offers All shifts and Refunded/Voided filters (`TransactionFilters.tsx:121-145,219-253`), but the load path cannot populate historical or non-completed rows. The export path queries all own transactions independently (`transactionExportApi.ts:17-79`). **Recommendation:** add a paginated, authorized read model rooted in `cashier_transactions` for the history screen, with joined order/payment/shift and consistent population/filter semantics. Keep current-shift hydration for operational workflows. Validate against real authenticated Cashier cases before changing navigation. Hosted snapshot: 42 transactions, all completed, so present absence of non-completed rows is not evidence that the status filters have ever been exercised.
2. **High — Order List may present inferred payment truth.** Direct order mapping sets online to GCash/Unpaid and walk-in to Cash/Verified before payment or own-sale enrichment (`supabaseOrderService.ts:485-487,615-632`; `CashierStore.tsx:193-233`). The live database currently contains 12 delivered online orders, of which 2 have no linked payment or transaction (read-only aggregate), so an order's operational status does not prove payment evidence. **Recommendation:** display an explicit unknown/unlinked state when no payment record exists; source actual method/status from `payments`/authorized RPC, and keep order status independent. Do not infer a financial correction from this audit.
3. **Medium — Financial values have two legitimate stored snapshots but one implicit presentation choice.** `orders.grand_total`, `payments.amount`, and item line totals coexist; `cashier_transactions` stores identifiers/status but no amount. Screen transaction mapping and export use `orders.grand_total` (`cashierSaleHydrationApi.ts:339-342,581-585`; `transactionExport.ts:93-104`); payment evidence uses `payments.amount`. Current hosted aggregate found **0** order/payment amount mismatches and **0** transaction/payment order-link mismatches, so no current divergent amount was established. **Recommendation:** document `orders.grand_total` as charged order total and `payments.amount` as payment evidence, assert equality at sale creation/verification, and explicitly define refund/net reporting from the appropriate refund record. Do not merge legitimate snapshots into one column solely to remove apparent duplication.
4. **Medium — CSV and on-screen history can disagree in record count and filters.** The screen filters `state.transactions`; export independently pages `cashier_transactions` and re-applies filters (`useTransactionHistory.ts:63,97-126`). A historical receipt can be exported but not selected/reprinted on the screen after reload. **Recommendation:** make the history list and export share the same authorized query definition or document and label any deliberate scope difference. Ensure UI count reflects the queried population.
5. **Medium — Sale hydration can hide delivery-fee detail.** The direct order query reads `orders.delivery_fee` (`supabaseOrderService.ts:336`), but both hosted sale RPC JSON order objects omit it (`20260831000000_secure_customer_gcash_verification.sql:387-410,559-583`, confirmed in hosted bodies). `mapDatabaseCashierSale` does not populate `Order.deliveryFee` (`cashierSaleHydrationApi.ts:368-461`), and `mergeDatabaseRefresh` replaces a matching direct order with that hydrated order (`CashierStore.tsx:193-210`). Order/transaction detail renders the delivery fee only when present (`OrderExpandedContent.tsx:15-65`; `TransactionDetailDrawer.tsx:69-85`). The hosted aggregate found 13 delivery transactions, all with a positive fee, totaling ₱650; no authenticated UI rendering was tested. **Recommendation:** include the recorded fee in the sale read model and verify subtotal + delivery fee − discount + tax = grand total in both details and receipt preview.
6. **Medium — Refunded is an unsupported hosted transaction state.** `TransactionFilters.tsx:121-145` exposes Refunded, `transactionSummaryMetrics.ts:66-73` computes refunds from transactions marked Refunded, and `transactionExport.ts:79-87` accepts a `refunded` string. Hosted enum `public.cashier_transaction_status` has only `completed, voided`; `public.paid_order_cancellations` is a distinct table that neither page reads. The current refund filter/summary therefore has no hosted transaction-row source. **Recommendation:** decide whether refunds should be modeled as separate ledger events or linked paid-cancellation records, then implement an explicit authorized read path and net/gross reporting rule. Do not add an enum value merely to make the UI filter selectable.
7. **Low — Overfetch and implicit copies reduce clarity.** Order direct fetch selects `customer_id`, `completed_at`, and item `line_total` without using them in its mapper (`supabaseOrderService.ts:326,342,374,443-530`); both details recalculate item display totals from unit price × quantity. `orders.customer_name` and `order_items.item_name/unit_price` are useful at-sale snapshots, while UI `Transaction` copies customer/amount/method from linked order/payment and is **in-memory**, not another PostgreSQL table (`cashierSaleHydrationApi.ts:567-612`). **Recommendation:** document snapshot semantics and remove genuinely unused read fields only after verifying no downstream consumer; compare `line_total` to calculation as a validation rule if it is intended to be authoritative.
