# CASHIER-DB-01 — Cashier necessity and elimination audit

**Date:** 31 October 2026, Asia/Manila. **Project:** `zhzluhqvysvsadwuugpa`. **Execution:** read-only source, hosted catalog/aggregate/plan inspection and local non-destructive checks. **Decision:** approve no implementation from this report alone.

## 1. Executive summary

The smallest defensible architecture still needs distinct order, basket, payment, receipt, shift, status-history, refund-event, menu, profile, inventory, Kitchen and Rider records. Their business facts differ. The measurable simplification is narrower: two unmounted Cashier components, two duplicate timestamp triggers, and one duplicate profile owner SELECT policy are concrete elimination candidates. One legacy current-shift RPC has no active web/Rider source caller but requires external-consumer clearance. Optional Manager approval fields, rejection text overlap, discount contracts, and several sparse operational fields require policy or historical migration decisions. Zero rows or zero index scans were never treated as proof of obsolescence.

The complete per-column dispositions for the 20 examined tables (246 columns) are in [the column matrix](CASHIER-DB-01-COLUMN-MATRIX-20261031.csv); the 397 catalog objects and their definitions/dispositions are in [the object inventory](CASHIER-DB-01-OBJECT-INVENTORY-20261031.csv). [RPC detail](CASHIER-DB-01-RPC-DETAIL-20261031.csv) adds 99 definition-level table references and authorization/lock/write indicators. [The elimination register](CASHIER-DB-01-ELIMINATION-REGISTER-20261031.csv) identifies exact changes, tests, rollback and approval gates. These are recommendations, not deletions.

## 2. Project owner architectural vision

Retain only objects with a current operation, financial/historical fact, security control or reliability role. Remove entire dependency chains when an operational feature has no defensible purpose. Treat an existing source reference as a dependency to resolve, not as proof the feature is necessary. Treat a zero-row exception table as an event model, not as dead code. No speculative target object count governs the recommendations.

## 4. Current database architecture

`orders` records the commercial/fulfillment state; `order_items` stores the original basket; `payments` records method, amount and verification; `cashier_transactions` identifies a completed/voided sale and its receipt, one linked order/payment/shift; `cashier_shifts` owns the drawer and frozen settlement; `paid_order_cancellations` is a distinct Manager refund attestation. `order_status_history` supports operational chronology and confirmed-order inventory deduction. `profiles` authorizes actors. `menu_items`, `menu_categories` and `drink_choices` supply shared catalog/price choices. `delivery_assignments` and Rider supporting tables govern offers, status and proof. Inventory and KDS supporting tables are included in the matrix because paid orders feed production.

`public` has 36 ordinary tables; all 36 have RLS enabled. The 20 directly linked tables selected for this audit contain 246 columns. The 12 initial target tables contain 149 of them. There are no `public` views in the hosted catalog; RPCs form the read models.

## 7. Column-level necessity matrix

The CSV gives each of 246 columns its own class, current nullable population where measured, specific rationale and removal gate. It records 159 `KEEP — PROTECTIVE`, 75 `KEEP — ESSENTIAL`, 5 `BUSINESS DECISION REQUIRED`, 4 `RETAIN TEMPORARILY`, 2 `MERGE CANDIDATE`, and 1 `DERIVE CANDIDATE`. Those classes are **audit dispositions**, not 234 individually executed runtime proofs. Supporting inventory/KDS/Rider rows identify cross-module contracts; their source-level necessity should be revalidated before any proposed change to those tables.

The highest-value challenge is `cashier_shifts.manager_approved_by/at`: 0/6 rows populated, no active approval writer, Cashier-led closure has no Manager approval requirement. They still appear in `get_closed_cashier_shifts` output, and `manager_approved_by` has a profile FK. They are conditional column removals, not a safe direct drop. `notes` (0/6) may serve a distinct handover explanation; `variance_reason` is required when the server computes nonzero variance. `closed_by` is a distinct act of closure, CHECK-required and useful for attribution even though the current RPC sets it to the owner.

The active POS has no new discount/note/GCash control, but `orders.discount_type/reference/amount` and old sale RPC arguments remain financial compatibility facts; current hosted discount type/reference are 0/63. `orders.notes` has 2/63 and is shared by Customer/KDS and Cashier operational edit. `order_items.special_instructions` is 0/69 but remains an active Customer/KDS contract. `orders.geolocation` is 0/63 but standalone Rider parses explicit coordinates for its destination map. `payments.rejection_reason` (2/44) and `rejection_notes` (1/44) both reach Customer/Cashier; merging them requires preserving structured reason and free text. `menu_items.image_path` is 0/20, but menu loaders read it. None of these can be removed from a null count alone.

Stored `orders.grand_total`, `payments.amount`, `order_items.unit_price/line_total/item_name/modifiers`, receipt identifiers, `cashier_shifts.expected_cash/actual_cash/variance`, and payment/void timestamps remain protective. ## 9. RPC/function inventory and decisions

The inventory CSV records signatures, return types, definer mode, search path and anon/authenticated EXECUTE for 99 named public functions. The RPC detail CSV adds text-derived table mentions and auth/lock/write/error indicators; these are not a complete call graph or execution proof. Principal Cashier contracts are `get_open_cashier_shift`, `start_cashier_shift`, `close_cashier_shift`, `get_closed_cashier_shifts`, `create_walk_in_sale`, `get_current_shift_cashier_sales`, `get_cashier_transaction_history`, `get_cashier_sale`, `get_cashier_online_payments`, `verify_customer_gcash_payment`, `reject_customer_gcash_payment`, `cancel_order`, `update_cashier_order_operational_details`, `release_ready_order` and `get_cashier_delivery_assignment_statuses`. Customer placement/payment, Manager paid cancellation, KDS advancement and Rider offer/delivery functions are shared dependencies.

`get_current_shift_walk_in_sales()` remains hosted but has no active `src` caller in web or standalone Rider searches. It predates the active `get_current_shift_cashier_sales()` hydration. Treat it as a **conditional** RPC retirement: confirm PostgREST/external clients, SQL dependencies, permissions and migration compatibility before a reviewed forward drop. `get_cashier_transaction_history` is **not** a candidate: it owns historical closed-shift access, active Cashier/dual-owner checks, limit 1–100, offset 0–10,000, NULL rejection, stable `created_at DESC,id DESC`, filtered count and denied anon access. `get_cashier_sale` remains detail authority; no per-list-row N+1 call was found.

Catalog text inspection of selected financial functions shows role checks, locks and idempotency paths; these are source facts, not a current authenticated/concurrency PASS. Consolidation of write RPCs solely for function-count reduction is rejected because sale, verification, cancellation and closure have different authority and transaction boundaries.

## 10. Financial source of truth

`orders.grand_total` is the charged order snapshot; `payments.amount/status/method` is payment evidence; `cashier_transactions` is a unique completed/voided receipt, attributed through `shift_id`; `cashier_shifts` stores opening float and final expected/count/variance. The server close predicate counts only **completed receipts with verified payments**, split by Cash/GCash, and saves the final drawer snapshot. GCash is outside physical cash. Tender `cash_received` is not revenue. Manager fulfilled-order revenue uses another population and date axis. A `paid_order_cancellations` row records Manager full-refund attestation and voiding, not necessarily the physical drawer from which cash was paid.

Hosted read-only aggregate: 42 completed verified receipts; 0 orphan receipt links, 0 transaction/shift owner mismatches, 0 completed receipts with unverified/mismatched payment, 0 bad saved closed variance, and 0 cancelled orders retaining a verified payment. This is current data consistency, not proof of future concurrent outcomes, physical cash, or snapshot immutability under privileged writes.

## 11. Query and performance findings

The mounted Cashier provider loads several independent read models in parallel and refreshes on order/status Realtime, focus/reconnect and manual refresh. Assignment polling is visibility/eligibility gated at 15 seconds; Kitchen queue polls at 5 seconds. Source shows possible repeated refresh work but no measured per-user duplicate rate. RS-02 already separated shift-choice loading from each History filter/page fetch.

Hosted `pg_stat_statements` (reset 4 August 2026 UTC) records the PostgREST-shaped `get_current_shift_cashier_sales` statement at 4,644 calls, 62,419.3 ms cumulative, 13.44 ms mean; `get_cashier_online_payments` at 4,485 calls, 28,874.4 ms, 6.44 ms mean; the history RPC at 13 calls, 138.2 ms, 10.63 ms mean. These are cumulative mixed workloads, not current screen latency. A non-executing SELECT-equivalent `EXPLAIN (FORMAT JSON)` for owner-scoped transaction/shift/payment history showed a sequential scan of the 42-row transaction table, hash join to payment, shift PK lookup and final sort; its cost is an estimate, not actual duration. No index addition is justified at this size. The receipt/transaction-number unique indexes and `menu_items_is_available_idx` show zero cumulative scans, but uniqueness and future selectivity cannot be dismissed from that statistic.

History CSV uses bounded 100-row RPC pages up to 5,000 rows; concurrent same-count churn can still alter offset pages. Deep history beyond offset 10,000 and shift dropdown beyond 500 are explicit scale limits. No material payload size or authenticated network waterfall was measured. Do not claim a hosted speedup from this audit.

## 12. Security/RLS/grants assessment

All 20 examined tables have RLS. Direct authenticated SELECT on shifts and transactions is constrained to own active Cashier or active Manager. The deployed history definer RPC additionally checks active Cashier and both transaction and shift owners; anon EXECUTE is false. `get_closed_cashier_shifts` is invoker with own Cashier/Manager scope. Other definer RPCs need branch-specific authorization replay before alteration. Several order/payment/item/assignment tables have anon SELECT grants but RLS policies restrict rows; grant presence alone is not exposure. Public menu rows are intentionally readable under active/available policies. `payments` has no direct Cashier SELECT policy in the inspected catalog; Cashier payment evidence comes through guarded RPCs.

`profiles_select_own` and `profiles_view_own` are both authenticated SELECT policies with equivalent `auth.uid()=id` predicates. Removing one is a catalog-supported candidate only after checking effective OR policy behavior and all roles in a disposable database. No policy/grant was changed.

## 13. Foreign key and constraint assessment

Unique order/payment/request/transaction/receipt keys on `cashier_transactions` prevent duplicate receipt identity and retry duplication. Its FKs link one order, payment, shift and Cashier. Partial unique shift indexes enforce one open shift per Cashier and one per case-insensitive terminal. Shift status CHECK requires closure values/actor only when closed. Voided transaction CHECK requires reason/time. Paid cancellation unique keys protect one refund event per order/payment/receipt/reference even with zero current rows. Order/payment FKs and status/amount checks prevent several invalid states; aggregate checks above found no current violation. Indexes and constraints are enumerated in the CSV; no FK or unique protection is proposed for removal.

Two distinct duplicate trigger pairs were found in the hosted catalog: `profiles_set_updated_at` + `trg_profiles_set_updated_at`, and `riders_set_updated_at` + `trg_riders_set_updated_at`. Each pair fires `BEFORE UPDATE FOR EACH ROW EXECUTE FUNCTION set_updated_at()`. Retire one named trigger per table after a disposable single-trigger update replay. The `payments` pending-GCash advisory-lock trigger and order-history inventory deduction trigger must remain.

## 14. Cross-module dependency analysis

Customer creates order/item/payment evidence, submits GCash proof, reads rejection reason/notes and delivery status. Manager reads orders, fulfilled revenue and authorized shift audit, controls menu/availability and records paid cancellation/refund. Kitchen reads paid confirmed orders, item modifiers/instructions and status history; the history trigger deducts inventory. Cashier creates cash walk-in sales, verifies/rejects GCash, releases orders, resolves operational detail and settles one drawer. Standalone Rider directly reads assigned `delivery_assignments`, selected order fields (`order_number`, contact, address, `geolocation`, landmark, notes, amounts) and order items; Realtime subscribes to assignments; Rider commands call offer/delivery RPCs. Removing shared fields from Cashier's view does not clear these consumers. Shared `profiles` remains role authority across all modules.

An unused field is not an authorization to alter the underlying service policy. Current Cashier-led variance reconciliation expressly has no mandatory Manager sign-off; the approval columns remain a conditional cleanup because the read contract still exposes them.

## 22. Migration and rollback requirements

Every DB change requires the exact hosted definition/hash/version preflight, disposable migration replay with representative current and historical rows, a reviewed forward migration, recovery/backup readiness, and explicit hosted authorization. For duplicate triggers, preserve the retained trigger and recreate the removed exact trigger in a forward rollback if needed. For a policy, restore the exact SELECT policy and verify effective own/other role access. For the legacy RPC, preserve definition, grants, search path and clients before drop. For any column retirement, preserve historical values and version the RPC/client contract first; never destroy archived financial facts or reset migration history. Hosted migration ledger divergence forbids an unscoped `db push`.

## 23. Panelist defense appendix

- **Why separate order and payment?** An order can exist while GCash is pending/rejected; payment supplies verification and tender evidence independent of fulfillment.
- **Why separate receipt?** It supplies one stable unique receipt/transaction identity, Cashier and exact shift attribution, and void chronology.
- **Why a shift snapshot?** Physical count and the as-closed expected figure cannot be derived after later receipt changes.
- **Why order items and status history?** Item price/name/modifier snapshots survive catalog changes; status events explain Kitchen/Rider progress and trigger inventory deduction.
- **Why refund event?** Manager attestation/reason/reference is distinct from order status and does not equate to actual drawer movement.
- **Why delivery assignment?** One order may have offer/rejection/reassignment chronology, Rider proof and ownership distinct from the order.
- **Why RLS plus RPC checks?** Direct table access and definer functions have different execution privileges; both need own-row and active-role boundaries. Current A/B runtime penetration remains open.
