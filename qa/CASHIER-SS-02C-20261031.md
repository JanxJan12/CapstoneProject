# CASHIER-SS-02C — Shift Settlement usability refinement

**Date:** 31 October 2026 (Asia/Manila). **Scope:** active Cashier Shift Settlement frontend, focused tests, QA documentation. **Pre-edit worktree:** 359 dirty entries, including pre-existing edits to the active Shift Settlement files. No backend, migration, RLS, or hosted financial mutation is authorized.

## Pre-edit implementation and impact map

`ShiftSettlementPage` mounts `EndShiftDialog` for the active Cashier shift; the Dashboard also mounts the same dialog. `useShiftSettlement.handleEnd` calls `CashierStore.endShift` → `useCashierActions.end` → `closeCashierShift` RPC, then displays the server-returned saved figures. `EndShiftDialog` first validates the physical count and local provisional variance, stores review values/snapshot, and opens `ConfirmationDialog`. Only its `confirmClosure` handler calls `onConfirm`; a synchronous ref prevents duplicate submission. On uncertain failure it reads own open/saved shift state and blocks another attempt until refresh. Closing or cancelling before confirmation does not call the RPC. The form and its notes remain mounted when the final review opens, so Back preserves values. The current count validator requires finite, nonnegative values with at most two decimals, and a reason for nonzero estimated variance; server authority and possible final discrepancy remain.

## Executive summary and revised flow

The Cashier still enters a physical count, receives a provisional Balanced/Shortage/Overage result, and must provide a reason for a nonzero estimated variance. **Review settlement** validates and opens the existing final review without calling the closure action. **Back to cash count** dismisses only that review; the mounted form retains the count and notes. **Confirm and close shift** is the sole action wired to the existing closure callback. The server still decides eligibility and saved financial amounts. No hosted close was submitted.
