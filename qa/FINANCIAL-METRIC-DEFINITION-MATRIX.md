# H-07 financial metric definition matrix

**Status:** Current implementation definitions, verified against source and the [isolated reconciliation](FINANCIAL-RECONCILIATION-REGRESSION.md). Proposed accounting terms below require restaurant-owner approval before changing SQL, UI business wording or historical interpretation.

| Metric / question | Current exact definition and time axis | Authority / consumer | H-07 disposition |
| --- | --- | --- | --- |
| Order gross / booked value | `orders.grand_total` per order; created-date sum if an order intake metric is wanted. Includes unpaid/cancelled unless filtered. | `orders`, Customer/Cashier/Manager order detail | **Not a revenue metric**. Owner to approve scope, discounts/tax/delivery treatment. |
| Submitted GCash | `payments.status='pending'`, amount and count; rejected is separate, no journal | Cashier pending queue; Manager dashboard pending count is global, not “today” | Verified in isolated state/RPC transitions. Never include in collected sales. |
| Rejected GCash | Rejected payment row, same order/payment identity; later resubmission returns it to pending | Customer tracking, Cashier queue | Verified transition locally with synthetic metadata stubs. Rejection history is an event, not money. |
| Verified collections | Sum `payments.amount` where status is currently `verified`, irrespective of order fulfillment, preferably by `verified_at` for collection-date reporting | Payment table; no dedicated Manager collection card | **Proposed name.** Current-state net of later voids; not immutable cashflow history. Owner must decide date and refund treatment. |
| Cashier completed receipts / older “Sales Today” card | Sum `cashier_transactions` whose **current** status is completed, using receipt `created_at` Manila date. Method amounts from linked payment / hydrated receipt. | Active Transaction History; older `CashierMetrics` component is not mounted on the current Dashboard | **Verified current history definition and local browser date filter.** It can include paid unfulfilled orders and excludes later voided receipts. | Manager verified fulfilled sales / report revenue | Sum verified payment amounts for successfully fulfilled orders on effective fulfillment date. Excludes voided paid cancellations by current status. |
| Manager fulfilled order count | Count successful fulfillments with completion timestamp in range, regardless of payment row | Sales report `total_orders` | Verified source and synthetic result. Can exceed paid fulfilled count if inconsistent rows exist; decide whether this is desired. |
| Manager average order value | Fulfilled verified-payment revenue divided by number of fulfilled orders having verified payments, rounded to cents | Sales report `average_order_value` | Verified. Label should disclose denominator if retained. |
| Top item | Quantity of sold-time `order_items` for fulfilled orders with verified payment; joins current menu identity for fallback name | Sales report | Fixture with direct seeded orders had no lines; **not tested** end-to-end with multi-line completed POS. |
| Walk-in vs online | `orders.order_channel`; POS sets walk-in, Customer checkout online; fulfillment type separately dine-in/takeout/delivery | Orders/POS/Manager | **Verified identity distinction.** No combined channel sales report exists. Owner decides whether cross-channel breakdown is needed. |
| Unpaid cancellation | `cancel_order` on eligible order with no verified/pending payment and no cashier transaction | Cashier operations | Isolated RPC PASS for no-payment order. Rejected payment is source-permitted; not separately exercised in cancellation RPC. |
| Paid cancellation / refund | `paid_order_cancellations.refund_amount`, original payment/receipt IDs, confirmation, method and external reference; payment/receipt become voided | Manager panel and settlement RPC | Isolated PASS for GCash settlement and exact replay. “Refund” is Manager attestation of an external completed payment return, not an initiated transfer. |
| Net sales | No authoritative standalone net-sales RPC or approved formula. CSV output and the unmounted older “Sales Today” card remain not tested. |

## Owner decisions before metric changes

1. Adopt separate names for **order intake**, **verified collections**, **receipt-day completed sales**, and **fulfillment-day revenue**, with the intended audience for each.
2. Define whether historical sales are restated when a later paid cancellation voids a payment, or whether refunds are a separately dated contra-entry. The current schema has a settlement timestamp but no separate negative cashier transaction.
3. Define tax, discount and delivery-fee inclusion in any “gross” or “net” metric. Current verified-payment and fulfilled-sales sums use the full payment amount, generally the order grand total.
4. Define the close-shift view after a later permitted GCash cancellation: preserve original closed-shift snapshot, show current net receipts alongside it, or add an approved adjustment ledger. Do not silently rewrite closed shifts.
5. Decide whether Manager “Fulfilled Orders” should count fulfillment without verified payment, and whether the average label must explicitly identify its paid-order denominator.
