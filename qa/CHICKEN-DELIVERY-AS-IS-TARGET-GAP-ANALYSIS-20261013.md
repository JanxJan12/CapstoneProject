```sql

SELECT 'inventory_request_documents' AS entity, count(*) FROM public.inventory_request_documents
UNION ALL SELECT 'inventory_request_lines', count(*) FROM public.inventory_request_lines
UNION ALL SELECT 'inventory_request_revisions', count(*) FROM public.inventory_request_revisions
UNION ALL SELECT 'inventory_request_events', count(*) FROM public.inventory_request_events
UNION ALL SELECT 'production_replenishment_requests', count(*) FROM public.production_replenishment_requests
UNION ALL SELECT 'receiving_reports', count(*) FROM public.receiving_reports
UNION ALL SELECT 'receiving_report_items', count(*) FROM public.receiving_report_items;
-- Result in listed order: 1, 2, 1, 3, 0, 1, 2.

SELECT d.status, d.current_revision,
       (SELECT count(*) FROM public.receiving_reports rr WHERE rr.inventory_request_id=d.id) AS linked_receipts,
       (SELECT sum(l.requested_quantity) FROM public.inventory_request_lines l WHERE l.request_id=d.id) AS requested,
       (SELECT sum(ri.quantity_accepted) FROM public.receiving_reports rr
          JOIN public.receiving_report_items ri ON ri.receiving_report_id=rr.id
         WHERE rr.inventory_request_id=d.id AND rr.status='posted') AS accepted
FROM public.inventory_request_documents d;
-- One row: partially_received, Rev 1, one linked receipt, requested 12.000, accepted 8.000.

SELECT rr.status, rr.source_type, rr.inventory_request_id IS NOT NULL AS formal_link,
       rr.replenishment_request_id IS NOT NULL AS legacy_link,
       rr.inspected_by_name IS NOT NULL AS inspector_recorded,
       count(ri.id) AS lines, sum(ri.quantity_delivered) AS delivered,
       sum(ri.quantity_accepted) AS accepted, sum(ri.quantity_rejected) AS rejected
FROM public.receiving_reports rr
LEFT JOIN public.receiving_report_items ri ON ri.receiving_report_id=rr.id GROUP BY rr.id;
-- One row: posted, production_team, formal link true, legacy link false,
-- inspector true, two lines, delivered 9.000, accepted 8.000, rejected 1.000.

Receipt/item FKs, delivered-positive, accepted-nonnegative/at-most-delivered, rejected-reason, date, source, posting-field, and quantity-scale checks are present. Unique indexes ensure one receipt item per inventory item within a report, one batch per accepted receipt item, and one receiving movement per batch. The formal and legacy guards and after-post reconciliation triggers are enabled.

All four formal request tables, `receiving_reports`, `receiving_report_items`, `inventory_batches`, `inventory_transactions`, and `production_replenishment_requests` have RLS enabled. The four formal tables and receipt/batch tables have no direct `anon`/`authenticated` table DML in the inspected ACL; formal RPCs and Receiving RPCs grant `authenticated` EXECUTE and deny `anon`. `inventory_transactions` has SELECT grant but no policy in the inspected catalog, so the app's Manager movement read is through its gated RPC. `inventory_request_manager_required()` checks `auth.uid()` against an active Manager profile and is not client-executable. `post_receiving_report` performs its own active-Manager check. ### Important distinctions

1. **One-to-many is already installed for formal requests.** The older unique `replenishment_request_id` governs only the legacy single-item workflow. Applying its one-to-one finding to `inventory_request_id` would be wrong.
2. **A request is not stock.** Issue, revision, export, dispatch/acknowledgment events, draft Receiving and shortfall closure leave stock unchanged. Only accepted quantities in a successfully posted report enter book balance/batch/ledger.
3. **“Immutable” has a scope.** Revision snapshot/history is retained by application RPC and client table DML is denied. Privileged database writers can still alter those rows because no append-only trigger was observed. Do not claim cryptographic or tamper-proof Messenger evidence.
4. **The hosted sample is incomplete and illustrative.** It is presently partial (12 requested, 8 accepted, 4 outstanding) and has no recorded Messenger send/reply. The item labels indicate QA intent, but the redundancy audit did not prove deletable synthetic provenance; this report proposes no cleanup.
5. **Foodhouse custody only.** Current `inventory_items`/batches represent Foodhouse stock. There is no authoritative Production inventory, transfer in transit, or manufacturing yield here. A policy decision is required before expanding scope; do not invent supplier POs or kg-to-pieces conversion to model Production.

### P1 — choose and tighten the canonical workflow

1. Decide whether **all new** Production deliveries must originate from a formal issued request. If yes, make the historical panel read-only for old Phase 7B rows, narrow new legacy creation, and require formal/legacy linkage for new Production Receiving through an additive, data-safe rule. Preserve old rows, direct-supplier PO Receiving and existing source references. If exceptions are allowed, require a documented reason/category and show them as unmatched in reconciliation.
2. Decide whether a Manager-entered physical inspector name and Messenger reference is sufficient evidence. If not, specify minimal identity, attestation, attachment/storage and retention rules before adding columns or screens. Keep external Production messaging outside the app unless the client reverses that policy.
3. Decide no-show, rejected goods, accepted overage and shortfall closure policy: who closes, when, and whether revised request or separate exception document is required. Keep delivered, accepted, rejected and missing semantically distinct.
4. Test split receipts, all-rejected receipt, no-delivery closure, cumulative cap and competing retries under authenticated local roles. Fix only demonstrated failures.

### P2 — hardening and usability after P1 decisions

1. If audit immutability must survive privileged application code, design append-only protection for revision/event records and a controlled exception path for maintenance. Avoid an unaudited trigger that breaks installed RPCs or recovery.
2. Improve request/receipt exception visibility (unmatched Production receipts, aging outstanding lines, missing Messenger attestations) with a read-only query/RPC. Do not reclassify a missing delivery as rejected inventory.
3. Review threshold planning parameters and audit-history limit with real business units/counts. Keep the current minimum-gap suggestion explicitly provisional and preserve batch/expiry behavior.
