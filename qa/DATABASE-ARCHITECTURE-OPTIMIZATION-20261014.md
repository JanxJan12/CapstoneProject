## P0 trigger proof and rollback

The migration guard requires both trigger pairs to be enabled row-level BEFORE UPDATE, unrestricted by predicate/column/arguments, and to call the same `public.set_updated_at()` function. It retains the original names. Distinct `profiles` and `riders` triggers remain untouched. The function sets `NEW.updated_at = now()`, so duplicate invocation within a transaction has no further business effect. The local rollback-only [test](../supabase/tests/verify_single_timestamp_triggers.sql) recreated the old pair in a savepoint and compared stamp behavior with the retained single trigger; `BEGIN`/`ROLLBACK` preserved rows.

Rollback **after confirming the target catalog matches**: run the guarded [rollback SQL](ROLLBACK-DUPLICATE-TIMESTAMP-TRIGGERS-20261014.sql), which recreates only those two `trg_` trigger names in one transaction. Do not run it on a database where either retained name or function differs.

## Domain boundaries and invariants

The formal Manager request's unit is an issued document with lines, revisions, and events; the Phase 7B Production request's unit is one inventory item with its own status events. The Manager Requests route calls `get_inventory_request_register` / `issue_inventory_request`; Production and the Manager replenishment route still use the legacy request API. `receiving_reports` allows formal and historical source links, and `post_receiving_report` is the sole accepted-stock boundary. Preserve both request families and their read contracts. A future migration should only retire legacy creation after product ownership, deployed-client telemetry, event retention, and a tested mapping for every source-linked receipt are established; do not map old statuses by name alone.

For tracked stock, enforce the existing batch amount and master/ledger posting protocol transactionally. The inventory ledger records before/after and source lineage; it is an audit log, while current master and batch balances are materialized state at different grains. `inventory_transaction_batch_allocations` preserves the actual issued lot for permitted cancellation reversal. FIFO/FEFO policy is an issue-time ordering rule, not a reason to rewrite historical lots. An opening balance requires a signed physical baseline. Current modifiers are priced by the server and recipe deduction must follow the confirmed order's persisted lines. Draft requests, review, dispatch, acknowledgment and unposted Receiving never change stock. Existing nonnegative, lineage and idempotency checks were retained; a new cross-table CHECK cannot safely express the mixed aggregate/batch invariant.

The Supplier/PO path has a distinct commercial source type: `direct_supplier` Receiving requires a PO; its lines resolve inventory identity from PO lines and update PO received/remaining quantities after posting. `production_team` uses direct inventory identities and no PO. `suppliers`, `purchase_orders`, and `purchase_order_items` therefore remain conditional procurement schema. `supplier_items` is a dormant catalog bridge with no direct SQL-function body reference, but external consumers and future supplier catalog scope are unverified. **Recommended scope:** keep PO-backed direct receiving available; designate supplier catalog authoring as dormant until the owner confirms planned procurement use and deployed-client inventory. No destructive deprecation now.

For repeated `order_status_history` groups, the aggregate read-only screen found 19 excess `waiting_payment_verification` events in 11 groups and 2 excess `waiting_for_rider` events in 2 groups. All 13 groups had note variants, none had equal-status events within the same second, and actor variants occurred in several groups. Payment resubmission and rider reoffer routines can intentionally revisit these states. The actual event payload and actor audit must be reviewed privately with request/retry identifiers before declaring a duplicate producer. Retain all 223 hosted history rows and use request-specific idempotency keys for any later proven producer fix; a unique `(order_id,status)` index would be wrong. Retention must cover dispute/refund, payment, delivery, stock deduction, and food traceability timelines.

Sold-at-time `order_items` names, modifiers, unit prices and totals are financial snapshots, while current menu/recipe rows are mutable catalog data. `orders.current_status` and total are maintained projections, not duplicate purchases. `payments` records tender/verification; `cashier_transactions` records cashier receipt/shift settlement. Deleting an order currently cascades to lines, payments, status history and assignments, and can detach stock lineage. Define a graph-complete archive with proof-byte recovery and jurisdiction-specific holds before considering any retention migration.

## P3 schema review

Nine hosted public tables are empty: opening balances, batch allocations, paid cancellations, both Production request tables, and the four Supplier/PO tables. Each has an identified conditional or historical role. The register flags local all-null columns, but that is from a synthetic restored stack and does not prove hosted or future non-use. Example hosted all-null fields such as `menu_items.image_path` and `orders` geolocation/table/landmark support optional presentations or fulfillment contexts. They remain nullable.

Index scan counters in the earlier catalog lack a reliable observation window and this database is small. PK/unique indexes enforce constraints regardless of scans; FK support and partial indexes may be critical under real load. No pair was proved semantically duplicate by predicate, ordering, uniqueness and representative `EXPLAIN` plan. Function-body lexical references cannot prove an RPC dead; deployed clients and effective grants require an inventory before revocation. The pending `20261013000302_revoke_authenticated_maintain_privileges.sql` is a separately reviewed permission correction in the existing chain; it has not been applied hosted here.

## Rollout and stakeholder decisions

1. **P0 local:** already implemented and verified; retain the migration and rollback SQL in source history. No rewrite of the 51 prior migrations.
2. **P1/P2/P3 local:** keep the architecture boundaries above; no extra migration is warranted without a proven redundant object. A future retirement uses additive compatibility, deployed-client telemetry, a full data/Storage recovery set, and isolated replay first.
3. **Hosted gate:** still **NO-GO**. Historical clean replay is blocked by unsourced Phase 2A menu/inventory identities; the protected encrypted off-device recovery and restore gate, migration provenance, and hosted end-to-end acceptance are not established. Full engineering authorization permits preparation and local proof, not avoidable live data loss.

Decisions required from accountable stakeholders: a provenance-backed historical master-data/recipe baseline and zero-or-physical opening-stock decision; future Supplier/PO and supplier-catalog scope; Production legacy creation retirement and client compatibility; accounting/food-traceability/privacy retention periods; and a secure hosted recovery/rollout window after the objective gates pass. No synthetic identity, recipe, opening quantity, production deletion, or optimistic release status is inferred.
