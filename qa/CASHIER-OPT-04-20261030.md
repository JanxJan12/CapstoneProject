## Executive summary and source of truth

The Dashboard now separates immediate Cashier actions from operational monitoring. The Order List remains the comprehensive search/filter/history workspace; Pending Payments, Transaction History, and Shift Settlement keep their distinct contracts. No order status, payment, financial record, or backend rule was changed.

| Display | Source and scope |
| --- | --- |
| Dashboard current/older/unresolved | `CashierStore` hydrates all RLS-visible active orders; `getCashierActionQueue` excludes terminal statuses, and `partitionCashierWorkQueue` uses Manila date from order creation. Current is today; older includes previous days and invalid dates. This is not a shift or terminal metric. |
| Cashier actions | Pending payment records joined to an active order, across dates; Ready orders from today are counted in the shortcut. The action tab includes only current Verify Payment and Release actions. Older action candidates remain in Older Backlog; the payment shortcut can surface older pending payments directly. |
| Operational monitoring | Current Confirmed Kitchen queue, Preparing, Waiting for Rider, and later delivery stages; stage threshold crossings and order age past the cashier-local review preference are separate. Kitchen and Rider transitions remain outside Cashier control. |
| Order List | Today’s Work means nonterminal orders created today, Older Backlog means nonterminal older/undated, All Orders includes terminal history. Search and filters combine by AND, counts follow the filtered set, and pagination resets when filters/view/sort change. All Orders and export retain their existing read scope. |
| Pending Payments | Pending payment rows across dates in its dedicated verification workspace. No decision rule changed. |
| Transaction History / Shift Settlement | Recorded financial transactions and receipts versus current Cashier shift reconciliation. No calculation or permission changed. |

The fixed stage thresholds remain payment pending 5 minutes, Preparing 20, Ready handoff 10, Rider assignment 10. The order-age review preference defaults to 20 minutes and is stored per cashier in local browser preferences. It is not an established restaurant SLA. Source order history and payments are Supabase-backed; Dashboard aggregation and date partition are client-side read models. A read-only hosted `pg_policies` query confirmed Cashiers can read their own profile while Managers can read profiles generally, so the Cashier UI does not attempt to resolve another account’s name.

## Cross-module impact and remaining risks

Only active Cashier source, Cashier regression scripts, and Cashier QA documentation changed. Customer, Kitchen/KDS, Manager, Rider, POS creation, Pending Payments verification, receipts, financial reporting, schema, RPC signatures, and RLS were not edited.

Other account names and roles cannot be resolved through current Cashier profile RLS; “Recorded account (identity unavailable)” is intentional. The stage thresholds are hardcoded existing constants, while the order-age review threshold is cashier-local; management would need a policy and contract change to define a restaurant-wide SLA. Dashboard aggregation is still a client read model over RLS-visible orders and payments, so authenticated browser verification of live counts, filters, responsive layout, and refresh remains open. The older backlog is preserved without reclassifying or mutating historical orders.
