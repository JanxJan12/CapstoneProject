## 4. Hosted migrations, schema and authorization alignment

The business mutation and private-read RPCs are callable by `authenticated`, not `anon`, and their bodies check active role/ownership; internal payment-lock and closed-snapshot trigger functions deny `authenticated` direct execute. `payments` has RLS enabled and no direct client policy. `orders`, `cashier_shifts`, and `cashier_transactions` have RLS enabled; active Cashier direct shift/transaction reads are owner-scoped and active Manager reads are allowed where intended. Hosted migration ledger versions are **not identical** to some local filenames, though inspected objects align semantically. The latter hosted function body and active local file agree on owner scope and one-payment/one-transaction validation. Hosted `cashier_shifts` retains expected/actual/variance/closed-by fields but no retired notes/variance-reason columns; `cashier_transactions` has request/shift/status but no retired transaction-number column. `get_closed_cashier_shifts` still returns two legacy approval-shaped columns as typed `NULL` for compatibility; neither active Cashier nor Manager UI consumes them. **Do not use a repository-wide migration push based on filename comparison.** This audit did not establish hash-level equality for every historical migration.

## 5. Financial reconciliation

The active provisional Cash Drawer estimate is `openingCash + completed Cash transaction amounts − legacy locally classified Cash refunds` in `shiftService.calculateShiftTotals`. GCash is counted separately, and the disclosure says physical refund movements are not tracked there. The authoritative hosted close RPC uses `round(opening_cash + sum(payment.amount for completed cashier_transactions on the exact shift with verified Cash payments), 2)`. It separately sums verified completed GCash, rounds actual counted cash to two decimals, and saves `variance = round(actual − expected, 2)`. Voided/non-verified rows do not enter those sums; cancellation of paid orders uses the Manager refund path, and closed snapshots are immutable. The live estimate and saved settlement are therefore intentionally different authorities. The browser subtracts legacy locally classified cash refunds while the server closure formula does not; no current hosted mismatch was demonstrated, so this is an explicitly labeled reconciliation boundary to explain during a demo, not a proposed financial-rule change.

At inspection, seven of seven closed shifts had non-null expected/actual/variance; seven of seven saved variances equaled rounded actual minus expected, and seven of seven saved expected amounts matched opening plus *currently* verified completed Cash on their shift. The sample had 29 completed/verified Cash and 14 completed/verified GCash transaction rows, zero voided rows, zero completed rows with non-verified payment, and zero transaction rows lacking a shift. This is a current aggregate consistency check, not proof that later refunds cannot create a valid difference from immutable historical snapshots. Database unique indexes prohibit duplicate transaction order/payment/request/receipt links and duplicate GCash references under the current index rule.

The one pending online GCash row has no Cashier transaction/shift link yet. That is expected before verification and does **not** narrow the backend closure guard: the hosted `close_cashier_shift` checks pending online GCash across the restaurant under an advisory lock shared with pending-payment insert/resubmission. The local Cashier queue warning is advisory; server eligibility remains authoritative. `ORD-000080` stayed pending and was not accessed for a decision.

## 6. Security, failure and cross-module integration

- **PASS, direct contract evidence:** Hosted verification requires active Cashier, open shift, pending online GCash, owned stored proof path/object, amount equality, order waiting status, locks, and unique transaction links. A replay of the same request ID returns its existing transaction; another request cannot verify an already processed payment/order. This validates contract design, not a live malicious-input test.
- **PASS, direct contract evidence:** Hosted start/close require active Cashier; Manager cannot close a Cashier shift through that RPC. Shift/transaction RLS and history RPC distinguish Cashier ownership from Manager audit access. Prior Track 2C rollback-only tests executed those role boundaries on a disposable database.
- **PASS, source evidence:** POS keeps a request ID across uncertain submission and searches the current shift before another attempt; payment page blocks decisions while reconciling an ambiguous result; closure dialog reads open/closed status and requires recheck rather than blind resubmission. Actual dropped HTTP responses remain untested.
- **PARTIAL:** Customer quote/place/submit and private proof upload feed Cashier online payment hydration; Kitchen status RPCs feed order stage/ready handoff; Rider assignment status is polled and read through a Cashier RPC; Manager paid cancellation/refund and shared saved-shift audit are separate paths. These interfaces were inspected only as needed. No Customer, Kitchen, Rider or Manager business action was run.
- **PASS, source evidence:** Receipt preparation requires a recorded matching transaction/payment/item snapshot, and the UI disables printing voided receipts. CSV serialization prefixes spreadsheet formula starters. No new authenticated export or browser print was observed.
