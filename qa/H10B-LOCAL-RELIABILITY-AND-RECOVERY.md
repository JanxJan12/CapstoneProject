# H-10B local reliability and Checkout recovery — 2026-10-16 (Manila)

**Result: PASS for isolated local Checkout recovery, account/request isolation, payment progression, and authoritative SQL.** Docker resource exhaustion was confirmed during the blocked run; the full restored container set responded at the end of this run. Long-term reliability under simultaneous stacks still needs observation. Hosted Supabase remains READ-ONLY and restaurant deployment remains NO-GO under its separate gates.

## Local reliability diagnosis and recovery

The preserved `rrj_h09_order_flow_20261015` stack was used throughout. Before recovery, Docker Desktop said `running`, WSL was running, and ports 48321/48322 listened, yet **three Auth and three PostgREST requests timed out at 4 seconds**. Docker API and SQL calls also stalled. The H-09 DB/Auth/Kong containers were nominally healthy, demonstrating that container health alone did not represent interactive responsiveness. H-09 Auth had restart count **4**; its DB and Kong had restart count **0** in the inspected containers. PostgreSQL logs showed startup recovery after an earlier unclean shutdown and delayed autovacuum workers; PostgREST logged only startup DB-unavailable errors, and the inspected Kong tail contained no errors.

The Docker WSL VM had **7,803 MiB total RAM**, only **1,235 MiB available**, and **1,798/2,048 MiB swap used**. Load averages reached roughly **755/796/499**; memory and I/O pressure were high. The kernel recorded a **global out-of-memory kill** of `beam.smp` in an unrelated analytics container. Docker listed **94 running containers** using about **5,900 MiB** in aggregate. Three analytics containers outside H-09 accounted for about **1,578 MiB**. Docker backend logs also showed repeated port bind failures on **60321/60322** for a separate synthetic replay stack; these do not establish the cause of H-09 Auth delay.

For a reversible mitigation, `supabase_analytics_my-local-todo-app`, `supabase_analytics_rrj_phase8_sim`, and `supabase_analytics_rrj_h08c_history_20261015` were stopped gracefully. No volumes or databases were removed. WSL available RAM rose to **2,605 MiB**, current memory pressure fell to zero, and Auth returned HTTP **200 in 92/19/15 ms** while PostgREST returned **200 in 378/54/57 ms**. Both browser runs and SQL reconciliation then completed. The three containers were started again and confirmed running; immediate post-restore Auth checks were **200 in 82/10/15 ms** and PostgREST **200 in 182/126/91 ms**. This sequence, together with the OOM log, supports **VM resource exhaustion as the cause of the observed failure**. It does not prove every earlier intermittent episode had the same cause. Restoring all 94 containers leaves limited headroom (about **1,049 MiB available** immediately after restoration), so longer-term stability remains **NOT TESTED**.

## Authenticated Chrome post-commit recovery

The focused [H-10A browser result](h10a-browser-20261016/result.json) committed new synthetic **`ORD-000062`** with request ID `18a1fdfb-137b-4987-811c-439f2d847fe4`. The Chrome CDP Fetch interceptor paused the `place_customer_order` **POST response stage at HTTP 200**. Independent SQL confirmed the committed row and order count **29→30** before `Fetch.failRequest(ConnectionClosed)` dropped the response. Checkout showed the uncertain-response explanation. After refreshing the **same tab**, the same authenticated Customer and request ID remained, and name, contact, address, and landmark were restored. The explanation and **Retry & Check Order** button appeared. Clicking it returned **`ORD-000062`**, with order count still **30**, one request row, one order number, and an identical purchase-time item/modifier snapshot.

A second disposable [H-10B commit checkpoint](h10b-browser-20261016/commit-checkpoint.json) created **`ORD-000063`**, count **30→31**, through the same response-stage failure. Its extended harness stopped after the successful retry because it wrongly expected the draft's `responseUnknown` flag to remain true after retry. That was a harness assertion error; the Checkout had reset the flag on the next submission. `ORD-000063` was retained and reused. No additional order was created by the corrected isolation harness.

The [account and request isolation run](h10b-browser-20261016/isolation-clearing-result.json) used a second local synthetic Customer profile and seeded the **previously committed** `ORD-000063` request/draft into a fresh Chrome tab to exercise the guards. Rendered Customer sign-out/sign-in showed blank address/landmark and no recovery explanation for the second account. Returning to the first account restored its draft. Changing only the stored request ID to an unrelated UUID, then refreshing, again showed blank address/landmark and no recovery explanation. Restoring the original ID and clicking **Retry & Check Order** returned `ORD-000063`. A single simulated local GCash claim then cleared both `rrj_customer_order_request_v1` and `rrj_customer_delivery_retry_v1`. This was synthetic browser/storage guard testing, with no real payment.
