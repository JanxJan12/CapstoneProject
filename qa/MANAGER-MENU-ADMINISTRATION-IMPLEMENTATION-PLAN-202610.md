# MGR-01 — Conditional implementation specification

**Status:** REQUIRES POLICY APPROVAL. This is a plan, not an instruction to implement or deploy. The [policy decision sheet](MANAGER-MENU-ADMINISTRATION-POLICY-202610.md#restaurant-decision-sheet) defines the owner decisions. The [technical assessment](MANAGER-MENU-ADMINISTRATION-TECHNICAL-READINESS-202610.md) records the current contract. No new ordinary product/category editing scope is approved by repository evidence.

## Scope gate

**Existing/technically available:** Manager menu read, name/code search, category filter, manual availability, guarded existing Fixed Meal Options, and guarded existing Drink Choices. **Requires policy approval:** every ordinary product/category write, ordinary price changes, images, retirement rule, and any expanded recipe editing. **Requires technical change after approval:** corresponding narrow server writers, audit, validation, and UI for only the fields authorized. **Out of scope for MGR-01:** discounts/tax/fee policy, financial record changes, general inventory/recipe overhaul, legacy generic modifiers, unrelated Manager batches, and hosted deployment. A wording change to describe the existing page accurately could be a later small batch if the owner chooses technical/owner-managed master data.

## Conditional batches and effort

1. **Policy freeze (required before code; small decision effort).** Obtain dated restaurant approval identifying who may add products; edit name/description/category; change ordinary prices and choice adjustments; manage categories/images; retire items; and approve recipes/rice quantities. Choose Manager self-service or owner/technical maintenance. Record approvals and disallowed fields. No implementation begins while those answers are missing.
2. **Narrow catalog writers and audit (medium to large, only approved operations).** Draft reviewed additive SQL migration(s) for field-specific SECURITY DEFINER functions; validate active Manager or a narrower approved role, set safe `search_path`, explicitly revoke public/anon, grant only intended execution, retain denied direct table writes, lock rows, validate values and category state, record actor/time/reason/before-after, and return authoritative row. Avoid generic JSON mass-update or arbitrary column writer. Include active/inactive publication policy and recipe gate for new products. Migrations and hosted deployment require their own explicit approval.
3. **Mounted Manager editor (medium, only after approved backend).** Extend [MenuManagementPage](../src/modules/manager/menu/MenuManagementPage.tsx#L39) and a focused Manager API module beside [managerPhase2Api](../src/modules/manager/api/managerPhase2Api.ts#L438). Add only approved create/edit/archive/category forms and separately gated price/image actions. Show field errors, loading, stale-data/conflict and uncertain-write reread, unsaved-change warning, accessible keyboard/mobile behavior, and manual versus effective availability. Do not imply a paused item is in stock. Preserve current meal/drink/availability controls.
4. **Image path, if approved (medium).** Define an approved Storage bucket or static asset publication process, file limits, MIME/type checks, private/public access decision, orphan cleanup, and Customer/Cashier rendering. The present Customer `image_path` and Cashier static ProductCard images differ, so verify both before enabling image edit. Do not repurpose payment or Rider document buckets.
5. **Focused acceptance and release review (medium).** Isolated database/browser scenarios for the exact approved operations, role denial, constraints, audit, quote refresh, historical snapshots, Cashier, Kitchen, inventory, Reports, and image behavior. Then separately review migration contents/hash, hosted preconditions, cutover, rollback, and approval. Do not edit real menu or order records during QA without separate authorization.

## Acceptance rules for an approved self-service batch

- A Manager with approved authority can change only approved fields; another Manager, Cashier, Customer, anon, and inactive profiles are denied according to the chosen policy. Hidden controls alone are insufficient.
- Create/edit rejects blank or duplicate code/name where required, invalid category, invalid/precision-breaking price, unauthorized image path, and incomplete recipe/publication state. Exact business limits come from the approved policy.
- New or renamed categories have deterministic active-product handling. Retired products remain retrievable through historical receipts and Reports. Foreign key constraints and order snapshots remain intact; there is no hard delete of transacted menu items.
- A future Customer quote and Cashier catalog reflect an approved change; a stale Customer quote is rejected and re-confirmed at current authoritative price. Existing `order_items.item_name`, `unit_price`, `line_total`, `modifiers`, and order totals are unchanged by menu editing.
- Availability tests separate manual pause from ingredient-stock gating; Fixed Meal With/Without Rice and required drink choices retain their current guards. No rice item or serving quantity is invented.
- Every successful write has authoritative readback and an audit record for the chosen fields. Invalid/unauthorized writes produce no audit success or partial menu change.
- Local typecheck/build, focused SQL role tests, synthetic authenticated UI behavior, and cross-module regression pass before release review. A fixture pass is described as fixture evidence, not a faithful hosted runtime replay.

## Rollback and operating safety

Before a later rollout, capture reviewed migration SQL, object signatures/grants, dependent contracts, and a catalog backup/recovery plan. Prefer reversible feature exposure and disabling newly introduced writers/UI if they misbehave; do not attempt to repair a bad price edit by rewriting historical orders. If a migration or activation fails, pause the new editing action, preserve secure role denial, inspect audit/readback and dependent menus, then use a separately reviewed corrective migration. Existing live availability, Fixed Meal, and Drink Choice contracts remain regression gates. Any production migration, permission change, Storage policy, or real-record edit needs separate explicit approval.
