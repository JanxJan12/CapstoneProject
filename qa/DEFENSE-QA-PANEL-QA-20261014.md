# RRJ’s Food-House defense panel questions

**What is the system boundary?** The React web app and standalone Expo Rider app share Supabase Auth, PostgreSQL, PostgREST RPCs, and private Storage. The browser and Rider are clients. Important order, payment, stock, role, and lifecycle decisions happen in database functions; the UI reports their returned state. The Rider source is a separate codebase, and its demo APK points only at the local emulator endpoint.

**Is the demo using the restaurant’s live data?** No. The dedicated unlinked stack has explicitly synthetic menu prerequisite rows, fictional opening batches, local demo accounts, and generated orders/proofs. Some menu or stock names appeared in interviews, but the project never received a comprehensive, approved master dataset. We do not turn partial interview confirmation into a claim that all values, recipes, or opening counts are authoritative.

**Why does the migration ledger say 52 while the repository has 51?** The 51 current source files are preserved byte-for-byte. A disposable demo runtime inserts one explicitly synthetic historical prerequisite before Phase 2A and uses two local diagnostic compatibility variants. A pristine replay of the 51 original files fails with SQLSTATE `23503` because historical recipe mappings refer to missing menu/inventory IDs; later enum qualification also needs a reviewed solution. Therefore the 52-version demo install demonstrates downstream function, **not** production clean-install reproducibility. `qa/MIGRATION-REPRODUCIBILITY-RESOLUTION-20261014.md` records the separate failing gate.

**How are user roles enforced?** Each demo person signs in through local Supabase Auth, gets a real session, and has a server profile role. Protected web routes check that role, while RLS and RPC role checks enforce the boundary again. A Customer cannot verify GCash proof or act as a Rider; wrong KDS secrets and repeated terminal advances were denied in local tests. Frontend hiding alone is not the security boundary. The KDS terminal is a separate ID/secret credential, not a shared staff account.

**Can a forged modifier price reduce an order total?** The Customer sends menu and option IDs. The server checks active options, group selection rules, and current prices, then stores a purchase-time `{id,name,price}` snapshot on each line. Local API tests checked the snapshot and Cashier/KDS/Rider projections; the browser POS test selected Extra rice and reconciled the sale to the stored server amount. A modifier table by itself would not be enough; the active order RPC is the pricing contract.

**When does stock move?** Formal request issuance, Production preparation, dispatch, acknowledgment, and Receiving draft save no stock. `post_receiving_report(uuid)` posts accepted quantities to batch and movement ledger; rejected quantities do not enter stock. Tests proved a partial report, draft no movement, one batch and receiving movement, Manager adjustment, and no negative item totals. The demo opening batches are fictional and must not be interpreted as a physical count. Online orders do not pre-reserve inventory; walk-in deduction follows the existing batch-aware sale rule.

**Where are recipes and personal information?** Recipe mappings and historical master-data provenance are sensitive; the demo flow diagram and handout omit ingredient quantities. Proof buckets are private, and screenshots use synthetic contacts/addresses. The reports contain no passwords, service keys, terminal secret, private proof bytes, or real customer PII. The private local role card stays on the presenter machine.

**Does a GCash screenshot prove that money arrived?** No. The demo checkout explicitly displays `NO REAL ACCOUNT` and `DEFENSE DEMO — DO NOT PAY`. The app stores a private synthetic proof and a Cashier’s internal verify/reject decision. It does not query or settle with GCash. The same fresh synthetic order was exercised from Customer submission through Cashier verification, KDS Ready, Rider emulator delivery and Customer tracking; actual settlement would need provider integration, reconciliation, and operational controls before restaurant use.

**How do you prevent duplicate orders and double posting?** Customer placement uses a request ID and returns the same order for an idempotent replay. Payment and KDS transitions reject stale repeated actions. Receiving posting is atomic, rejects duplicate or over-limit posts, and records stock movements once. Fresh demo runs create new UUIDs and do not reuse consumed order numbers.

**Why is the Rider phone demonstration limited?** The final local APK uses Android emulator host-loopback `10.0.2.2:61321`. On the emulator, an approved Rider signed in and completed both independent `ORD-000013` and the continuous browser-created `ORD-000017` with pickup, transit, synthetic gallery proof, and Delivered History. Customer Chrome then showed `ORD-000017` as Delivered. A physical phone cannot reach that loopback address. A real camera, physical handoff, and handset network path were not tested.

**Is this ready for a real restaurant rollout?** No. The capstone demo can be judged on its isolated, labeled synthetic workflow. Actual rollout remains NO-GO until authoritative master data and opening balances are approved, the untouched migration replay and independent encrypted off-device recovery set pass, hosted changes receive separate authorization, and hosted/browser/device/OAuth/payment/physical acceptance are completed. The local demo is not a waiver of those gates.
