# RRJ’S FOOD-HOUSE database architecture — final assessment

**Date:** 2026-10-14 (Asia/Manila). **Decision:** **GO for the already rehearsed isolated synthetic Capstone defense demonstration; NO-GO for restaurant production deployment or hosted schema/data changes.** This is an assessment, not a migration or release approval. No database or application object was changed in this pass.

## Evidence boundary

The [34-table normalization matrix](DATABASE-NORMALIZATION-ASSESSMENT.md) and [performance plan](DATABASE-PERFORMANCE-OPTIMIZATION-PLAN.md) use the existing [architecture optimization](DATABASE-ARCHITECTURE-OPTIMIZATION-20261014.md), [disposition](DATABASE-DISPOSITION-REGISTER-20261014.md), [ERD](DATABASE-TARGET-ERD-20261014.mmd), [recovery](DATABASE-REPRODUCIBILITY-RECOVERY-20261014.md), [release gates](RELEASE-READINESS-GATES-20261014.md), and [defense readiness](DEFENSE-DEMO-READINESS-20261014.md) reports, plus the 51 preserved migrations, catalog snapshot, constraints, SQL RPCs and service-layer query paths. Hosted figures are dated captures, not a new live query. Docker was unavailable for a new isolated `EXPLAIN`; performance opportunities remain unmeasured. The Rider repository and APK were not modified or retested for this assessment.

### Security and integrity interpretation

The combination of RLS and RPC authority is sensible for this application, but the count of 83 `SECURITY DEFINER` functions warrants a function-by-function preproduction inventory of effective EXECUTE grants, `auth.uid()` and role checks, `search_path`, dynamic SQL, and cross-role negative tests. `advance_kds_order` and other terminal-authorized paths require credential-specific review; an `anon` EXECUTE grant alone is not proof of a vulnerability or safety. Do not change privileges as part of this assessment. The already prepared MAINTAIN grant migration remains a separate review item.

Transaction atomicity and row/advisory locks are visible in Receiving, formal requests, and stock deduction migrations. The prior isolated same-database tests covered selected duplicate/concurrent posting, rejected or partial receipt, role denial, exact allocation, and reversal cases. That is meaningful local proof, not evidence of hosted load, every interleaving, or a successful clean install. Exact stock and financial reconciliation must be repeated on a later approved target before and after any change.

The ERD's KDS terminal → order-status edge describes authorization/event flow, **not a declared FK**. `payments` and `cashier_transactions` differ in purpose; `inventory_items.quantity_on_hand`, `inventory_batches.quantity_on_hand`, and `inventory_transactions` have different grains. Formal Manager documents and single-item Production replenishment requests cannot be merged without losing owner/version/status meaning. Historical snapshots, event repetitions, and empty conditional tables must remain until retention and consumer evidence establishes otherwise.

## Answers to the ten engineering questions

1. **Adequately normalized?** **Yes for the current transactional design, with documented exceptions.** Most relationships have clear grains and declared keys. This is an engineering judgment, not a formal proof of 3NF/BCNF for every business FD.
2. **Which forms are demonstrable?** Scalar columns and bridges support conventional 1NF/2NF for much of the schema; JSON/arrays and time-specific snapshots need semantic qualification. Explicit arithmetic dependencies prevent a blanket strict 3NF/BCNF claim. BCNF is **not proven globally** because complete business determinants are unavailable.
3. **Further investigation?** Highest priority: `cashier_transactions`, `paid_order_cancellations`, `receiving_report_items`, `inventory_batches`, `inventory_transactions`, `inventory_transaction_batch_allocations`, and request/receipt reciprocal links for cross-table identity; `orders`, `order_items`, `inventory_items`, `purchase_order_items` for projection reconciliation; structured-payload tables only if element-level rules arise. `supplier_items` needs owner/external-consumer confirmation, not a drop.
4. **Confirmed redundancies?** Two duplicate timestamp triggers in the earlier hosted snapshot; already addressed in a preserved isolated local stack. **No** table, business row, column, or index is proven redundant.
5. **Justified denormalization?** **Yes, conditionally:** sold-at-time prices/names/modifiers, issued request revisions, event payloads, order/shift/PO totals, and stock balances support audit, customer display, and operational reads. Their writers and reconciliations are the condition for safety.
6. **Proven performance bottlenecks?** **None.** Static SQL/index shape and zero-scan counters cannot establish latency or an improvement.
7. **Safe worthwhile improvements?** Now: read-only relationship mismatch counts and sanitized workload/plan baselines. Later, one validated writer guard or index at a time if evidence identifies a defect. The existing guarded duplicate-trigger cleanup is the smallest proven object-level optimization, subject to hosted release gates.
8. **Changes to avoid?** No table/index/history deletion from empty or zero-scan evidence; no unique `(order_id,status)` history index; no order snapshot rewrite from current menu; no recomputation of stock from incomplete opening history; no request-family merge, blind migration replay, hosted permission/schema edit, or synthetic business baseline.
9. **Is restructuring necessary?** **No broad restructuring is justified.** The existing normalized core and intentional projections can support the demo and incremental growth while measured defects are addressed.
10. **Smallest safe next improvement?** A read-only, privacy-safe cross-table relationship and reconciliation baseline, followed by targeted RPC review. As a future DDL candidate, the already versioned duplicate-trigger cleanup has the narrowest proven scope, but hosted application remains blocked by independent recovery/replay/approval gates.

## Recommended implementation sequence and rollback requirements

| Order | Proposed change or decision | Impact | Reversible approach and regression gate |
| --- | --- | --- | --- |
| 1 | **No schema change:** capture relationship mismatch counts, current grants/function definitions and sanitized workload/plans. | Read-only observation; no application impact. | No rollback needed. Verify query is SELECT/plain EXPLAIN, does not expose private values, and identifies the exact catalog snapshot date. |
| 2 | **Conditional writer guard** only if a real mismatch path is proven (for example PO line item vs Receiving item, or payment vs receipt order). | May reject previously accepted operations or historical exceptions. | New forward migration with exact prior RPC body retained for restoration; test valid legacy/current paths, bad-link denial, idempotent replay, concurrent posting, RLS/role denials, and no change to totals, ledger or private proofs. No data repair without separate provenance. |
| 3 | **Conditional non-unique composite index** only if representative plans show a material gain. | Extra storage/write cost and possible build lock; query output unchanged. | Add one named index in a new migration on isolated/staging first; compare old/new plan, p50/p95, buffers, writes and locks. Roll back by dropping only that named new index after dependency check. Keep unique/partial business indexes. |
| 4 | **Already prepared duplicate-trigger cleanup** after separate hosted gates. | One fewer timestamp trigger call on each of `profiles` and `riders`; no row/column removal. | Use the guarded existing migration, not a rewritten original. Existing rollback SQL recreates only the two removed `trg_` names after catalog confirmation. Test Auth/profile, Rider approval, timestamps, grants/RLS, counts and role flows. |
| 5 | **Production promotion decision.** | Potentially broad operational risk. | Requires provenance-backed historical baseline, successful clean chronological replay, encrypted off-device database/Auth/Storage object-byte backup and restore rehearsal, complete isolated regression, and separate hosted/browser/device acceptance. No promotion before those pass. |

## Demo versus production

The [defense readiness report](DEFENSE-DEMO-READINESS-20261014.md) records a continuous local Chrome → Android emulator workflow and Manager request → accepted-only Receiving → batch/ledger proof with synthetic data, plus scoped security checks. That supports the **isolated Capstone defense GO**. It does not establish real GCash settlement, physical stock, physical Android camera/handoff, hosted OAuth, all hosted private proof bytes, or a clean install from the unmodified 51 migration chain. The [release gate](RELEASE-READINESS-GATES-20261014.md) and [recovery report](DATABASE-REPRODUCIBILITY-RECOVERY-20261014.md) therefore keep restaurant production **NO-GO**.
