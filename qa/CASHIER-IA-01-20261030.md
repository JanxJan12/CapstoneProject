## Executive summary and architecture

The active Cashier sidebar now has one **Orders & Receipts** destination with accessible **Orders** and **Receipts & Sales** views. Orders retains the operational Order List component and its actions. Receipts & Sales retains the historical Transaction History component, including the deployed `get_cashier_transaction_history` read model, server-bounded paging, same-filter CSV export, own-sale detail, and reprint. No order, payment, and receipt record was merged. The two views mount on first use and remain mounted while switching within the workspace, so filters and selection state are retained without loading historical History merely because Orders was opened.

Previously, the active `CashierModule` exposed separate sidebar IDs `order-list` and `transactions` with F4/F6 shortcuts and in-memory page state under `/cashier`. The app now uses protected `/cashier/*` child URLs: `/cashier/orders-receipts/orders` and `/cashier/orders-receipts/receipts`. F4 selects Orders; F6 selects Receipts & Sales. Direct legacy `/cashier/order-list` and `/cashier/transactions` paths resolve to the matching view and replace to canonical URLs. `/cashier` still opens Dashboard. All routes remain inside `RequireAuth role="cashier"`; no URL bypasses that gate. Existing internal aliases and notification destinations map through the same resolver.

The [lineage audit](CASHIER-IA-DATA-LINEAGE-20261030.md) establishes `orders` plus item/status/payment/assignment records as the operational projection and `cashier_transactions` plus payment/order/shift joins as the receipt audit projection. [DATA-01](CASHIER-DATA-01-20261030.md), [DATA-01B](CASHIER-DATA-01B-20261030.md), [DATA-01C](CASHIER-DATA-01C-20261030.md), [DATA-01D](CASHIER-DATA-01D-20261030.md), [final QA](CASHIER-QA-FINAL-20261030.md), [manual findings](CASHIER-MANUAL-FINDINGS-20261030.md), and applicable OPT reports were reviewed. ## Implemented behavior

- Orders keeps Today's Work, All Orders, Older Backlog, search/filter/sort, pagination, CSV, expansion, drawer/timeline, operational edit, eligible cancellation, ready release and Rider status. No order action or payment rule changed.
- Receipts & Sales keeps completed/voided historical records, method/date/shift/terminal/customer/order/receipt filters, 50-row pages, total counts, summary, details, audit, same-filter CSV, and completed-receipt reprint. Its transaction detail now explicitly labels payment method, current order fulfillment, and shift terminal so a completed sale cannot be mistaken for a completed food order.
- Order detail offers **Find receipt** only when it has a persisted order UUID. It makes one on-demand, at-most-100-row query against the cashier-owned historical RPC. A matching result must have the same cashier ID, order UUID and human order number, plus the known transaction ID if present. A missing or inaccessible row shows an informational message; no receipt is fabricated. Voided records can open in financial detail but retain the existing no-print guard.
- Transaction detail offers **View linked order** only when the authorized own-sale detail's order ID and database UUID match an order in the Cashier operational store. Otherwise it states the order detail is unavailable. The target opens in All Orders with its drawer; no customer-name or amount matching is used.
- Switching views uses client routing without a full-page reload. Visited views retain their local filters; inactive detail dialogs close and inactive `/` search listeners detach. Toolbar/export and business-specific tables remain separate.
- Dashboard order/financial shortcuts and notifications still use their old internal page IDs, which resolve to the correct consolidated view. The existing Dashboard recent-receipt reprint dialog remains a direct route to its intended receipt. Sidebar F4/F6 preserve their familiar targets.

## Read model, performance, and security

The frontend still calls `get_cashier_transaction_history` through `fetchHistoryPage` for History screen and CSV. A fresh **read-only hosted catalog check** found the deployed signature `(integer, integer, jsonb)`, `SECURITY DEFINER`, `postgres` owner, empty search path, explicit NULL-page guard, both transaction and shift ownership predicates, `anon` execute denied and `authenticated` execute granted. DATA-01D records deployment version **20261030042437**. This check does not substitute for an authenticated Cashier A/B browser test. No direct `payments` read or former current-shift-only query was introduced into History.

Opening Orders does not mount the historical History hook. After first Receipts visit, its current page remains in memory while switching tabs; it does not refetch on every switch. The shared Cashier provider still loads operational orders and current-shift data for other workspaces, so that existing provider-wide traffic remains. One History lookup is added only when **Find receipt** is clicked; there is no per-row N+1 lookup. The server keeps the 1–100 row and 0–10,000 offset bounds, deterministic sort, closed-shift access, and 5,000-row CSV client limit. Existing offset/concurrent-export consistency and high-volume index questions remain as documented in DATA-01.

Current order descriptive fields in old receipts and offset pagination under concurrent writes retain the limitations documented in DATA-01. No new backend or financial defect was found in this task.
