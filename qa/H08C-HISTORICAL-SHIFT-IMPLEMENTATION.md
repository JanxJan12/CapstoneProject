# H-08C historical shift access — isolated local implementation

**Scope:** Owner-approved active Cashier own history, active Manager all-Cashier audit, stale-token denial after deactivation, and immutable closure snapshots. No hosted deployment or accounting-policy change. This builds on the dirty canonical checkout without resetting it. The original 51 migrations were not edited; H-08C adds `20261014191853_h08c_historical_shift_access.sql` after them.

## Contract and source changes

- `supabase/migrations/20261014191853_h08c_historical_shift_access.sql` replaces the existing `cashier_shifts_select_staff` policy. Both own-Cashier and Manager branches now require a **current active profile and role**. Anonymous and authenticated table grants are reduced; authenticated receives SELECT only on the safe shift columns used by the invoker RPC and existing staff reads. No direct client INSERT/UPDATE/DELETE remains. Existing privileged start, close, and open-shift RPCs remain in place. The new RPC has authenticated-only EXECUTE; anonymous and PUBLIC EXECUTE are revoked.
- `get_closed_cashier_shifts` returns only closed shifts and explicit settlement fields. It checks `auth.uid()` against the current active profile on every call, enforces ownership or approved Manager scope, validates date bounds/cursor/page size (1–50), and sorts by `ended_at DESC, id DESC` with a keyset cursor. Cashier supplied cross-owner filters are rejected. It uses `SECURITY INVOKER`, schema-qualified objects, and an empty fixed search path. No receipt, payment, customer, private profile, or synthetic cache fields are projected.
- A trigger rejects changes to closure facts or deletion after a shift is closed. Manager approval fields remain independently available for a future separately approved workflow; the start/close flow changes an **open** row and is not blocked by this trigger.
- `src/modules/cashier/api/closedShiftHistoryApi.ts` validates RPC rows and converts Manila calendar-day filters to inclusive UTC start and exclusive next-day UTC end. It requests 26 records and presents 25, using the extra record to determine whether a next page exists.
- `src/modules/cashier/shifts/ClosedShiftHistory.tsx` keeps fetched history in component memory and exposes date filters, bounded paging, loading, empty, retryable error, and saved-detail states. It identifies figures as closure snapshots. It does not recalculate as-closed cash/GCash or transaction counts from current receipts.
- `src/modules/cashier/shifts/ShiftSettlementPage.tsx` mounts the authoritative history below the current open shift and stops rendering local cached closed shifts or prototype rows as history. `src/modules/manager/index.tsx` mounts the same read-only component under Manager **Shift Audit** navigation. Existing role route guards remain; database checks supply the actual authority.

## Permission delta and compatibility

Before H-08C, the H-08B local catalog had an authenticated table SELECT grant, an anonymous SELECT grant restricted to zero visible rows by RLS, and authenticated write grants without matching shift write policies. Its own-Cashier SELECT policy lacked an active-profile check, so an inactive Cashier's valid JWT could still read its own shift directly. After H-08C, both direct SELECT and RPC evaluate the current active profile. The new isolated catalog confirms RLS enabled, `authenticated` table-level SELECT **false** but explicit column SELECT **true**, authenticated table UPDATE **false**, `anon` column SELECT **false**, authenticated RPC EXECUTE **true**, anonymous RPC EXECUTE **false**, and service-role SELECT/UPDATE **true**. The only shift SELECT policy requires an active `profiles` row with Cashier ownership or Manager role. The new RPC is invoker/stable; existing start/close/open RPCs remain definers and were not edited. Authenticated HTTP checks confirmed stale inactive Cashier and Manager JWTs are denied via both RPC and direct-table REST. A new RPC by itself would not have repaired the prior direct-table stale-token path.

## Local migration and rollback plan

The disposable H-08C stack is a copy of the H-08B **52-version diagnostic chain** plus this migration (53 versions). That diagnostic chain contains a synthetic historical prerequisite and is not a clean replay of the original 51 migrations. Keep original stacks, volumes, backups, and the hosted project untouched.

For a local rollback, first preserve the disposable DB, then drop `protect_closed_cashier_shift_snapshot` trigger/function and `get_closed_cashier_shifts` function. Restore the prior `cashier_shifts_select_staff` policy and pre-H-08C grants from that stack's catalog/backup, then restore the earlier frontend files. That rollback restores the known stale-token read gap; it is for isolated recovery only. Any eventual hosted deployment needs a fresh reviewed migration, provenance-backed clean replay, recoverable off-device backup/restore evidence, and separate explicit authorization.

No refund recognition, net-sales, post-close adjustment, payment, or stock formula was changed.
