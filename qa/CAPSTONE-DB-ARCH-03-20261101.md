## Objective, evidence boundary, and prior decisions

The aim is to remove responsibilities a restaurant designed around today's workflows would not need, while retaining financial snapshots, operational history, security, and independent authorities. Reused [DB-01](CASHIER-DB-01-20261031.md) and its column/elimination matrices, [DB-02A](CASHIER-DB-02A-20261031.md), [DB-02B](CASHIER-DB-02B-20261031.md), [DB-03A](CASHIER-DB-03A-20261031.md), [MIG-01](CAPSTONE-MIG-01-20261031.md), [ARCH-01](CAPSTONE-DB-ARCH-01-20261101.md), its dependency-probe conclusion, [ARCH-02](CAPSTONE-DB-ARCH-02-20261101.md), [Track A](TRACK-A-LEGACY-BACKEND-CONSOLIDATION-20261026.md), [six-table acceptance](SIX-TABLE-HARMONIZATION-LOCAL-ACCEPTANCE-20261027.md), and financial mapping. ## Four investigated opportunities

**1. Retire old Manager-request Reason write adapters — selected for clearance.** Exact objects: `public.issue_inventory_request(uuid,text,timestamptz,text,jsonb,jsonb)` and `public.revise_inventory_request(uuid,integer,text,timestamptz,text,jsonb,jsonb)`. The newer five- and six-argument signatures respectively own current Manager issue/revise. The old pair validates `p_reason`, invokes the current writer, and injects Reason into `inventory_request_revisions.snapshot`; it does not own an independent stock transaction. The `inventory_request_documents.reason` column has already been removed. `src/modules/manager/inventory/inventoryRequestApi.ts` sends only current argument sets, and current formal-request SQL tests use them. No Rider source caller was found. The hosted old issue signature nevertheless has **two observed PostgREST calls** versus three for the new issue signature in the available `pg_stat_statements` sample; revise-call attribution was not established. Authenticated can execute both old functions; anon cannot. This is an **external compatibility dependency**, not evidence that Reason remains a required new-request field. Hosted revision aggregate: **5 revisions, 2 with nonblank Reason**. Those two JSON values are historical obligations and must remain readable; `get_inventory_request_register()` still projects Reason from current revision JSON. No historical migration may be rewritten. Proposed end state removes the two old writer functions and their grants, retaining current writers, register projection and all five revision rows. Expected guaranteed post-clearance reduction: **2 public functions, 0 tables/columns/rows**. No current web/Rider module edit is needed; only focused tests and any external client migration. Barrier: identify/retire the observed old-signature consumer and establish a bounded no-use window or approved versioned transition. Dropping now would break a previously observed caller.

**2. Retire the unoffered discount authoring feature — conditional, not selected.** Exact persistence is `public.orders.discount_type`, `discount_reference`, and `discount_amount`; `create_walk_in_sale(...)` accepts old discount parameters and `get_cashier_sale`, `get_current_shift_cashier_sales`, and legacy `get_current_shift_walk_in_sales` project discount fields. Customer quote/place functions also calculate `discount_amount`; Customer, Cashier receipts/history, and Manager financial UI read that amount. Current POS fixes discount to zero and has no discount control. Hosted aggregate found **0 of 63** orders with nonnull type/reference or nonzero amount. Yet a charged discount amount is a historical financial fact and the existing RPCs are exposed contracts. The only conservative possible first reduction is the **two metadata columns** after restaurant discount-policy and external-writer clearance, with compatibility projections; deleting `discount_amount` or changing historic totals is **not approved**. Financial tests would need tax/total/receipt/shift and refunded-order cases, including a positive discount fixture. Expected 2 columns only, conditional; a broader three-column/branch retirement is speculative. The dependency burden and financial-policy uncertainty make this lower feasibility than candidate 1.

**3. Retire persisted dine-in table assignment — conditional, low impact.** Exact object `public.orders.table_number`; `create_walk_in_sale`, `update_cashier_order_operational_details`, sale and current-shift RPCs, and Cashier operational edit/hydration consume it. Hosted 0 of 63 orders have a value. A restaurant without table service could use order number/customer name for counter pickup, but the active UI permits table assignment, so business need is **unknown**, not disproved. Existing RPC return/input shapes and potential external clients are compatibility dependencies; no financial value is stored in this field. A business decision to end table seating plus caller transition could remove **1 column** and one workflow control, but that is a narrow gain and cannot be selected without the service-policy decision.

**4. Retire uploaded menu-image path — conditional, low impact.** Exact object `public.menu_items.image_path`; Customer menu loading selects it and maps it into cart/menu presentation, while Cashier/menu RPC references need exact field inspection at implementation. Hosted 0 of 20 menu items have a path. Text-only menu presentation could satisfy ordering, but product/brand image requirements and any private Storage objects or other clients are **unknown**; payment-proof image paths are unrelated and essential. Removing the column would save **1 column**, with Customer mapping/type and any menu projection changes. No uploaded image data should be deleted without a separate Storage inventory and owner decision. This is not a compelling structural batch today.

No FK/bridge/status-history table is nominated merely because it is empty. `paid_order_cancellations`, request revisions/events, KDS terminal and Rider push/proof records serve distinct exception, security, or audit purposes. `orders.geolocation` is rejected because it supports Rider's explicit-coordinate destination path. The six-table local-only candidate must finish its own acceptance rather than be counted twice here.

## Selected implementation specification: old Reason adapters

**Current flow.** Manager `inventoryRequestApi.ts` issues/revises formal multi-line requests through the current signatures. Both current writers own role checks, request/revision validation, idempotency and request history. The old overloads are compatibility shims: they require Reason, call the current writer, and preserve supplied Reason in revision JSON. The register reads that JSON; two of five hosted revision snapshots hold a nonblank value. Formal Receiving links and `post_receiving_report` then account for accepted stock; these must not be touched.

**Target flow and exact removal inventory.** New requests continue through `issue_inventory_request(uuid,text,timestamptz,jsonb,jsonb)` and revisions through `revise_inventory_request(uuid,integer,text,timestamptz,jsonb,jsonb)`. Retire exactly the two old signatures above, including their function ACLs. **0 tables, 0 columns, 0 triggers, 0 policies, 0 views, 0 FKs, 0 active web/Rider consumers, 0 stored snapshots are deleted.** Keep `get_inventory_request_register()` and its historical Reason projection, formal request tables, authorization helper, Manager UI, Receiving and stock posting. Historical migration definitions remain untouched. Update focused SQL/source tests only if they explicitly assert old overload availability; current tests must keep exercising the new signatures. An actual external client, if identified, must be migrated to the current argument set before retirement; if it genuinely needs Reason for a live business duty, stop and revisit the selection.

**Ordered next milestone.** (1) Identify the owner/client of the two observed old issue calls, query a fresh sanitized signature-specific workload window, inventory service-role and external API consumers, and obtain explicit retirement clearance. Absence in a short counter window alone is insufficient. (2) Capture exact hosted function definitions, grants, dependency references, current revision-count/Reason-key aggregates and a restorable current schema; hash the before-state. (3) Prepare a new forward-only local migration with exact-signature and definition/grant guards, two explicit `DROP FUNCTION` statements **without CASCADE**, and postconditions that the current writers, register projection, grants and all request/Receiving tables remain. Do not modify prior migrations. (4) Apply only in a disposable current-schema database with synthetic request/Receiving rows. (5) Run the acceptance matrix below and rehearse exact function/grant restoration; inspect diff and obtain separate hosted deployment approval. (6) If deployed later, monitor API errors and the retained current signatures; a new forward restoration is required after commit. No broad repository `db push` follows from this design.

**Data and restoration.** No backfill, transformation, archival table, deletion, or existing JSON rewrite. Preserve the two historical Reason values and all revision/event links. Before any future hosted change, prove recoverable database/Auth/Storage state under the separate release gates. A failed local transaction rolls back. After a committed deployment, restore only the captured two exact function definitions and grants in a reviewed forward migration, then recheck catalog and old/new authorized calls. Recreating the shims restores call compatibility but cannot recreate any request a client failed to submit during downtime; error monitoring and operational reconciliation are required. The separate Phase 2A replay blocker remains a production gate, not an excuse to rewrite history here.

**Required local acceptance.** Catalog: exactly two old signatures absent, current issue/revise and register present, expected grants unchanged, no unintended function/table/trigger/policy diff. Positive: active Manager issue, idempotent retry, revision with expected version, register/history, formal linked partial Receiving and accepted-only batch/ledger update. Negative: anonymous/Customer/Cashier issue/revise denied, stale revision/duplicate ID rejected, duplicate Receiving post no extra stock, old signatures unavailable only after declared cutover. Historical: pre-existing synthetic Reason revision and current non-Reason revision both remain readable and unchanged; hosted aggregates rechecked without extracting private text. Cross-module: Manager Requests/Receiving, inventory proposal, Cashier paid-order cancellation/settlement, Customer checkout, KDS and Rider order/delivery smoke as appropriate to the restored schema; report each local SQL, signed-in API/browser and device result separately. Financial: payment/receipt/shift counts and totals unchanged in fixture; no sale or settlement RPC altered. Migration: direct application and restoration A/B in isolated current schema, no `CASCADE`, no unintended grant widening. Full clean replay and hosted authenticated acceptance remain separate release gates.

**Quantified outcome.** Current hosted catalog: **36 public tables; four issue/revise overloads (two each)**. This milestone: **0 objects removed**. If clearance and implementation later pass: **36 tables remain; two issue/revise functions remain; two old functions removed**. Historic five revision rows and two nonblank Reason snapshots remain. No speed, storage, or labor saving is estimated. The already prepared six-table retirement, if separately approved/deployed, is excluded from these numbers.
