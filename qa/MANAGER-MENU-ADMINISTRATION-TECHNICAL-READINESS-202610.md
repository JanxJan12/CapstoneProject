# MGR-01 — Technical readiness for menu administration

**Assessment:** 2026-10-23; hosted project `zhzluhqvysvsadwuugpa`. **Status:** technically assessed, policy pending. Evidence below is source inspection and direct read-only hosted catalog inspection. No authenticated Manager/Customer/Cashier runtime write was attempted.

## Active path and available contracts

The [Manager page switch](../src/modules/manager/index.tsx#L393) mounts [MenuManagementPage](../src/modules/manager/menu/MenuManagementPage.tsx#L39), which calls the [Manager menu read and availability API](../src/modules/manager/api/managerPhase2Api.ts#L438), [Fixed Meal API](../src/modules/manager/api/mealOptionsApi.ts#L32), and [Drink Choice API](../src/modules/manager/api/drinkChoicesApi.ts#L23). The UI shows name/code search, category chips derived from loaded rows, manual/effective availability, and existing meal/drink configuration. It has no ordinary product/category create/edit/retire form, image upload, ordinary price editor, or ordinary master-data API. The Manager RPC read returns all menu rows under a Manager guard, including inactive rows, while availability changes refuse inactive items.

Direct hosted catalog inspection found `public.menu_items` (`id`, `category_id`, `code`, `name`, `description`, `price`, `image_path`, `is_available`, `is_active`, `aliases`, and Fixed Meal fields), `menu_categories` (`id`, `name`, `description`, `is_active`), `menu_ingredients`, `drink_choices`, and `order_items`. `menu_items.category_id` references `menu_categories` **ON DELETE RESTRICT**; `order_items.menu_item_id` references `menu_items` **ON DELETE RESTRICT**; recipe links from `menu_ingredients` reference menu items **ON DELETE CASCADE**. Hard deleting a transacted item is blocked by the order FK, but a product with no order reference could still remove its recipe links if a privileged delete path were introduced. Category deletion with assigned products is blocked. `menu_items.code` is unique and format constrained; category name is unique; product `price >= 0` is only a database floor, not a fully approved positive-price business rule. Fixed Meal fields have paired mapping and price constraints. `order_items` stores `item_name`, `unit_price`, `line_total`, and JSONB `modifiers`; `line_total = unit_price * quantity` is constrained. Hosted menu item/category triggers update timestamps only. No menu-specific audit table or audit trigger was found by the focused catalog search; a proposed editor needs an explicit, reviewed change log if the restaurant requires one.

Hosted `menu_items`, `menu_categories`, `menu_ingredients`, and `drink_choices` have RLS enabled. `anon` and `authenticated` have **no direct INSERT/UPDATE/DELETE table privilege** on any of those four. `anon` and `authenticated` can SELECT active categories/items under RLS; staff item SELECT additionally covers active items for active Cashier/Manager profiles. No direct select grant was found for `drink_choices`. Hosted `get_manager_menu_items`, `set_manager_menu_item_availability`, `get_manager_fixed_meal_options`, `set_manager_fixed_meal_option`, `get_manager_drink_choices`, and `set_manager_drink_choice` are SECURITY DEFINER RPCs executable by `authenticated`, not `anon`; inspection of the four relevant definitions found explicit `auth.uid()`/active Manager profile checks. Thus broad `authenticated` EXECUTE alone does not mean Customer/Cashier authorization. `set_manager_menu_item_availability` locks the row, checks active product and nonnull input, and writes manual availability; effective availability still depends on stock. The meal writer validates positive cent prices, lower Without Rice price, active approved inventory mapping and serving quantity precision. The drink writer validates nonnegative cent adjustments and prevents disabling the final active choice of a required kind. These are existing narrow writers, not general CRUD authorization.

The hosted public function catalog contained **no ordinary product or category create/edit/archive/delete Manager RPC**. This is a catalog finding within `public`, not proof that arbitrary privileged administration outside the app is impossible. Existing controlled SQL configuration in [Phase 6B.5C](../supabase/migrations/20261004163102_controlled_foodhouse_inventory_menu_configuration.sql#L243) seeded menu items under migration control, illustrating technical data maintenance without a mounted self-service path. A future Manager writer would need new reviewed server code and exact field authority; browser direct table writes remain unavailable.

## Integration and preservation

Customer [reads active categories/items, `image_path`, effective availability, and Fixed Meal options](../src/modules/customer/index.tsx#L5499); Cashier [reads active categories/items, effective availability, drink choices, and Fixed Meal options](../src/modules/cashier/api/menuApi.ts#L78). Deactivating a category or item can remove it from these catalogs. Cashier throws if an active item refers to a category absent from its active category read. The Customer's [server pricing](../supabase/migrations/20261022120000_customer_preorder_quote.sql#L13) uses live menu price, availability, drink choices, and meal configuration, validates stock, and produces quoted lines. The [accepted quote writer](../supabase/migrations/20261022120000_customer_preorder_quote.sql#L284) locks requested menu rows, reprices, rejects a stale pricing hash, and writes order-line name/price/choice snapshots. A menu price change should affect a *future* quote; an already quoted cart can require renewed confirmation. Do not rewrite historical snapshots when product text or price changes. Read-only inspection confirmed hosted quote, accepted-quote writer, `get_cashier_sale`, choice, availability, and meal functions are present with expected public signatures; this assignment did not exercise those RPCs as authenticated application users.

Inventory availability depends on `menu_ingredients`, and stock consumption depends on approved recipe quantities. A new product without a reviewed recipe can appear available while stock consumption is undefined for that product; creation must resolve its sale/recipe policy before publication. Fixed Meal rice mappings require the actual rice inventory item and owner-approved quantity. Kitchen ticket and Reports compatibility require historical order name/choice/price fields to remain snapshot-based; this was assessed from schema/source, not replayed with a live order. Cashier [ProductCard images](../src/modules/cashier/pos/ProductCard.tsx#L7) use a static mapping and fallback, while Customer reads `image_path`; an image workflow therefore needs explicit cross-module presentation design. No hosted Storage bucket with a menu/product-named ID or corresponding upload policy was found by the focused catalog query. That does not prove no other image facility exists; no Manager image upload contract is established.

## Technical gaps and required acceptance

| Proposed action | Backend and validation needed after policy approval |
|---|---|
| Create product | Manager-scoped RPC; unique code/name policy, active category, positive two-decimal selling price, image path rule, initial inactive/unavailable state, stock/recipe publication gate, change log. |
| Edit name/description/category | Field allowlist, optimistic concurrency/readback, nonblank/length rules, active category check, audit before/after, preserve ID and historical order-line snapshots. |
| Change ordinary price | Separately gated RPC/approval rule; positive cent amount, row lock, audit reason and actor, future quote refresh, Fixed Meal relation check. |
| Create/rename/deactivate category | Narrow Manager RPC; unique normalized name; prevent deactivation with active products unless approved reassign plan, preserve historical reporting semantics. |
| Archive product | Prefer controlled `is_active=false` only if approved, with reporting/history regression. Do not hard delete by default. |
| Product image | Approved asset source and permissions, file type/size/path validation, cleanup policy, Customer and Cashier display contract. No existing Manager upload workflow to reuse. |
| Generic recipe editing | Separate inventory authority and tests; outside ordinary menu CRUD unless separately approved. |

Regression gate for any later implementation: Manager allowed/denied by actual profile, Customer/Cashier/anon denied to writers, validation and audit on invalid/valid edits, active category/item catalog propagation, pause versus stock-derived availability, stale quote/price refresh, mixed drink/meal carts, Cashier Quick Add, Kitchen labels, archived item receipt retrieval, Reports category/product grouping, ingredient consumption and stock alerts, image handling, keyboard/mobile states, and preservation of existing orders/payments/stock. Use isolated fixtures first; any hosted deployment or business-record change requires separate approval.

No test failed. Technical feasibility does not establish restaurant authority.
