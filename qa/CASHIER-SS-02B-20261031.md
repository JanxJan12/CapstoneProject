## Implemented Cashier workflow

The assigned Cashier still starts one authorized shift, processes sales, counts the physical drawer, reviews a provisional difference, and confirms server closure. The Shift Settlement header now says to count and settle at duty end. Active identity, terminal, Manila start time, and duration remain prominent. After 12 hours the warning states elapsed time and explains that the shift stays open until the server confirms closure; it does not invent a scheduled end time or expiry.

**Opening:** the ₱4,000 prefill is gone. “Opening Cash (₱)” starts blank, asks for the physical float already in the drawer, and permits explicit ₱0. The form validates an exact decimal string before converting it for the unchanged `start_cashier_shift` numeric argument. Empty/whitespace/nonnumeric, negative, more than two decimals, and >₱100,000 are rejected locally; no value is silently rounded. A synchronous submission ref plus loading state prevents concurrent duplicate clicks. The profile terminal remains editable under existing authorization; no assignment policy was added. A backend error remains visible on the page and permits correction. The former page “Retry” button merely cleared an error, so it was removed.

**Reconciliation:** the active page now puts opening cash, completed Cash receipts, and **Expected Cash — Estimated** in order. It explains that GCash is outside physical drawer cash and that the server finalizes verified receipts. Audit details remain expandable. The End dialog repeats the essential Cash components, then the actual physical count and text outcome. GCash, voids, transaction count, positive historical discounts, and legacy refund classifications remain in expandable details. The count label says “Actual Cash Counted (₱)” and explicitly includes the opening float. Balanced, Shortage, and Overage appear with absolute difference and text as well as color; the underlying signed variance and `cashVariance` logic are unchanged. Missing/invalid count still blocks review. The existing server-required reason for nonzero variance, optional notes, and optional zero-preview reason remain.

**Closure readiness and confirmation:** a local Pending count is identified as the **Cashier queue**, not an exact representation of the server predicate. Guidance explains that the server independently checks pending online GCash across the restaurant, including another shift. The current local block and Pending Payments link remain; no pending payment is auto-decided. A ready message says that final eligibility and totals are rechecked on confirmation. The confirmation names the shift reference, provisional expected, counted cash, estimated balanced/short/over result, optional reason/notes, and that the action saves a closed settlement. Existing shift-ID/estimate invalidation and duplicate-confirm ref remain. On RPC success, the toast uses the **returned saved expected/count/variance**, local active state is replaced with the returned closed shift, and Saved closed shifts refreshes. No new shift starts automatically.

**Uncertain close result:** known server variance-reason and pending-payment rejections return the Cashier to review with specific guidance. A known authorization rejection asks for session/shift refresh. For any other error, the dialog does **not** retry the close RPC. It reads `get_open_cashier_shift`; if that exact shift is no longer open, it reads the first page of `get_closed_cashier_shifts`. It distinguishes still open, saved closed, and unconfirmed outcomes without declaring an unknown result a failure or success. Another close attempt remains disabled until a deliberate page refresh, which reloads authoritative state and history. A saved closure beyond the returned history page can only be called unconfirmed; the message does not claim absence. This is a conservative recovery path, not a new idempotency contract. The Dashboard uses the same End dialog, but its route and action behavior were not altered.

**History:** `ClosedShiftHistory.tsx` was inspected and left unchanged. Cashier history already shows persisted opening/expected/count/variance, Manila open/close times, terminal, reason/notes, date filters, keyset paging, and secondary audit IDs. As-closed Cash/GCash component totals are not separately stored, so no “recorded historical Cash receipts” figure was invented. The Manager view that reuses this component was untouched.

## Remaining risk and next milestone

The local pending queue is advisory and can lag the server's exact restaurant-wide pending online GCash predicate. A new receipt/void during review can alter the server's final amount; the server remains authoritative and may demand a reason. A failed close with no returned acknowledgement requires a page refresh before another attempt. Physical payout-drawer attribution, handover of a still-open terminal, scheduled-duty recording, payment-blocker scope, and any tolerance/Manager approval policy remain **deferred** pending the owner decisions in SS-02A; no new rule is implied here.

**Recommendation:** ready for local source/fixture acceptance; proceed next to an authenticated Cashier desktop/narrow-screen review and isolated two-Cashier/payment/close concurrency acceptance. Do not treat this as production or financial-policy acceptance. Preserve hosted financial records during those browser checks.
