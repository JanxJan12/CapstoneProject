## Duplication classification and edge cases

**Necessary parallel history:** Formal lines/revisions/events and legacy request/status events record different workflow generations. Formal snapshots duplicate current line values by design to retain earlier revisions; legacy events duplicate current status by design to retain transitions. The two nullable Receiving request links distinguish provenance. The common posting RPC avoids duplicate stock-writing logic.

**Redundant or transitional logic:** The uncalled frontend `createReplenishmentRequest` wrapper and authenticated-revoked RPC are dormant normal-request creation paths. Manager and Production have separate legacy queue presentations over the same read RPC. Current and reason-signature issue/revise overloads coexist; the old overloads are compatibility adapters, outside this legacy Production table retirement. Proposal's legacy open-quantity addition is necessary only while legacy requests can exist, but removing it now would make a newly restored or privileged legacy request invisible to suggestions.

**Risks:** (1) Formal requests do not appear in the mounted Production queue; retiring the legacy queue alone would leave Production with no formal task/status view. (2) An open legacy request subtracts its full requested quantity from the proposal until `received`; unlike formal residual, legacy partial accepted quantity is not subtracted before closure, because one linked receipt closes it. (3) Legacy status `received` closes on a posted linked report even if accepted is less than requested; formal request can remain partially received or close short. Treating these statuses as interchangeable would misstate outstanding quantity. (4) A posted report moves accepted stock exactly once; request issue and Production advancement do not. (5) Existing reports and FKs require provenance-preserving reads even when today's hosted legacy row count is zero. (6) Old reason-signature overloads remain callable on hosted; removing them needs its own caller and authorization check.

Existing SQL tests cover legacy idempotent creation, strict status order, ready-only Receiving, one-line linkage, accepted/rejected results, duplicate post, and supplier isolation (`supabase/tests/verify_phase_7b_replenishment_requests.sql`); formal tests cover issue retry, stale proposal/revision, accepted overage rollback, partial fulfillment, and close short (`verify_manager_inventory_request_documents.sql`); policy tests cover new-write restrictions (`verify_production_delivery_policy.sql`). These SQL files were **inspected, not executed against hosted**. The earlier Track A authenticated disposable-local report proves one bounded formal post, not a hosted or legacy transaction.
