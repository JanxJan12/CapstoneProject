# Database performance optimization plan — read-only assessment

**Date:** 2026-10-14 (Asia/Manila). **Decision:** no index or query change is justified by measured performance evidence yet. This document evaluates the 122 hosted public indexes captured on 2026-10-13, current SQL/RPC and service-layer access paths, and the existing architecture reports. No hosted or isolated SQL was executed for this pass. Docker's local engine was unavailable, so there is **no new EXPLAIN plan**; none of the opportunities below is a measured speedup. See the [full index catalog](DATABASE-REDUNDANCY-EVIDENCE-20261013.json) and [normalization report](DATABASE-NORMALIZATION-ASSESSMENT.md).

## FK support screen

The catalog shows 73 FKs. A static comparison of FK columns with the leading column of each table's B-tree indexes found **22 single-column FK references without a dedicated leading-column B-tree index**: `cashier_shifts.closed_by`, `cashier_shifts.manager_approved_by`, `cashier_transactions.cashier_id`, `cashier_transactions.shift_id`, `inventory_opening_balances.verified_by`, `inventory_request_documents.closed_by`, `inventory_request_documents.issued_by`, `inventory_request_events.actor_id`, `inventory_request_revisions.issued_by`, `menu_item_modifier_groups.group_id`, `order_items.menu_item_id`, `order_status_history.changed_by`, `paid_order_cancellations.processed_by`, `payments.rejected_by`, `payments.verified_by`, `production_replenishment_requests.inventory_item_id`, `production_replenishment_requests.requested_by`, `production_replenishment_status_events.changed_by`, `production_replenishment_status_events.receiving_report_id`, `purchase_orders.created_by`, `receiving_reports.posted_by`, and `receiving_reports.received_by`.

This is a **screening list, not 22 index recommendations**. Several are sparse actor/audit references or tiny tables. Existing non-B-tree/partial indexes, parent deletion frequency, FK action, and planner statistics must be checked individually. The highest-value candidates to *measure first* are `order_items.menu_item_id` (RESTRICT parent operation and menu-centric joins), `menu_item_modifier_groups.group_id` (reverse bridge access), and `cashier_transactions.shift_id` (shift reconciliation). No schema change is proposed from the static screen alone.

## Query-plan and workload protocol

1. Record the observation window and `pg_stat_database.stats_reset`; rank sanitized `pg_stat_statements` fingerprints by total time, p95 proxy/variance, calls, rows, and shared block activity. Exclude literal PII, recipes and credentials from artifacts. A zero `idx_scan` without a reset window is not removal proof.
2. On hosted, use **plain read-only `EXPLAIN (FORMAT JSON)` for SELECT** only, with representative parameters and role context. No `EXPLAIN ANALYZE` on hosted in this task. `EXPLAIN ANALYZE` executes its statement; run it only on a safe isolated representative restored copy, with no business data mutation and no demo-stack disruption.
3. For each proposed index, compare old/new plans, actual rows vs estimates, sort nodes, buffers, latency distribution, insert/update cost, storage, locks, and regression across Customer/Cashier/KDS/Rider/Manager roles. Small tables may correctly use sequential scans.
4. Evaluate composite leading keys and predicates against exact `WHERE`, `ORDER BY`, RLS conditions and `LIMIT`. Avoid indexing every FK or combining unrelated predicates by default. PostgreSQL and Supabase guidance recommend workload-driven testing: [PostgreSQL index usage](https://www.postgresql.org/docs/current/indexes-examine.html), [Supabase query optimization](https://supabase.com/docs/guides/database/query-optimization), [Supabase `pg_stat_statements`](https://supabase.com/docs/guides/database/extensions/pg_stat_statements).

## Reversible implementation proposal (future only)

For one proven candidate at a time, create a new additive migration **after** lineage/recovery gates. If a new non-unique index is justified, name it exactly, inspect existing semantics, build/test it on an isolated stack, retain existing indexes during validation, then review a separate future retirement only if equivalence is proven. Rollback removes only the new named index after verifying no constraint uses it. A query rewrite uses a versioned RPC body and a reviewed restoration body; preserve output shape, authorization, ordering, pagination, and snapshot semantics. Test concurrent receipt posting, duplicate requests, FIFO/FEFO allocation and cancellation reversal, all core flows, and before/after plan metrics. Hosted remains read-only; the current clean-replay and off-device recovery gates are unresolved.
