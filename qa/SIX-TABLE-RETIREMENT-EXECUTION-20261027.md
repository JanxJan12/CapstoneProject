## Dependency findings

The four foreign keys *owned by surviving tables* are `inventory_transactions_purchase_order_item_id_fkey`, `receiving_report_items_purchase_order_item_id_fkey`, `receiving_reports_purchase_order_id_fkey`, and `receiving_reports_replenishment_request_id_fkey`. A drop without explicit dependent changes fails; `CASCADE` could remove these and other dependencies without review. All six target tables have RLS enabled and no row policies. Supplier/PO tables have SELECT grants to `anon` and `authenticated` but no matching policy; the legacy request tables have neither direct user grants nor policies. These ACL details matter when retaining or replacing RPC paths.

Live metadata showed `postgres` ownership for all 21; the RPCs include `SECURITY DEFINER` functions with existing grants/search paths. The preflight records definitions' MD5 digests to detect drift, but full replacement definitions and security review were **not** completed. PostgreSQL may defer body name resolution for PL/pgSQL, so a successful `DROP TABLE` would not prove these functions still execute.

Surviving triggers call legacy and PO-aware bodies, including `inventory_open_replenishment_unit_guard`, `receiving_link_guard`, `receiving_linked_line_guard`, `receiving_closes_replenishment`, quantity-scale and shelf-life guards, and formal request reconciliation triggers. The formal Manager flow must retain `inventory_request_documents/lines/revisions/events`, `receiving_reports/items`, accepted-only `inventory_batches`/`inventory_transactions`, and exactly-once posting. The live `get_inventory_request_proposal` still references legacy outstanding requests. The current `post_receiving_report` body still includes PO operations. Removing columns, triggers, or function branches requires a coordinated, reviewed migration and a regression proof for rejected quantities, duplicate posting, partial delivery, and role denial.

The current React source still exposes the older single-item Manager history and `get_replenishment_requests`/`start_replenishment_receiving` callers. `StockReceivingPage` still offers `direct_supplier` PO receiving and maps PO data from `get_manager_receiving_workspace`; `receivingApi.ts` expects that shape. `PurchaseOrdersPage` is a prototype, but the actual Receiving PO branch is not merely a mock. Source changes should be staged with the corresponding SQL and released together, after rehearsal. Editing these callers now while hosted still has the old contract would create avoidable divergence.
