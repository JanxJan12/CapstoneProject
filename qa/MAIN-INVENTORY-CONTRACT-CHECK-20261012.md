## Additive migration and exact caller contracts

`supabase/migrations/20261011120154_manager_inventory_request_documents.sql` sorts after the other 45 main migrations. It depends on existing `inventory_items` (including unit, precision, reorder, and batch policy), `inventory_usable_quantity(uuid)`, `inventory_batches`, `profiles`/`user_role`, Phase 7B `production_replenishment_requests` and `receiving_reports.replenishment_request_id`, and the source-neutral `receiving_reports`, `receiving_report_items`, and `post_receiving_report`. It adds four RLS-enabled, direct-client-DML-revoked request tables, two request-link columns and inspector fields on Receiving, line/header guards, a posting reconciliation trigger, and these Manager-checked RPCs:

- `get_inventory_request_proposal(p_needed_at)` → proposal JSON; `issue_inventory_request(p_request_id,p_priority,p_needed_at,p_reason,p_lines,p_expected)` and `revise_inventory_request(p_request_id,p_expected_revision,p_priority,p_needed_at,p_reason,p_lines,p_expected)` → numbered request/revision JSON. `inventoryRequestApi.ts` sends those exact names and keys. The proposal includes usable stock at need and open new/legacy request quantities; the server compares the expected proposal on issue/revision.
- `get_inventory_request_register()` → documents, issued snapshots, lines, posted accepted/rejected totals, receipts, and events; `record_inventory_request_event(p_request_id,p_revision,p_event_type,p_details)` → Manager-attested dispatch or acknowledgment. The frontend labels external Messenger action as manual.
- `start_inventory_request_receiving(p_request_id,p_revision,p_report_id,p_inspected_by_name,p_inspection_note)` → linked draft ID/RR number; `close_inventory_request_short(p_request_id,p_revision,p_reason)` → audited shortfall closure. The frontend passes the exact arguments. A draft/request event does not move stock. The new after-post trigger sums posted accepted quantities, enforces the requested cap, updates request status, and records a receipt event in the posting transaction.

New RPCs revoke `PUBLIC`/`anon` execution and grant `authenticated`/`service_role`; their `inventory_request_manager_required()` gate checks `auth.uid()`, active profile, and Manager role. Existing Receiving/posting and movement RPCs have separate active-Manager gates. These are **source definitions**, not effective-permission proof on a running database.
