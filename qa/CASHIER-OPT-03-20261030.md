# CASHIER-OPT-03 — lifecycle and action matrix (30 Oct 2026)

## Pre-implementation findings

Source reviewed: active Cashier order hooks, Dashboard queue, Order List, Kitchen terminal client, and local SQL definitions for `update_cashier_order_operational_details`, `cancel_order`, and `release_ready_order`. A read-only hosted catalog query confirmed these four RPC signatures and the hosted financial/status guard patterns. The backend RPCs, not these UI rules, make final authorization and transition decisions.

Order creation differs by channel: Customer checkout produces an online payment for Cashier verification; Walk-in POS records a cash sale. Verified/paid orders enter Confirmed. Kitchen's terminal RPC advances Confirmed → Preparing → Ready. Cashier's release RPC locks Ready and sends delivery to Waiting for Rider (and offers a rider), or completes dine-in/take-out. Rider transitions own the later delivery stages. Cashier ordinary cancellation and operational editing do not alter items, prices, payments, or reconciliation.

| Order state and payment | Cashier edit operational details | Ordinary Cashier cancel | Cashier release | Verified repository rule / improvement |
| --- | --- | --- | --- | --- |
| Awaiting Payment; Unpaid or Rejected, no sale | Allowed | Allowed with reason and confirmation | Not applicable | Edit RPC permits waiting payment verification; cancel RPC rejects pending/verified payments and any cashier transaction. |
| Awaiting Payment; Pending | Allowed | Blocked | Not applicable | Payment must be resolved or rejected first. |
| Awaiting Payment; Verified or sale exists (inconsistent/stale view) | Allowed only while actual backend status permits | Blocked | Not applicable | Financial guard is authoritative. Refresh before action. |
| Confirmed; verified/paid | Allowed | Blocked; Manager refund settlement is separate | Not applicable | Edit RPC permits operational fields; ordinary cancel rejects verified payment/transaction. Kitchen owns next transition. |
| Preparing; verified/paid | Allowed | Blocked; Manager refund settlement is separate | Not applicable | Kitchen owns preparation; edit RPC still permits instructions, although whether late instructions reach Kitchen requires a policy/integration decision. |
| Ready; verified/paid | Allowed | Blocked; Manager refund settlement is separate | Allowed with confirmation | Release RPC requires Ready and active cashier/manager, locks order, audits transition. Proposed confirmation addresses accidental completion. |
| Ready; Unpaid/Pending or unknown (inconsistent/stale view) | Allowed while backend status permits | Blocked if payment pending or sale exists | Requires clarification | Existing release RPC checks Ready but does not verify payment. Do not invent a new payment policy in this stage. |
| Waiting for Rider; verified/paid delivery | Allowed | Blocked; Manager refund settlement is separate | Not applicable | Cashier may offer next rider when assignment rules allow. |
| Rider Accepted / Picked Up / Out for Delivery | Blocked | Blocked | Not applicable | Operational edit RPC excludes these states; Rider owns delivery. Manager refund settlement has separate eligibility through Rider Accepted, not ordinary Cashier cancellation. |
| Delivered / Completed / Cancelled | Blocked | Blocked | Not applicable | Terminal states. |

For all rows, an unauthenticated or inactive cashier is blocked by RPC authorization. `release_ready_order` also allows an active manager; the operational edit RPC requires an active cashier. Action visibility is a convenience, not an authorization boundary. The UI must keep payment and transaction presence in mind because status alone is insufficient for cancellation. Walk-in cash sales are paid immediately, so their ordinary cancellation is blocked even if a stale status appears eligible.

## Pre-implementation defects and risks

- **High, confirmed in source:** Order List row/card menu, bulk selection, and details drawer expose ordinary Cancel through Preparing, Ready, and Waiting for Rider based only on status. The backend rejects paid orders. The user screenshot shows Cancel for paid ORD-000075; no cancellation was attempted.
- **Medium, confirmed in source and user report:** Ready order release is one click from detail view. The backend intentionally completes non-delivery orders on release, so ORD-000042's reported transition is consistent with the RPC, but the UI lacks a handoff confirmation.
- **Medium, source risk:** release and cancel handlers can be invoked again before React updates `loading`; stale orders rely on RPC rejection. The UI should prevent repeat submission and explain refresh/reconciliation.
- **Low, source risk:** timeline actor `Staff / Customer` does not identify a particular person or role. UUID presence alone cannot establish a role; do not fabricate an actor.

## Hosted read-only corroboration

ORD-000042 is a walk-in dine-in sale with verified payment and a cashier transaction. Its recorded timeline is Confirmed → Preparing → Ready on 10 September, then Completed on 29 October with note “Ready order released by cashier” and a cashier account recorded. The observed one-click completion therefore matches the deployed release RPC's intended transition; the missing confirmation was the UI defect. ORD-000075 remains Confirmed/Verified with a cashier transaction. Ordinary Cancel shown for it was ineligible under the deployed `cancel_order` financial guards. These queries selected status/audit fields only; no hosted records were changed.

## Implemented Cashier-only changes

Stage 3 source files changed: `src/modules/cashier/orders/orderOperations.ts`, `OrderTableRow.tsx`, `useOrderList.ts`, `OrderDetailsDrawer.tsx`, `useOrderDetailsDrawer.ts`, `EditOrderDialog.tsx`; `src/modules/cashier/hooks/useCashierActions.ts`; `src/modules/cashier/constants/index.ts`; `src/modules/cashier/services/supabaseOrderService.ts`; and `src/modules/cashier/api/cashierSaleHydrationApi.ts`. Stage 3 evidence/backlog files changed: this report, `qa/cashier-opt-03-action-regression.mjs`, and `qa/CASHIER-MANUAL-FINDINGS-20261030.md`. Existing uncommitted Stage 1/2 and unrelated edits were preserved.

- Shared Cashier order-action predicates now use database identity plus status and payment/sale evidence. Row/card menus and bulk cancellation use the same predicate; the detail drawer does too. Paid ORD-000075-like orders no longer show ordinary Cancel. The server remains authoritative if the local view is stale.
- Ready-order handoff now opens a contextual confirmation. Dine-in/take-out says it will complete the order; delivery says it will wait for and offer to a rider. A synchronous in-flight guard prevents repeat requests before React updates loading, and the release response is checked for matching order, prior status, and resulting status.
- Order List edit/cancel re-check the latest hydrated order; cancellation errors retain the RPC reason and trigger a refresh. The detail drawer refreshes after ambiguous failures. Operational edit warns that late instruction saves do not prove Kitchen saw them.
- Timeline no longer calls every non-null `changed_by` “Staff / Customer.” It displays the recorded account ID. Exact known Kitchen transition notes show “Kitchen terminal”; other null actors show “System / terminal.” No historical event was changed.
