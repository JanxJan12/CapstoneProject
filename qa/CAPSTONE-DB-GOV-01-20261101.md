## Proposed supported-client policy — **awaiting owner adoption**

1. **Eligibility and registry.** The supported set is the owner's approved canonical web release, approved Rider APK release(s), active first-party Edge/Cron integrations, and explicitly registered external tools. Record client ID, environment/project, release URL or package/version/signing identity, owner/maintainer/contact, backend APIs used, deployment and last verification date, update path, and support/sunset state. Keep secrets out of the registry.
2. **Authority.** The restaurant/project owner names an accountable API owner and deployment approver. Engineering supplies evidence and executes only separately authorized changes; an external maintainer confirms its migration. An owner decision is required for a support boundary or residual unknown-caller risk. Hosted DDL still requires its own recovery/rollback and exact-change approval.
3. **Older and development builds.** Local demos, copied debug APKs and unregistered experimental tools receive no indefinite compatibility promise **after the owner adopts this policy**. Identify known active installations first. Record supported version(s) and a practical update/sunset window; do not use the policy retroactively to dismiss a known active client.
4. **External integrations.** Register each intentionally supported reporting/admin/automation client and its contract owner. If none exist, record an owner attestation with date and scope; do not convert repo search silence into that attestation.
5. **Interface changes.** Before changing an exposed RPC, inventory exact signature, grants/roles, active consumers, current replacement behavior, historical data, security and financial effects. Prefer a temporary compatible overlap and documented replacement guidance. Stop new use of deprecated signatures through managed client updates; do not add permanent wrappers merely to hide unresolved ownership.
6. **Retirement and notice.** Notify affected supported maintainers with old/new signature and argument mapping, environment, migration date, acceptance steps and rollback contact. The owner sets the sunset window based on actual web/APK distribution and operational use; no arbitrary universal number of days is inferred here. Observe available logs during that window without claiming absence proves no unknown client. Delete only with a reviewed exact-signature migration and restoration plan after the gates below pass.

### Repeatable ten-gate RPC procedure

| Gate | Required evidence / stop condition |
| --- | --- |
| 1. Business responsibility | Replacement covers required behavior; preserve distinct old behavior until explicitly retired. |
| 2. Owned clients | Supported web/APK/worker/scripts inventoried and migrated or retired, with deployed release identity verified. |
| 3. Known external clients | Registry/contact confirms each dependency and coordinated transition. Unknown registry is a stop or explicit owner risk decision. |
| 4. Unknown calls | Inspect existing sanitized workload/API logs for shape, window and attribution; record what cannot be known. No-use alone is insufficient. |
| 5. History | Snapshot/event/read projection and linked operational record preservation proven; no historical rewrite. |
| 6. Security | Exact EXECUTE, role helper, RLS, service-role and negative authorization unchanged or deliberately reviewed. Emergency exposure would require a separate decision. |
| 7. Notice | Replacement guidance, responsible recipients, version sunset and rollback contact documented where supported clients exist. |
| 8. Owner authorization | Specific signatures and residual compatibility risk approved; this cannot waive history, security or financial integrity. |
| 9. Local removal | Guarded new migration, no `CASCADE`, disposable current-schema role/business/Receiving/stock/financial tests and exact function/grant restoration. |
| 10. Hosted review | Clean-history and recovery prerequisites, exact migration/ledger/rollback, separate hosted approval and postflight; no broad `db push`. |

Outcomes per signature: **SAFE TO RETIRE** only after all relevant gates; **RETIRE AFTER TRANSITION** for identified supported callers; **OWNER RISK ACCEPTANCE REQUIRED** for an irreducible, described unknown-caller residue after reasonable inventory; **RETAIN** for required behavior or unacceptable risk. A risk acceptance addresses compatibility only. It does not authorize unsafe history loss, weakened authorization, financial corruption, or hosted deployment.
