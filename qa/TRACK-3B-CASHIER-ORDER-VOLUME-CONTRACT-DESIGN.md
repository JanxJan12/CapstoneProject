# RRJ’S FOOD-HOUSE — Track 3B Cashier order-volume contract design

**Date:** 2026-11-03 (Asia/Manila)  
**Mode:** read-only investigation and design. No production code, migration, hosted data, payment decision, or shift state was changed.  
**Finding labels:** **CONFIRMED** = directly shown by source/catalog; **RISK** = mechanism under a defined growth condition; **INFERENCE** = proposed behavior or untested extrapolation; **BLOCKED** = evidence unavailable.

## 1. Executive summary

**RISK — T3-02 is substantiated as a P2 scalability and completeness risk, not a reproduced hosted omission.** The active Cashier startup reads all `orders` without a range, then separately reads all `order_items` and `order_status_history` for those IDs. The payment RPC returns all pending, verified and rejected online payments without input pagination. The UI treats these results as complete. Hosted counts during this inspection were 66 orders, 72 items, 269 history rows, 17 online payment RPC-eligible rows, 34 active orders, and one pending online GCash payment. No hosted row-limit failure was observed. The hosted Data API maximum-row setting and authenticated browser behavior were **BLOCKED** from direct verification.

**Recommendation:** stage **C + B**: add narrowly scoped, server-authorized operational reads for actionable payments/orders and authoritative counts; then move historical Orders and Receipts to bounded, deterministic server-backed discovery and on-demand detail hydration. Retain the existing financial mutation RPCs and restaurant-wide pending-GCash shift-close guard. A first-page count must never represent the full queue.

## 5. Confirmed limitations and evidence

1. **CONFIRMED:** No range/loop on parent, child, or online-payment reads, and the Orders UI pages only after local filtering. This is source-level behavior, not proof that today's hosted response is truncated.
2. **RISK:** Supabase documents a default maximum of 1,000 returned rows, configurable per project ([fetch reference](https://supabase.com/docs/reference/javascript/v1/select)); hosted project setting was **BLOCKED**. If the cap is 1,000, the 1,001st order can vanish from startup state; the 1,001st item or history row can vanish earlier even with fewer than 1,000 orders. A query returning exactly the cap gives no completeness signal. At current data, the largest observed order has three items and twelve history rows; these are observations, not upper bounds.
3. **RISK:** The online-payment RPC sorts all statuses together. If response truncation applies to its set-returning result, a pending row can be hidden behind newer verified/rejected rows even when pending count is small. The page's fresh read gates failed calls, but a successful truncated call is not detectable. Current eligible hosted rows: 17.
4. **RISK:** `.in(orderIds)` grows with parent count; URL/request and SQL planning costs grow, and child result boundaries are independent of parent boundaries. Batched payment/assignment reads are already bounded, but only cover loaded parents. Child ordering has no ID tie-breaker.
5. **RISK:** Every order Realtime insert/update or status-history insert invokes whole-state hydration. Client mapping, grouping, queue sorting, `find` joins, and DOM work scale with loaded volume. At 100,000 orders this is not a viable refresh model even with a raised API cap.
6. **CONFIRMED:** Transaction history and saved closed shifts have real server pagination. **RISK:** transaction offset moves under concurrent inserts and cannot address beyond offset 10,000; CSV checks total only. The 500-row shift-filter cap is independent of saved closed-shift pagination.
7. **INFERENCE:** No missing or duplicate page was reproduced under concurrent traffic; no latency or memory benchmark was run. Do not call these current production defects.

| Active orders and Dashboard | Server-defined active/actionable predicates and exact counts independent of displayed pages. Provide older backlog navigation and targeted lookup by order number/UUID. Show an explicit unavailable/stale state if counts or a page fail. |

## 8. Financial and authorization invariants

- Verify/reject eligibility is rechecked in the existing server RPCs against current payment/order state and authenticated active Cashier. Keep stale-version checks and proof access private. Pending and rejected submissions require distinct states; never infer Verified from order status or missing payment data.
- `create_walk_in_sale` owns request-ID idempotency, one order/payment/transaction linkage and verified amount. Pagination must not create a second client-side sale path. The current POS uncertain-response lookup scans the current-shift JSON array and needs a direct request-ID recovery read at scale.
- Completed versus voided transactions and Manager `paid_order_cancellations`/refund settlement stay distinct. Do not sum a paginated receipt page, treat `Refunded` as a transaction status, or merge cash and GCash. Preserve unique receipt number and owner-scoped reprint detail.
- `calculateShiftTotals` is a client display calculation on `state.transactions`; it must never become closure authority. The hosted closure RPC locks the owned open shift, enforces restaurant-wide pending online GCash, sums verified completed transaction payments, and writes the snapshot. The local pending count only gives early guidance; a truncated zero must not be shown as authoritative permission to close.
- The payment submission associated with `ORD-000080` remains pending and untouched. No hosted fixture or decision was made to prove this design.

## 9. Architectural options

| Criterion | A. Frontend query improvements | B. Coordinated server pagination | C. Dedicated operational reads |
|---|---|---|---|
| Correctness/completeness | Bounded direct `orders` keyset and child batches can improve history. | Performance | Lower initial payload if history is lazy; multiple REST calls and fanout remain. | Indexed keyset page cost is bounded; exact counts/search may be costly. | Narrow projections and indexes bound work; avoid all-sale JSON hydration for routine refresh. |

| RLS/security | Direct table RLS remains in force; payment cannot be direct-read without policy change. | Invoker direct reads or carefully scoped definer RPCs; owner/role assertions required. | Definer functions for payment joins need explicit active-role checks, revoked PUBLIC/anon EXECUTE, fixed `search_path`, minimal projection. |

| Rollback/testing | Frontend-only rollback easy but incomplete solution. | Additive backend contracts then client flag rollback; synthetic concurrency and ACL tests needed. | Additive backend contracts then client flag rollback; precise queue/count/pending tests needed. |

**Recommendation — INFERENCE:** C for operational completeness, B for historical discovery, with a small A-style on-demand detail cleanup. Keep old reads during staged cutover until new consumers pass acceptance. This is driven by the hosted unpaged payment RPC and client-derived counts, not file count.

## 10. Recommended target architecture

Use three read models: (1) **payment work** filtered by current status with authoritative pending count and direct order detail; (2) **order work** filtered by server-owned active/actionable definitions, exact counts, keyset browsing and order-number lookup; (3) **history** filtered, keyset paged, with on-demand children/receipts. An operational page is a window, not a completeness proof. Display `asOf`, error/stale state, total matching count (or explicit count-unavailable), and a continuation control. Refresh counts and first page on events/focus; do not refetch all history. Revalidate the selected record before a sensitive action; existing mutation RPC performs the final check.

Keep `get_cashier_transaction_history` for compatibility while introducing a cursor successor only when deep-history acceptance demands it. Keep `get_closed_cashier_shifts` intact. Replace current-shift JSON dependency for dashboard totals with an aggregate read and POS ambiguous-result scan with a narrow authorized request-ID lookup; retain `get_cashier_sale` for full receipt detail.

Illustrative additive signatures: `get_cashier_payment_work(p_status payment_status, p_cursor_created_at timestamptz DEFAULT NULL, p_cursor_id uuid DEFAULT NULL, p_limit integer DEFAULT 25) RETURNS jsonb`; `get_cashier_order_work(p_scope text, p_filters jsonb, p_cursor_created_at timestamptz DEFAULT NULL, p_cursor_id uuid DEFAULT NULL, p_limit integer DEFAULT 50) RETURNS jsonb`; `get_cashier_order_detail(p_order_id uuid) RETURNS jsonb`; `get_cashier_work_counts() RETURNS jsonb`; `get_cashier_sale_by_request_id(p_request_id uuid) RETURNS jsonb`; later `get_cashier_transaction_history_v2(p_filters jsonb,p_cursor_created_at timestamptz,p_cursor_id uuid,p_limit integer) RETURNS jsonb`. Exact request-ID type must be checked against hosted column before migration.

All page RPCs validate limit 1–50 (default 25 for payment, 50 for order), paired cursor fields, filter enum/date/length, and active Cashier role. They derive identity from `auth.uid()`; no client cashier ID is authoritative. Pending payments filter status **inside SQL before `LIMIT`**. Return `limit+1` internally, at most `limit` rows, `hasMore`, `nextCursor=null` at end, and exact aggregate counts from the same statement snapshot where feasible. If count is too costly at scale, provide a separately refreshed exact operational count with its own `asOf`; never label a page length as total. Use SQLSTATE `22023` invalid input, `42501` unauthorized, and a typed no-result for an authorized absent record. Do not expose payment proof content or other Cashiers' sale detail.

Server search must specify exact order-number/receipt/UUID matching and bounded customer-text search (minimum length, escaped literal pattern, indexed strategy); retain existing filters only when semantics are matched. UI-only custom sort choices need either indexed server alternatives or an explicitly scoped page sort label, never a falsely global sort. Detail reads include all item/history rows ordered `(created_at ASC,id ASC)`; if response size exceeds a defined safe bound, return explicit overflow and provide child pagination rather than silent truncation.

## 12. Pagination, ordering, consistency, and retry semantics

Use immutable `(created_at DESC,id DESC)` keysets; cursor carries the filter hash and optional first-page anchor to keep later-created rows out of an ongoing browse. Reject a cursor reused with different filters. For mutable status-filtered work queues, a row can leave or enter between pages; keyset prevents duplicates caused by inserts ahead of the cursor, but cannot promise a historical snapshot. The UI should refresh counts/first page after status/payment changes and provide lookup by ID for a row that moved. Never auto-append an event response to an old page without reconciling its filter membership. Deduplicate by UUID when merging pages and discard out-of-order responses using request generation plus filter/cursor identity.

For immutable-history browsing, anchor plus keyset gives stable traversal if rows are not backdated or deleted. For changing status/payment filters, exact snapshot consistency across multiple HTTP calls would require a server snapshot/session contract; **INFERENCE:** eventual consistency with explicit refresh is acceptable for display, while mutation eligibility and shift closure remain transactionally checked in their RPCs. A page error preserves the last known page as visibly stale and disables sensitive decisions until a fresh selected-record read succeeds. Retry the same cursor idempotently; on cursor invalidation, restart at page one. Network interruption must not convert an unknown payment/receipt outcome into an empty or verified state. A cancelled/deleted row vanishes on refresh and direct lookup yields unavailable, without promoting another row's action.

## 17. Migration, deployment, and rollback strategy

Deploy additive backend read contracts and measured indexes first. Verify signatures, definitions, grants, RLS interaction, exact ledger entry, direct authenticated results, and old-RPC compatibility. Then deploy one Cashier consumer stage at a time with an immediate frontend rollback path; retire old read RPCs only after complete acceptance and a separate review. Never combine queue, history, POS recovery, and financial read changes in one deployment. No repository-wide database push. Preserve the exact current close-shift and payment mutation functions. For any new SECURITY DEFINER function, fix `search_path`, qualify relations, validate `auth.uid()` and active role, revoke PUBLIC/anon, grant only intended roles, and prove owner scope. Rollback new indexes/functions only after consumers are reverted. Hosted schema/data backup and rollback evidence must be checked under the user's deployment policy at the later implementation stage.
