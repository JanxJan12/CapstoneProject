# H-08B historical Cashier shift audit assessment

**Status (2026-10-15 Manila):** Source trace, read-only checks on the retained H-07 stack, and a fresh disposable synthetic H-08B stack with authenticated local API/browser checks complete. Historical UI retrieval, any new RPC, and access-policy changes are **PROPOSED ONLY**. Hosted Supabase was not contacted. The original 51 source migrations were left intact.

## Exact current path

1. `/cashier` is protected by `RequireAuth role="cashier"` (`src/app/routes.tsx`) and mounts `ShiftSettlementPage` through `src/modules/cashier/index.tsx`.
2. `CashierProvider` initializes from `loadCashierState()` in browser `localStorage`, then refreshes orders, payments, sales, menu, and `fetchOpenCashierShift()`. That API calls `get_open_cashier_shift()`, which returns **open only** for an active cashier. `get_current_shift_cashier_sales()` likewise reads the current open shift.
3. `mergeDatabaseRefresh()` explicitly keeps `current.shifts.filter(status !== "Open")` and replaces only the open shift. `useCashierActions.endShift()` calls `close_cashier_shift()`, then puts its returned closure values in the browser store. The persistence helper saves that store back to `localStorage`.
4. `ShiftSettlementPage` passes `state.shifts` to `ShiftAuditTable`; `useShiftSettlement()` selects `activeShift ?? state.shifts[0]` and calculates receipt totals from local transactions for overview/report. H-08 changed closed expected-cash display to `shift.expectedCash`; the audit table already uses `shift.expectedCash`, `actualCash`, and `variance`.
5. `close_cashier_shift()` sums currently completed `cashier_transactions` joined to verified `payments` by `shift_id`, then writes `cashier_shifts.expected_cash`, `actual_cash`, `variance`, `ended_at`, `closed_by`, and status. These fields are settlement snapshots. Later Manager paid cancellation can void the current payment/receipt without rewriting the closed shift (H-07 rollback scenario).

**Cause:** A fresh browser has no local closed-shift cache. The only mounted hydration RPC is open-only, so a persisted closed shift never enters `state.shifts` after fresh login. A same-browser reload can preserve it via `localStorage`; that is not independent database recovery. The seeded initial state may also supply prototype records, so UI appearance alone is not proof of a persisted closed row.

## Existing read authority: important correction to H-08F

No current historical-shift RPC exists: local `pg_proc` contains `get_open_cashier_shift`, `get_current_shift_cashier_sales`, `get_current_shift_walk_in_sales`, `start_cashier_shift`, and `close_cashier_shift`. **An existing direct table read does exist.** The source migration grants authenticated `SELECT` on `public.cashier_shifts`, enables RLS, and applies `cashier_shifts_select_staff`: own `cashier_id = auth.uid()` **or** an active Manager profile. The retained isolated H-07 database confirms `has_table_privilege(authenticated,...,'SELECT') = true`, RLS enabled, and that exact policy. It holds one open shift and zero closed shifts. Its local ledger has 52 diagnostic versions and is not a clean replay of the 51 original source migrations.

Read-only local SQL using `SET LOCAL ROLE` plus a request JWT subject returned one own row, zero rows for a different identity, one row for an active Manager, and zero for `anon`. This checks PostgreSQL grant/RLS behavior on the open row, **not** fresh JWT/PostgREST behavior, inactive-account denial, or closed-row access. `anon` has a table-level SELECT grant in this local catalog but no matching RLS policy; relying on that combination should be reviewed before release. Authenticated UPDATE/DELETE grants also exist, but no matching shift policies appeared in the catalog; no write was attempted.

The ownership arm of the existing RLS policy does **not** require an active cashier profile. The new isolated H-08B stack confirmed this with a real local JWT/PostgREST read: after deactivating one synthetic Cashier, its existing token still fetched its own closed shift. Therefore, direct-table retrieval would not meet a strict “active Cashier only” design. The mounted role route is a navigation gate, not database authorization. Do not treat the existing direct SELECT as owner approval to expose a historical audit screen.

## Financial meaning and limits

The frozen as-closed values are `cashier_shifts.opening_cash`, `expected_cash`, `actual_cash`, `variance`, `variance_reason`, `notes`, `started_at`, and `ended_at`. Current `cashier_transactions.status` and linked `payments.status` are mutable projections; a later cancellation can make a current sum differ from expected cash saved at closure. The closure RPC returns `cash_sales`, `gcash_sales`, and `transaction_count`, but those three are **not stored in `cashier_shifts`**. They cannot be reconstructed as an exact as-closed breakdown from currently mutable receipts. Any proposal to persist a new immutable breakdown or adjustment journal is separate accounting work pending the financial policy decision sheet.

The UI currently retains `pendingPaymentCountAtClose` and cashier display name locally. Neither is a persisted shift column; a fresh authoritative history must not fabricate either. For persisted history, use the authenticated profile only for present display identity or show the cashier UUID until an approved safe name projection exists. `closed_by` and Manager approval fields can be returned as IDs without widening unrelated profile access.

**Decision:** Existing RLS-backed table SELECT is an available read path, but its active-cashier gap, broad table exposure, and unapproved staff access scope make it unsuitable to silently wire into the UI. The preferred narrowly scoped retrieval proposal and its permission gate are in [the implementation plan](H08B-HISTORICAL-SHIFT-IMPLEMENTATION-PLAN.md). No historical retrieval was implemented. Fresh browser independent closed-shift load: **NO — confirmed in the new isolated stack**. The DB had two persisted closed shifts, yet a fresh authenticated Cashier browser showed “No shift records yet” before and after reload.
