# MGR-REC-03A — Receiving runtime compatibility diagnosis

Date: 2026-10-23 (Asia/Manila). Scope: read-only diagnosis of the reported `PR-20261023-000004` Start Receiving error. No production code, hosted schema, or hosted business data was changed.

## Executive finding

**DIAGNOSED — connected backend is outdated for the current linked Receiving frontend.** The local UI sends a generated, non-null `p_report_id` and `p_inspected_by_name: null` to `public.start_inventory_request_receiving(uuid,integer,uuid,text,text)`. The hosted function in project `zhzluhqvysvsadwuugpa` still rejects a null/blank inspector and raises the exact displayed error, `Receiving ID and physical inspector required.` (SQLSTATE `22023`). The local MGR-REC-02B migration changes that precondition to require only the report ID and derives the inspector from the authenticated Manager. The failure mechanism is directly established by current source and hosted function definition; the original HTTP exchange was not captured, so the exact failed request/HTTP status was not independently observed.

The latter rereads the register, checks the same request/revision, and calls `startInventoryRequestReceiving(request.id, request.revision, reportId.current)` only when no draft is present. `reportId.current` starts as `crypto.randomUUID()`; the wrapper sends named arguments `p_request_id`, `p_revision`, `p_report_id`, `p_inspected_by_name: null`, and `p_inspection_note: null` through `supabase.rpc`. The posted receipt's next-delivery action uses the same wrapper.
- `ReceivingDocumentList` is rendered alongside the queue; it is not the Start Receiving handler. The exact error text exists in the original SQL function, not frontend validation or the API error formatter. The wrapper forwards `error.message` into a JavaScript Error, which the queue displays. No stale inspector form state remains on this linked queue path. Separate non-linked Receiving paths still have their own inspector fields and were not changed or diagnosed here.
- No existing browser network capture of the failed click was available. Thus endpoint `/rest/v1/rpc/start_inventory_request_receiving`, request argument names, and SQLSTATE are derived from current source and live SQL; HTTP status and the precise browser bundle/request payload were **not directly observed**. No write RPC was replayed.

## Connected versus local RPC contract

| Check | Hosted connected database | Local MGR-REC-02B target |
|---|---|---|
| Function | Exactly one `public.start_inventory_request_receiving(uuid,integer,uuid,text,text)` overload; five named arguments, no defaults, returns `jsonb` | Same signature and return type; no new overload |
| Security and ACL | `SECURITY DEFINER`, empty `search_path`; `authenticated` EXECUTE true, `anon` false | `SECURITY DEFINER`, empty `search_path`; explicitly revokes PUBLIC/anon and grants authenticated/service_role. Existing owner/EXECUTE context is preserved by `CREATE OR REPLACE` |
| Actor | Calls `public.inventory_request_manager_required()` to obtain authenticated active Manager UUID, used for `received_by` and event actor | Same authorization helper and `received_by`/event actor; stores `v_actor::text` as inspector and ignores the legacy caller inspector argument |

| Result on current linked call | Null inspector necessarily fails before request lookup, receipt insert, or delivery-start event | Null inspector is accepted after Manager authorization; the server supplies inspector identity |

The hosted `pg_proc.prosrc` was read directly. It contains the old null/blank inspector check and client-supplied inspector insertion, and lacks the 02B `v_actor::text` attribution. Its `pg_get_functiondef` MD5 was `c56e67d1fecef8ee7aed481d9602e14f` at inspection. Hosted migration history shows `20261012181744 manager_inventory_request_documents`; the inspected history contains no 02B inspector migration. Function body evidence, rather than history alone, establishes the current behavior. The local file `supabase/migrations/20261023113221_manager_receiving_verified_inspector.sql` exists and its SHA-256 was verified as `23D7F72D20C9D3B9C5791078EE56C17C8D458930EE7027164D49B0C582C8D776`.

The generated Receiving UUID is required *for draft creation*, before any receipt exists. The frontend supplies one; this is not a missing-ID or call-order defect. The exact hosted exception may mention both ID and inspector, but its OR condition means a null inspector alone triggers it. The prior `inventory_request_manager_required()` call implies that this specific SQL exception follows successful Manager authorization in that function, assuming the displayed message came from this call.

## Root cause, correction, and release boundary

Classification **A: backend older than frontend**, high confidence in the contract mismatch and failure mechanism; moderate confidence that the reported click used this exact request because no original browser network capture was available. The current local 02B migration is the narrowly scoped backend correction for this exact mismatch. No additional linked Receiving frontend source change or new migration is indicated by the evidence. Do not restore manual inspector/condition inputs or invent inspection notes; that would reverse the approved Manager inspection policy. Check the existing next-delivery caller and any other five-argument caller during cutover; preserving the signature supports them, while old clients' supplied inspector text will intentionally be ignored after 02B.

The next separately authorized action is a **controlled 02B deployment plan**, with explicit approval before hosted execution. Preflight should verify exact target, checksum and SQL, hosted function body/signature/grants/dependencies, migration history, and recovery/rollback capability. The prior clean migration replay and off-device recovery limitations remain unresolved; this diagnosis does **not** grant hosted release GO. With adequate recovery evidence and separate authorization, apply the backward-compatible backend function first, then ensure the updated local frontend/browsers use the matching code. Follow with a separately approved authenticated Manager smoke test on a safe authorized case, checking server-derived inspector, draft identity, role denial, and that stock moves only on posting. Do not use the real request for an experimental write without authorization. A Vite/browser refresh alone cannot fix the currently connected old SQL function.
