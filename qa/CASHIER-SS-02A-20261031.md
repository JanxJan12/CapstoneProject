# CASHIER-SS-02A — Shift Settlement implementation specification

**Date:** 31 October 2026, Asia/Manila. **Classification:** design and read-only verification. **Implementation authorization:** documentation only. No React/TypeScript source, migration, RPC, RLS rule, database object, or hosted business record was changed.

## Executive decision

The existing Cashier-led open → transact → count → review → close → retrieve lifecycle can support an end-of-duty routine without a new settlement backend state. The server already owns shift authorization, exact-shift receipt inclusion, the final drawer calculation, closure, and saved snapshots. A narrowly scoped frontend SS-02B is ready for review. It should make the opening amount deliberate, explain the provisional estimate, focus the count/variance task, and give precise blocker/retry guidance. It must preserve the current closure RPC and payment guard.

Duty-based ending is now approved **as an operating requirement**, but there is no schedule-linked shift end or automatic closure in the inspected path. `ended_at` records actual successful closure time. One hosted open shift was about **249.9 hours old at the 31 October read-only query**; one pending online GCash payment still existed. These point-in-time facts do not establish why that particular shift remained open. The current 12-hour warning does not itself close or hand over a drawer. No hosted settlement formula defect was demonstrated: five closed shifts had no saved `variance != actual_cash - expected_cash` mismatch in this snapshot.

## Approved policies and role boundaries

| Policy | Design consequence | Current support / boundary |
| --- | --- | --- |
| SS-POL-01 Cashier performs own reconciliation | Cashier counts and attests their own drawer. No mandatory second count or Manager approval. | `start_cashier_shift` and `close_cashier_shift` require an active Cashier and operate on that Cashier's open shift. Manager can review saved history via a separate route. Existing optional `manager_approved_*` columns do not create an approval requirement. |
| SS-POL-02 End at scheduled duty completion | Present a routine to settle when duty ends; preserve actual closure timestamp if late. | No duty schedule, shift deadline, freeze, handover, or expiry appears in the active Cashier settlement path. The Cashier must initiate close. Restaurant operations can continue on other terminals, subject to the current terminal constraints. |
| SS-POL-03 Physical cash accountability | Identify opening, Cash receipts, expected estimate, physical count, signed variance, and readiness. | Most facts already exist; the open page's four cards and long explanatory copy dilute the task. A count cannot be entered from this page while its pending-payment button is disabled. |
| SS-POL-04 Financial correctness | Server final amount and closed snapshot prevail; GCash excluded from drawer. | Inspected close RPC implements this. Browser projection is explicitly provisional; saved history reads stored columns. |
| SS-POL-05 No inferred rules | Keep automatic closure, approval/tolerance, denominations, payout accounting, float assignment, concurrent drawers and blocker changes out of SS-02B. | These remain business decisions and, for several, backend changes. |

**Cashier:** select the terminal they are using, enter the actual opening float, process authorized payments, count all cash including the float, explain a nonzero variance, confirm closure, and retrieve their own saved settlements. **Manager:** handle existing paid cancellation/refund attestation and authorized shift audit; ordinary reconciliation is not gated on Manager approval. Terminal text is an identifier in `cashier_shifts`, **not proof of a uniquely identified physical drawer or a Manager assignment**.

## Current state-transition model and recovery

Only `cashier_shifts.status = open|closed` is persisted. Preparing, counting and reviewing are browser states; they are not database states.

| Conceptual stage | Actor/control and required data | Backend mutation/guard and recovery |
| --- | --- | --- |
| No active shift | Cashier sees empty state and Start new shift; history remains available. | `get_open_cashier_shift` restores own open row. Do not treat missing local cache as authoritative absence after a failed read. |
| Opening | Start dialog pre-fills **₱4,000** and profile terminal, both editable; Cashier submits. Client schema allows 0–100,000, terminal at least 2 chars; server requires finite nonnegative cash and nonempty terminal ≤50 chars. | `start_cashier_shift` checks active Cashier, inserts one open row with server time; unique open-Cashier/terminal indexes arbitrate races. An uncertain response should be resolved by re-reading own open shift before starting again. Opening cash has no ordinary edit action after insert. |
| Active operation | Cashier POS and authorized online-payment decisions produce receipts/payments; transactions carry the shift FK. | Current Cashier read model hydrates current shift. No shift freeze or duty deadline. Other-terminal operations need their own shift under current rules. |
| Prepare and count | Page shows provisional estimate; Review end shift opens count form only when local pending count is zero. Actual count may be 0, otherwise nonnegative and at most two decimals. | No persistence until close. Invalid/empty input is rejected locally. Count must include opening float. No denomination requirement. Closing dialog is unmounted if active shift disappears. |
| Review eligibility | Browser derives variance from estimate and asks a reason when nonzero; optional notes. Review snapshot tracks shift ID and local expected amount, and invalidates if they change or pending count becomes positive. | Local guard is advisory. It cannot prove payment/sale state is fresh; server checks again. |
| Closure request | Cashier explicitly confirms; a local ref blocks duplicate clicks. | `close_cashier_shift` locks the own open row, serializes pending online GCash transitions with an advisory lock, recomputes final totals and variance, requires reason for nonzero server variance, writes closed fields atomically. A second call has no open shift to close. RPC error leaves dialog available. If response was lost after commit, re-read open and saved history before another attempt. |
| Closed/history | Cashier sees success only after RPC response and can retrieve saved history; Manager has a separate authorized audit route. | `get_closed_cashier_shifts` returns stored snapshot fields, newest first by `ended_at,id`, keyset page/date filters. Later receipt changes do not rewrite the saved values through this read path. Privileged mutation resistance beyond observed ACL/RLS was not proven. |

## Financial source-of-truth map

All amounts are PHP pesos; server monetary columns are `numeric`, with cent-rounded final settlement. Browser JavaScript totals are advisory. A Cash receipt is a payment collection, not necessarily fulfilled-order revenue; tender/change are not added to sales. A Manager refund attestation does not by itself prove physical cash movement.

| Value / UI consumer | Source, qualifying/excluded population, timing and risk |
| --- | --- |
| Opening cash / active header, metrics, saved card | `cashier_shifts.opening_cash numeric(12,2)` submitted at start and fixed to exact shift. Current ₱4,000 client default can be mistaken for a verified assigned float. Server does not receive or store a second-person float attestation. |
| Shift Cash receipts / active estimate details | `cashier_transactions.shift_id` links sale to shift; `payments.amount numeric(10,2)` is charged amount. Server at close sums **completed transaction AND verified payment AND Cash** for that exact `shift_id`; voided, unverified, GCash and other shifts excluded. Browser `calculateShiftTotals` sums hydrated `Completed` Cash rows and has a legacy `Refunded` subtraction; it does not re-check verified status, so stale/inconsistent state can diverge. Current hosted check from SS-01 found zero completed-unverified rows. |
| GCash / secondary active reference | Same server completed+verified shift population, GCash branch separately returned by close RPC; excluded from expected physical cash. A pending online GCash payment has no verified receipt to add. Manager fulfilled revenue uses a different fulfillment-date population. |
| Provisional expected / `ShiftMetrics`, `EndShiftDialog` | Browser `openingCash + Completed Cash − legacy locally Refunded Cash` from current hydrated state, in JavaScript. Rounded variance preview is informational. A Manager void, new sale, or delayed refresh can change it. The hosted transaction enum supports completed/voided, so the legacy `Refunded` branch is not a supported hosted status. |
| Final expected / RPC result and saved history | `close_cashier_shift`: `round(opening_cash + sum(verified completed Cash payment.amount on locked own shift),2)`. Saved as `cashier_shifts.expected_cash numeric(12,2)`; no client expected parameter. It is the final server snapshot. |
| Counted cash / form, RPC, history | Cashier physically counts bills/coins including float; frontend requires finite, nonnegative, ≤2 decimals. `p_actual_cash` is server-checked and rounded, saved `actual_cash numeric(12,2)`. Physical truth is an operator attestation, not independently sensed. |
| Variance / review and saved card | Server saves `round(actual_cash - expected_cash,2)` in `variance numeric(12,2)`, positive over/negative short; requires nonempty reason for nonzero and clears it when zero. Notes optional. Browser preview may differ from server; a discrepancy reason can be supplied even if preview is zero to handle a changed final total. |
| Closed snapshot / Saved closed shifts | `get_closed_cashier_shifts` reads saved opening, expected, count, variance, reason, notes, actors and timestamps. It does **not** persist as-closed Cash/GCash component sums separately. Do not label a current receipt re-sum as a historical closure fact. If showing `expected − opening`, label it a derivation under the existing formula, not a stored receipt total. |

The Manager paid-cancellation RPC voids an original payment/receipt after a full executed refund is attested; a Cash refund requires its original shift still open. The resulting current receipt sum excludes that void. There is no independent cash paid-out, drop, add, or transfer row tying the physical movement to a drawer. If cash was paid from a different drawer, current expected cash may be operationally wrong despite internally consistent receipt arithmetic. No new ledger or formula is approved.

## Long shifts, terminal handover and pending-payment alternatives

The long shift is technically possible because there is no server age cap or automatic expiry; the page warns after 12 hours and the close RPC can be blocked by any outstanding online GCash payment. The current source does not show a scheduled-duty value, terminal handover state, or recorded reason for delayed closure. Do not assert that the pending payment caused the particular 249.9-hour shift. A late closure must save its **actual** `ended_at`; do not backdate or split it. Guidance should direct the Cashier to resolve accessible payments, seek authorized help for an inaccessible/stale request, count, and close once eligible. Another Cashier can start a different terminal if the one-open-per-Cashier/terminal rules allow; using the same terminal before closure is rejected, appropriately avoiding untracked overlapping drawer accountability. Whether the restaurant has a distinct drawer available, and who holds the cash during a late handover, needs an owner decision.

The exact server predicate is `orders.order_channel='online' AND payments.payment_method='gcash' AND payments.status='pending'`, **without** shift, Cashier, terminal, or date filter. The local page instead counts all hydrated `Pending` payments and therefore is not a perfect server eligibility read; it can be stale or broader/narrower than the server query. The shared online queue includes Customer-originated reviews. A pending unverified payment does not currently increase expected physical Cash, but deciding its later verification owner/shift is an accounting and operations question. The advisory lock serializes a new/resubmitted pending GCash write with close under READ COMMITTED. It does not establish a restaurant policy for who resolves an old request.

| Option | Financial integrity and operational effect | Security, database/RPC/migration, testing | Recommendation / approval |
| --- | --- | --- | --- |
| **A. Preserve restaurant-wide block** | Strong simple no-unresolved-online-payment prerequisite; one unrelated old review can delay another Cashier's end-of-duty closure indefinitely. No cash is added for the pending item, but its future verification/receipt association remains unsettled. | No DB/RPC migration. Keep current role checks and advisory lock. Test old/new pending, concurrent insert/update/close, and Cashier resolution rights in isolated DB. | **Retain in SS-02B** while policy is unsettled. Owner must decide escalation and service response for inaccessible/old proof. |
| **B. Scope to relevant shift** | Lets unrelated drawers settle; requires a trustworthy assignment of a pending payment obligation to a particular Cashier/shift before verification, and a rule if that shift closes first. Current payment queue has no authoritative shift-scoped pending predicate. | New ownership contract and likely columns/events, RLS/RPC and migration; rework lock/predicate atomically. Test ownership, late verification, reassignment, cross-Cashier reads, races, refunds and history. | **Defer.** Owner must define who owns a Customer online request and which shift receives its eventual receipt. Frontend filtering alone is unsafe. |
| **C. Explicit exception / handover** | Permits duty closure with unresolved payment only if liability and later verification are assigned and auditable; wrong assignment could omit or double-count a later receipt. | Durable exception/assignment event, authorized actor, idempotency, immutable audit and eventual reconciliation; close and payment RPC changes, RLS/migration. More complex race/replay tests. | **Defer.** Owner must approve who may grant exception, who takes pending liability, and how later payment/receipt is settled. No silent bypass. |

Current recommendation is **A with clearer guidance**, not a claim A is permanently ideal. No payment blocker or server function changes belong to frontend SS-02B.

## Proposed Cashier interface and target lifecycle

```text
SHIFT SETTLEMENT
Active shift: Cashier name · Terminal [identifier] · Opened [Manila time] · Elapsed time
  Long-running? Show end-of-duty reminder and actual-closure guidance.

EXPECTED CASH (provisional)
  Opening float                        ₱...
  Completed Cash receipts              ₱...
  Expected drawer estimate             ₱...
  GCash ₱... is separate and is not cash in this drawer.
  [Details: transaction/void/discount context where already available]

CLOSURE READINESS
  Ready to review / Pending online payment review prevents closure.
  [Review payments] [Explain whom to contact if inaccessible or stale]

[Review end shift]
  Actual physical cash counted         [₱ input, blank initially]
  Balanced / Short ₱... / Over ₱...  (compared with estimate)
  Variance reason [required for nonzero; optional for a zero estimate]
  Notes [optional]
  [Review and confirm]
    Shift/terminal · provisional expected · counted · estimated variance
    Server rechecks eligibility and computes saved values on confirmation.
    [Back to review] [End shift]

SAVED CLOSED SHIFTS
  Manila closure-date filters · newest first · saved expected/count/variance
  Expand notes and technical audit identifiers; 25 per page.
```

**Begin duty:** Cashier reads/enters terminal and their physical opening float, confirms, and sees server-started shift. **Operate:** existing Cash/GCash and Kitchen flows continue with exact shift links. **Prepare at duty end:** Cashier sees identity, opening time, estimate and readiness; transactions are not frozen. **Count and review:** enter all cash, correct invalid input, see signed difference, give required reason, optionally note. **Confirm:** server rechecks, then saves; UI declares success only after response. **History:** own persisted record, including actual closure time, can be found without a new shift. This uses existing RPCs and does not invent a persistent “preparing” state.

Alternative flows: no shift → Start; zero count → valid and likely shortage if expected positive; exact → balanced/no reason; short/over → signed amount and required reason; pending → no close, review or escalate; long → warning and authorized late close; changed shift/estimate → review again; server mismatch/error → keep count and show specific rejection; uncertain network result → check open and saved history before retry; unauthorized/other shift → backend denial; historical lookup → read own snapshot. Count while the pending blocker is visible could be useful, but the present UI suppresses it; permitting a durable count draft or closing with a blocker needs separate UX/privacy and freshness design, so SS-02B need not add it.

**Accessibility and responsive acceptance:** retain labels, explicit error text and focusable controls; ensure the modal scrolls on small screens without hiding count or confirmation; `role=alert/status` must announce blocker and variance changes; keyboard-only Start, count, Back, Confirm, history filter/expand and screen-reader names must be checked in a real browser. Source markup alone does not prove rendered behavior.
