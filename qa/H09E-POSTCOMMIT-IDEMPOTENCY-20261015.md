## Boundary and source contract

The preserved synthetic `rrj_h09_order_flow_20261015` stack at `127.0.0.1:48321` / DB `48322` was reused. It began H-09E with **26** orders. A normal Docker Desktop restart restored its unresponsive Auth/engine before testing; the same volume and all other stacks, backups and demo resources were retained. The database still had **53 diagnostic** migration entries, and all **52/52** canonical migration hashes matched. Hosted Supabase was not contacted.

Active Customer Checkout stores `{requestId, fingerprint}` in `sessionStorage` under `rrj_customer_order_request_v1`. The fingerprint covers trimmed customer and delivery details plus sorted cart item/option identities. A network error leaves the request ID in place; a reload preserves it in the same browser tab, while the cart is separately restored from `rrj_customer_cart_v2`. The customer must re-enter the delivery details after reload; the same values reproduce the fingerprint. Successful payment submission clears the saved order request ID. The active `place_customer_order` RPC checks `customer_id + customer_request_id` under a transaction advisory lock and returns the existing order before repricing or inserting; the database also has the unique partial `orders_customer_request_id_uidx` on those columns. The RPC writes one order, purchase-time order-item snapshots and an initial status event in one transaction. ## Actual post-commit order test

The complete [Chrome result](h09e-browser-20261015/result.json) is for new synthetic **`ORD-000028`**, request ID `3ac82f72-b98d-425f-b35b-ec951fdff085`. Chrome submitted the order `POST` after its CORS preflight. CDP `Fetch.enable` paused the **POST response stage**, where the server status was **200**. While Chrome waited, a separate Docker `psql` read found the persisted order, its order number and ₱225 total; total orders had changed **27→28**. Only then did `Fetch.failRequest(ConnectionClosed)` prevent that successful response from reaching Chrome. The Customer checkout showed [“Unable to place your order: TypeError: Failed to fetch”](h09e-browser-20261015/postcommit-lost-response-error.png).

The same Chrome tab was refreshed. Its stored request ID was **identical before and after refresh**. The saved cart was reopened and the same delivery details were entered. Retry reached `place_customer_order` with the same identity and returned **`ORD-000028`** on the [payment step](h09e-browser-20261015/postcommit-existing-order-payment-step.png), rather than creating another order. Total orders remained **28**. Final SQL found **one** row and **one distinct order number** for the request ID, with the unique index installed. The one item retained its purchase-time **₱175** unit/line price and the same `Extra rice` and `H09 required choice` modifier snapshot at commit and after retry. The ₱50 delivery fee yielded ₱225. Before payment submission this order had **0** payments, receipts, stock entries and assignments. A later fresh authenticated Chrome session reopened the same order through [Customer History](h09e-browser-20261015/existing-order-history.png) and [Track Order](h09e-browser-20261015/existing-order-tracking.png).

This is a **response lost after a confirmed database commit**. H-09D’s blocked-before-server request is separate prior evidence and was not counted as this result. CDP Network request IDs and the synthetic request ID are in the [sanitized JSON](H09E-POSTCOMMIT-IDEMPOTENCY-20261015.json); preflight and `POST` events are distinguished by the interceptor’s method check.

## Payment submission response loss

The same new order used a clearly synthetic local proof image and fictional demo reference. The browser uploaded the image once, then called `submit_customer_payment`. CDP paused the actual `POST` at a **200 response**; independent SQL found one **pending** payment before the response was cut with `ConnectionClosed`. Chrome displayed the [payment submission error and Retry Payment Submission control](h09e-browser-20261015/payment-postcommit-lost-response-error.png). Clicking that control returned the same payment ID, `fea7581d-a511-417f-9db5-ce7128e583f7`, and displayed [the submitted demo claim](h09e-browser-20261015/payment-existing-submission-confirmed.png). Final SQL found **one pending payment**, its private proof object metadata present, **0** receipts, **0** stock ledger entries and **0** delivery assignments for `ORD-000028`. No Cashier verification, external GCash settlement or real payment was performed; those are **NOT TESTED** in H-09E. The existing payment RPC's exact pending reference/path/amount replay contract was exercised; no refund or accounting policy was changed.
