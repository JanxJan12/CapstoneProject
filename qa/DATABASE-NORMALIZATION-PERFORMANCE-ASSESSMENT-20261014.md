# RRJ’S FOOD-HOUSE: read-only normalization and performance assessment

**Assessment date:** 2026-10-14 (Asia/Manila). **Scope:** the 34 `public` tables in the existing hosted catalog snapshot, the canonical migration chain and application/Rider query paths. **Action taken:** analysis and this report only. No SQL, migration, data, index, repository cleanup, or hosted mutation was executed for this assessment.

## Evidence and interpretation

This continues [the architecture optimization report](DATABASE-ARCHITECTURE-OPTIMIZATION-20261014.md), [the 34-table disposition register](DATABASE-DISPOSITION-REGISTER-20261014.md), and [the redundancy audit](DATABASE-REDUNDANCY-AUDIT-20261013.md). Their [catalog and index capture](DATABASE-REDUNDANCY-EVIDENCE-20261013.json) and [column/policy supplement](DATABASE-REDUNDANCY-SCHEMA-SUPPLEMENT-20261013.json) are the hosted evidence. The disposition JSON contains all declared keys, constraints, FKs, and column names. The existing reports reconfirmed 34 public tables, 378 columns, 73 FKs, 122 indexes, and RLS on every public table on 2026-10-14. This assessment did not make a new hosted connection; counts and statistics below retain their capture dates. The preserved isolated stack's synthetic null/distinct profiles are **not** hosted measurements.

The matrix assesses functional dependencies (FDs) at the *business grain*, not merely whether a surrogate `id` determines its row. `K` means declared PK; `AK` means a declared unique alternate key or unique partial index. A nullable PostgreSQL `UNIQUE` value is only an alternate key for non-null rows unless `NOT NULL` or a predicate supplies that condition. Unlisted natural identifiers are **possible**, not declared candidate keys. `Y/Y/Y` means no identified 1NF/2NF/3NF breach at the modeled grain; `C` flags a condition or deliberate snapshot; `D` flags a stored derivation with a 3NF maintenance risk. A JSON/array column is one SQL value, yet nested elements are outside relational 1NF if independently queried or updated. Single-column surrogate PKs make 2NF formally trivial; they do not cure a hidden business-grain FD.

| `delivery_assignments` | K `id`; partial AK `order_id` only for active statuses; FKs `order_id → orders`, `rider_id → riders` | Y/Y/Y. `id → offered rider, lifecycle timestamps, proof path`; multiple rejected/cancelled historical offers per order are expected. `order_id` alone is not a candidate key across history. **Overall:** the relational cores and declared junctions are broadly 3NF. Strict 1NF depends on how JSON/array payloads are used; several are intentionally immutable documents or sold snapshots. Stored arithmetic and current-state projections create controlled 3NF-style maintenance risks, not an automatic mandate to split or delete them. No declared FD alone proves a table, row, or column redundant. The candidate-key list is limited to enforced uniqueness; additional business identifiers require owner definition and duplicate/null checks.

## Prioritized optimization report

| Priority | Opportunity and evidence | Decision / proof required before a change |
| --- | --- | --- |
| P0, consistency | `cashier_transactions` and `paid_order_cancellations` store multiple IDs connected through one-to-one payment/order/receipt relationships. `receiving_report_items`, `inventory_batches`, `inventory_transactions`, and batch allocations store item IDs also reachable through their source links. | Run privacy-safe **mismatch counts** on the true hosted grain and inspect RPC/trigger enforcement. If any mismatch exists, investigate provenance without repair. If zero and writers lack a guard, propose additive validation in isolated stack; cover legitimate historical exceptions first. |
| P0, projections | Order/line totals, PO totals/quantities, cashier variance, inventory master/batch balances, and request current revision are maintained values. Prior report's hosted arithmetic checks passed at capture, and stock semantics differ for tracked vs aggregate items. | Keep materialized values. Add a read-only recurring reconciliation specification and transaction-bound writer assertions only when a concrete drift path is demonstrated. Do not rebuild stock from incomplete history or invent opening balances. |
| P1, query plans | Manager order list uses `ORDER BY orders.created_at DESC, orders.id DESC LIMIT`, while hosted has a single-column `orders_created_at_idx`. Manager/dashboard recent orders and assignment lateral lookup have similar ordered access. | Capture sanitized `pg_stat_statements` workload and representative `EXPLAIN (FORMAT JSON)` for actual role/filter/cardinality. Candidate **only if measured**: `(created_at DESC,id DESC)` on orders, perhaps a role-specific status/date composite; compare to existing single indexes and write cost. No index created here. |
| P1, event lookups | Cashier hydration orders `order_status_history` by `created_at` after `order_id` filter, but current index is `(order_id)` alone; order item aggregation similarly orders by `(created_at,id)`. | On realistic history depth, compare sorts/buffers and candidate `(order_id,created_at,id)` indexes against current indexes. Keep if they improve the relevant RPC without undue write overhead. Never enforce unique `(order_id,status)`. |
| P1, rider offer/assignment | Rider source filters offered assignments and orders by `assigned_at`; manager order RPC seeks the latest nonterminal assignment. Existing indexes include single `rider_id`, `status`, `order_id`, plus a partial **unique** active-order index. | Test `(rider_id,status,assigned_at)` or a selective offered partial index for rider RLS access only after plan/traffic proof. Retain the active-order unique index; its constraint is independent of scan counts. |
| P2, inventory reads | `get_manager_inventory_movements` already has `(created_at DESC,id DESC)` and `(inventory_item_id,created_at DESC,id DESC)` indexes and keyset pagination. Its date predicates cast `created_at` to Manila local date, which may reduce direct index range use. | Compare current plan with equivalent precomputed UTC `timestamptz` bounds, accounting for Manila day boundaries and DST-independent local rule. Refactor only if plans and results match. Keep existing movement and FIFO/FEFO partial indexes. |
| P2, index portfolio | Some single-column FK/status indexes may overlap a composite's leading prefix, but 122 indexes include PK/unique/FK support, partial business constraints, and low-volume future paths. Index scan counters lack a trustworthy reset/observation window. | Inventory index definitions, uniqueness, predicates, `indisvalid`, size, writes, FK delete/update workload, and plans over an agreed period. Flag exact semantic overlaps for review; **zero scans or zero rows never justify a drop**. |
| P3, documents and scale | `aliases`, modifiers, `issue_input`, revision snapshots, event details, and opening payloads are structured values. No evidence shows a bottleneck or required element-level constraint. | Retain. If reporting needs nested predicates, first specify access paths, data shape, retention, and privacy. Consider generated relation/index only after measured workload and compatibility design. |

Index and plan recommendations follow [PostgreSQL's index usage guidance](https://www.postgresql.org/docs/current/indexes-examine.html) and [Supabase query optimization guidance](https://supabase.com/docs/guides/database/query-optimization): plans, row distribution, and write cost decide whether an index helps. `pg_stat_statements` is useful for workload ranking, but its counters require a known observation period ([Supabase documentation](https://supabase.com/docs/guides/database/extensions/pg_stat_statements)). `EXPLAIN ANALYZE` executes its statement, so hosted investigation should use plain `EXPLAIN` for SELECT plans unless a controlled read-only timing window has been explicitly established.

## Implementation proposal (not executed)

1. **Read-only baseline:** reconcile exact hosted catalog/migration lineage, capture query fingerprints, sanitized plan JSON, table/index statistics with reset time, and the existing arithmetic/relationship mismatch counts. Confirm each candidate query's actual caller and RLS role. Preserve source, Rider repository, dirty worktrees, original migrations and the defense demonstration stack.
2. **Isolated design:** for any confirmed mismatch path, specify the exact invariant and historical exceptions. For any index, compare baseline and candidate under representative cardinality in a disposable, isolated restored Supabase environment; measure p50/p95, buffers, planning time, write amplification and lock behavior. A composite's leading columns, predicate, and sort direction must match the actual query. No synthetic fixture enters the business baseline.
3. **One change per review unit:** additive guard/RPC fix or one independently justified index in a new forward migration. Do not edit applied migrations, merge formal and legacy requests, delete event history, or change order snapshots. The already prepared duplicate timestamp-trigger migration is a **separate** prior proposal; it is not rerun or included as a new normalization fix here.
4. **Rollback:** retain the old index/logic until the new path passes; for an additive index, rollback is the exact named index drop after confirming no constraint depends on it. For a writer guard, rollback restores the prior function body from a versioned, reviewed migration while preserving rows created meanwhile. Any data correction needs a row-level, provenance-backed reversal plan and backup; this assessment proposes none. Never treat a down migration as a substitute for complete DB/Auth/Storage recovery.
5. **Regression gates:** compare PK/AK/FK/check catalog, RLS/policies/grants, count/key fingerprints, financial totals, payment/receipt pairing, request revision snapshots, receiving accepted splits, PO links, stock master/batch/ledger and exact allocation reversals. Run authenticated Customer → payment → Cashier → KDS → Rider and Manager/Production/direct-supplier → Receiving → posted stock on an isolated same-database stack, plus Rider web/Android where affected. Preserve idempotent retry, rejected/partial receipt, cancellation and concurrent posting cases. Recheck all metrics and plans after any staged change.
6. **Hosted gate:** **NO-GO** for DDL/DML here. The prior reports' historical clean replay/provenance and encrypted off-device DB plus private Storage recovery/restore requirements remain open. Review a concrete statement set, rollback, regression evidence, and maintenance window only after those gates are met. Hosted remains strictly read-only under this request.

### Assessment limits

This is a structural and source-path assessment based on the current repository and the dated hosted catalog captures; it is **not** a fresh hosted workload benchmark. Candidate FDs involving cross-table identifiers are potential anomalies until real relationships and writers are checked. Current small hosted table sizes can favor sequential scans, so no proposed index is a demonstrated speedup. The isolated synthetic database can test correctness and candidate plans but cannot prove hosted cardinality, traffic, OAuth, browser/device, or release readiness.
