# Track B — deployed-schema clone acceptance (27 October 2026)

## Decision

**PASS for the bounded concurrency gate.** On an isolated, disposable PostgreSQL 17.6 database loaded from a schema-only export of hosted project `zhzluhqvysvsadwuugpa`, the original Manager/Rider bodies reproduced SQLSTATE **40P01**. Applying only the local Track B lock-order migration eliminated that deadlock in both controlled schedules. The expected winner committed; the loser was rejected by the existing state guard, with consistent financial and audit rows. This is a test of one synthetic order and the specified interleavings, not an end-to-end refund or production deployment acceptance.

**Deployment recommendation:** the lock-order migration is ready for a narrowly scoped deployment review/authorization. Do not deploy it as part of this acceptance. The real-world external-refund-before-RPC race still needs its own operational treatment; this migration does not make a refund atomic with Rider pickup.

## Reproduction boundary and limits

The local schema was exported on 27 October 2026 and may diverge after that time. It is a schema clone with synthetic rows, not a copy of hosted data, secrets, queues, scheduled jobs, or external payment behavior. Only one accepted assignment and the three forced schedules were covered. The `no_return` cancellation path intentionally had no inventory issue rows. RLS definitions and enabled state were preserved, but these security-definer RPC checks do not establish every direct-table policy or application UI workflow. The existing duplicate profile/Rider timestamp triggers were present in the clone and did not fail these schedules.

The labelled disposable container and its anonymous volume were removed after testing. Automatic approval review rejected deletion of the three schema-only export files in `C:\Users\Janmari\AppData\Local\Temp` (`rrj-track-b-deployed-schema-20261027.sql`, `rrj-track-b-auth-storage-schema-20261027.sql`, and `rrj-track-b-combined-schema-20261027.sql`), so those temporary local files remain. They contain schema definitions, not hosted table rows.

To rerun, create a fresh database per mode from the same current deployed schema-only export, load the fixture, apply the local migration only to the two corrected databases, and run `node qa/track-b-full-schema-concurrency-20261027.mjs <mode>` for `baseline`, `corrected-manager-first`, and `corrected-rider-first`. The runner expects the labelled local container and databases named in its source; it does not provision or delete them. Keep the hosted connection limited to schema retrieval.
