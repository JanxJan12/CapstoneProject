## 18. Prioritized finding register

### MGR-01 — P2 — Manager cannot administer ordinary product/category master data

**Status/confidence:** **CONFIRMED / PARTIAL** (mounted UI capability; owner policy not confirmed). **Screen/source:** `menu/MenuManagementPage.tsx`, `api/managerPhase2Api.ts`, Manager page switch. **Observed:** existing rows can be searched, filtered, paused/enabled, and given fixed meal/drink configurations; there is no ordinary product/category create/edit, base-price/description/image workflow. **Expected:** if the restaurant expects Manager-led menu maintenance, approved product/category changes should be possible through a guarded, audited authoritative path. **Impact:** routine menu changes require a separate technical/manual process; the page title overstates scope. **Cause:** current narrow RPC/UI contract. **Recommendation:** first obtain the owner’s field/approval policy; implement only approved fields with backend validation, audit trail, and explicit stock/quote effects, or rename the page and document the external process. **Acceptance:** Manager can perform only approved edits in an isolated stack; Cashier/Customer denied; invalid prices/categories/images rejected; future quotes update, historical snapshots unchanged; no retired modifiers. **Regression:** current availability, Fixed Meals, Drinks, Customer/Cashier catalog, KDS labels. No hosted change authorized by this audit. **Verification:** capability absence is source-confirmed; business requirement is **NOT TESTED**.

### MGR-02 — P2 — Dashboard physical low-stock count omits usable-stock urgency

**Status/confidence:** **CONFIRMED source / PARTIAL operational**. **Source:** hosted `get_manager_dashboard()` and `ManagerDashboard.tsx`; Inventory Overview uses usable/expired classifications. **Observed:** Dashboard low-stock count compares recorded `quantity_on_hand` with reorder level. An item with expired physical stock above minimum and low usable stock can be absent from that count. The UI accurately says “recorded on-hand”; no false numeric claim was observed. **Impact:** a Manager relying only on Dashboard may miss an item requiring action. **Recommendation:** add a distinct usable-out/low-usable attention indicator or make the Stock Monitor entry explicit without replacing the recorded-physical metric. **Acceptance:** synthetic expired-batch scenario produces a visible usable-stock warning, while physical count remains correctly labeled and no stock is changed. **Regression:** Overview classification, batch eligibility/expiry boundary, dashboard date/financial values. **Verification:** source definition **PASS**; operational counterexample execution **NOT TESTED**.

### MGR-03 — P2 — Desktop document can pan horizontally

**Status/confidence:** **CONFIRMED in synthetic browser / root cause NEEDS VERIFICATION**. **Source:** shared `AppShell`/styles, [20-screen result](manager-audit-browser-20261023/result.json). **Observed:** at 1024 and 1440 px, root scroll width was viewport +70 px; `scrollTo(999,0)` reached 80 px on four tested pages. Body and main did not overflow; the same behavior was noted in the older authenticated local browser report. Mobile/tablet fixture widths did not show it. **Impact:** unwanted horizontal pan/blank edge on desktop and possible keyboard/scroll friction. **Recommendation:** isolate the shell/root contributor (including pseudo or fixed elements), constrain only that source, preserve intentional table-local scrolling. **Acceptance:** root horizontal scroll reach 0 at 1024/1440 with Dashboard, Overview, Requests, Receiving and no clipped sidebar/table controls; repeat all five widths. **Regression:** drawer, fixed controls, internal table scroll, focus outlines. **Verification:** desktop no-overflow criterion **FAIL in synthetic fixture**, authenticated hosted **NOT TESTED**.

### MGR-04 — P3 — Full request-register aggregation may become costly

**Status/confidence:** **LIKELY / NEEDS VERIFICATION**. **Source:** hosted `get_inventory_request_register()` definition and `ManagerRequestsPage.tsx`. **Observed:** the register aggregates all requests with nested revisions, lines, receipts, and events without a page limit. No actual latency problem or high hosted cardinality was measured. **Impact:** historical loads may eventually delay Request History and increase response size. **Recommendation:** measure row count/response size and interaction latency before introducing cursor pagination. **Acceptance:** an agreed synthetic large-history threshold loads within the chosen target, and any pagination preserves revision/event ordering and selection. **Regression:** stale-response guard, filters, linked receipt navigation, revisions, exports. **Verification:** unbounded query shape source-confirmed; performance **NOT TESTED**.
