## 5. Findings by classification

**Confirmed source defect — completion timeline:** For `orders.current_status = completed`, `customerTrackingPage.tsx:899-903` sets `completedOrderStep` for the `delivered` step, and `:916-926` renders its green check even when no delivery history exists. `customerOrderSteps.ts:1-38` is a delivery-only nine-step list. This can visually claim a delivery milestone for an owned non-delivery order; the status card still says Completed. This is source-level proof of the branch, not a rendered reproduction. A later Customer-only correction should use fulfillment-specific steps, or omit delivery steps for non-delivery records, without changing stored status.

**Confirmed source guard gap — Cashier receipt reconciliation:** `receiptPresentation.ts:43-82` checks item lines against `order.subtotal` and order total against payment/transaction amounts, but it does **not** check `subtotal + deliveryFee + taxAmount = total`. A linked, verified synthetic record with internally matching payment/transaction total but inconsistent displayed charge components could pass preparation and print a receipt whose lines do not add to its total. The current order write trigger requires additive totals for new writes (`20261031193813...sql:21-35`), which reduces the normal-path likelihood; the migration explicitly leaves existing financial snapshots untouched. This is a source guard gap, not a reproduced live incorrect receipt. Preserve Cashier behavior in C.4 and route it to a separately scoped Cashier review if adviser evidence or historical data warrants it.

**Confirmed absence, not automatically a defect:** The active Customer pages have no sale-receipt print/download or `RCP-` display. Existing history/tracking already provide the itemized order view and recorded charges. The brief “Receipt format” feedback is insufficient to call this missing feature a bug. The Cashier receipt exists and is printable for a valid sale that passes its current guards.

**Risks:** A new Customer document generated from history alone could call waiting/rejected orders “paid,” create a second receipt number, use order placement as issue time, omit later void/refund information, or leak private proof/customer address. The active Cashier receipt relies on a verified payment and completed transaction but does not separately require fulfillment completion; labeling it “order completed” would be wrong. `customerHistoryPage.tsx:261-359` shows total even for unpaid orders, appropriately as “Server-confirmed total,” but a screenshot of that card could be mistaken for proof of payment if relabeled. Customer dates use the viewer's local zone while Cashier explicitly uses Manila, so shareable copies could disagree on displayed time.

**Unknowns:** Which example the adviser saw (GCash screenshot, checkout confirmation, Customer history, Cashier thermal print, or a requested downloadable copy); whether a Customer sale copy is needed at all; intended paper/PDF/mobile format; legal/tax wording and business registration requirements; treatment of legacy adjusted/voided/refunded sales; live grant/row shape drift; actual mobile printing, browser print headers, and physical printer output. No production receipt data, authenticated account, browser, device, or printer was inspected in C.4.

## 6. Minimal recommendation and owner/adviser decisions

1. **Keep the existing behavior now.** Preserve Cashier `RCP-` numbering, transaction/verification authority, guard conditions, print layout, and Customer order/history/tracking. Do not create a second receipt or add a generic print button from a total-only view.
2. Ask the adviser/owner to identify the exact screen or sample and desired recipient: Cashier paper receipt formatting, Customer order summary, downloadable copy of the already-issued sale receipt, or delivery acknowledgement. C.3 already covers the last item. Ask whether “Receipt format” is a visual correction to a current artifact or a requirement for Customer self-service access.
3. If a Customer copy of the sale receipt is explicitly required, use **the existing sale identity and recorded snapshots** after verified payment plus a valid completed transaction. Define a narrow own-order read path and a void/refund policy before UI work. Label it as a copy and keep order fulfillment state separate. Decide which personal details, if any, are necessary; default to order/receipt numbers, item/options, amounts, method and issued timestamp, without contact/address, proof image, internal IDs, Cashier shift, or Rider data.
4. Track the `completed`/Delivered timeline issue as a bounded Customer presentation fix after C.4 prioritization. It needs a non-delivery fixture and rendered check; it does not justify changing the sale receipt.

No tax rate, discount, service fee, new identifier, Customer acknowledgement, or legal “official receipt” claim should be introduced from this investigation.
