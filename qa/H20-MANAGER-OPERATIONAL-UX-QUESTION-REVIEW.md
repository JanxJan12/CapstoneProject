## A. Executive summary

The active Manager shell mounts Dashboard, Orders, Menu, seven Inventory entries, Riders, Customers, Reports, Shift Audit, and Settings. Stock item detail is an active drill-down from Stock rather than a sidebar entry. Formal multi-item request documents and the historical single-item Production queue coexist in Requests; they must remain separate. [Manager shell](../src/modules/manager/index.tsx#L89), [Requests](../src/modules/manager/inventory/ManagerRequestsPage.tsx#L1098).

The source supports several valuable answers: physical versus usable stock, expired quantity, reorder threshold, request outstanding quantity, per-batch balances, and ledger-linked movements. It also already provides pre-issue request review and a Receiving post review. The strongest confirmed *presentation* gaps are that no batch is explicitly named “next eligible for order consumption,” current and expired are the only batch badges, the request audit timeline exposes raw JSON event details, and the dashboard has no unified Receiving/request/waste task queue. These are source observations and UX inferences, not reproduced user failures. [Stock](../src/modules/manager/inventory/InventoryPage.tsx#L269), [batch list](../src/modules/manager/inventory/InventoryBatchList.tsx#L5), [request timeline](../src/modules/manager/inventory/ManagerRequestsPage.tsx#L1085), [dashboard](../src/modules/manager/dashboard/ManagerDashboard.tsx#L230).

**Key contract:** Issuance, recorded Messenger dispatch or reply, and Receiving drafts do not add stock. Only successfully posted accepted Receiving quantities do. A recorded dispatch is a Manager attestation, not proof of supplier delivery or acknowledgment. The H-16 local API/SQL campaign verified ten scenarios, including accepted-only posting and one duplicate-post denial, but zero rendered scenarios. [H-16 matrix](H16-MASTER-ACCEPTANCE-MATRIX.md#L3), [Receiving post RPC](../src/modules/manager/inventory/receivingApi.ts#L818).

## D. Batch rotation priority and authority

For batch-enabled items, confirmed-order deduction checks aggregate/batch consistency and locks eligible batches. Eligibility is **positive remaining quantity**, plus `use_by_date >= current Manila date` when `expiry_required` is true. With `rotation_policy = fefo`, it orders by earliest use-by date, nulls last, then received timestamp, then batch ID. With `fifo`, the expiry term is null and order is received timestamp then batch ID. The same order is used for actual allocations. Thus it is a policy-specific FEFO or FIFO **after eligibility**, not a universal rule that the earliest physical card is always usable. Standard non-batch items deduct aggregate stock. [allocation SQL](../supabase/migrations/20261004170254_fifo_batch_aware_sales_consumption.sql#L714), [allocation loop](../supabase/migrations/20261004170254_fifo_batch_aware_sales_consumption.sql#L802).

The detail read returns positive physical batches in policy order and marks `expired` only when expiry is required. **It does not filter expired rows from the list.** The current card shows code, quantity, receipt and use-by date, and status; the header says “Earliest use-by first” or “Oldest receipt first.” An expired FEFO batch can therefore appear before a current one in the list, while the order allocator excludes it. This is a source-supported risk of misreading order as use priority; no wrong physical pick or live incident was observed. [detail SQL](../supabase/migrations/20261005082921_manager_inventory_workspace_reads.sql#L99), [batch card](../src/modules/manager/inventory/InventoryBatchList.tsx#L5).

**Proposed Batch Rotation Priority presentation:** On the existing item detail, show ingredient, batch code, positive balance, use-by date if recorded, eligibility, rank, and the exact server policy explanation. Visually separate excluded expired rows; label the first eligible row “Next for confirmed-order allocation” and clarify this is **system order allocation guidance**, not proof of physical suitability or an instruction to manually issue stock. Link to authorized Waste, Adjustment, and Movements actions. Do not implement a client-only rank from an independently sorted array: use the existing server-ordered detail only after confirming it exactly matches the current allocator in a fresh local source/SQL review, or add an authoritative read projection if this relationship changes. Physical quality, reserved stock, and any location restriction are not proven by this read. The actual order deduction is automatic in `deduct_inventory_for_confirmed_order`; Manager waste/adjustment/Receiving are separate authorized actions. [SQL comment](../supabase/migrations/20261004170254_fifo_batch_aware_sales_consumption.sql#L877).

## F. Proposed task-oriented Inventory structure

Current sidebar: **Stock / Requests / Receiving / Stock Movements / Waste / Spoilage / Adjustments / Inventory Audit**. These are seven separate entries beneath Inventory. Proposed grouping below is **information architecture only**, not implemented or authorized to rewrite.

| Proposed group | Reuse mounted page/service | Gap, benefit, and dependency |
|---|---|---|
| Inventory Overview | Stock summary and dashboard count; stock/proposal reads | Put action counts and links together. Navigation/presentation only if sourced from existing reads; no new “urgent” policy. |
| Stock & Batches | Stock + item detail + batch list; summary/detail RPCs | Next-eligible label and explanation. Existing ordered read may support a narrow presentation; dedicated authoritative rank requires backend if current contract cannot guarantee it. |
| Requests & Replenishment | Requests, formal request API, historical queue | Keep two workflows visibly separate; add state-based links. Frontend grouping only; no supplier integration. |
| Receiving | Receiving and document list/workspace/post RPCs | Draft inspection and post consequence in one flow. Presentation only for existing fields; structured damage classifications require policy/schema. |
| Movements & Corrections | Stock Movements, Waste, Adjustments, Audit | Put investigation before correction. Navigation/presentation only; physical-count records or ranked waste analytics need backend/evidence. |

The grouping preserves Manager authorization and server write boundaries. It reduces the need to choose among seven sibling technical labels before knowing the task.
