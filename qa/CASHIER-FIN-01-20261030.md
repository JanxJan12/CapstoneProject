# CASHIER-FIN-01 — Cash drawer and settlement contract reconciliation

**Date:** 30 October 2026 (Asia/Manila). **Scope:** read-only hosted inspection, source review, isolated synthetic scenarios, and Cashier-only wording. No hosted financial operation, migration, schema, RLS, RPC, or Manager calculation was changed.

## Executive decision

**Do not change `close_cashier_shift` or the current Cashier calculation now.** The apparent refund mismatch from OPT-05 is a latent disagreement between a legacy client `Refunded` branch and the active database contract, not evidence of an incorrect hosted settlement. Hosted `cashier_transaction_status` permits only `completed` and `voided`. The deployed Manager cancellation RPC records a **completed, Manager-attested full refund**, voids the original payment and receipt, and requires the original shift to remain open for a cash refund. Both current calculations then exclude that receipt. Current hosted data has zero paid cancellations/voided receipts, 42 completed receipts all linked to verified payments, and five closed shifts whose saved expected cash equals opening plus current completed verified cash. The active shift's independent read-only projection is **₱4,000 opening + ₱1,585 cash = ₱5,585**; it has no saved closing amount.

This does **not** prove a physical drawer was correct. The schema does not record an independent physical cash payout, drawer movement, or the drawer that supplied a Manager-attested refund. The existing cash-refund restriction assumes the original open shift's drawer bears the payout. If restaurant practice differs, a new cash-movement contract and policy are needed. A browser refresh/Realtime delay and the current-shift read RPC's lack of a verified-payment predicate are residual ways the estimate could temporarily differ from closure. The 23 synthetic scenarios reproduce these boundaries; the actual financial RPCs were not executed in this run because the disposable Docker engine was unavailable.

Cash tender is not sale revenue; change is tender less amount. Pending/rejected are not collected cash. |

| Paid refund/cancellation | Manager `PaidOrderCancellationPanel` → `settle_paid_order_cancellation`. | Active Manager only; full verified payment equal to order total, one completed receipt, original method, reason/reference and confirmed **already returned** money. Hydration requires both the Cashier ID and their open `shift_id`, and completed receipt status, but does **not** predicate payment `verified`; closure uses shift ID and verified payment status. GCash is reported separately. A second close finds no open shift. Closed history reads stored snapshot, not current receipts. |
| Manager report | `get_manager_sales_report` (and dashboard RPC). | Sums currently verified payment amounts for successfully fulfilled orders in Manila fulfillment-date range. Current voided paid cancellations drop out; this is not drawer cash or an immutable gross/net journal. No standalone approved net-sales or refund-period metric exists. |

Hosted catalog inspection confirmed the cited numeric types, FK/unique relationships, payment and transaction enums, one-open-shift-per-cashier and per-terminal indexes, function execute ACLs (authenticated yes, anon no), and SECURITY DEFINER role checks in the inspected close/refund definitions. The hosted refund and close function definitions were inspected, not called. The Cashier history RPC is a saved-snapshot read. A status-history event records cancellation actor; the cancellation row records Manager actor and time. Cashier transaction history can show a voided receipt, but its `Refunded` summary/status is legacy compatibility, not a count of Manager refund attestations.

## Findings, decision matrix and correction plan

| Class / severity | Finding and impact | Decision |
|---|---|---|
| **B — Medium** presentation | OPT-05 showed a zero “Refunds”/“Cash refunds” line as if it were a ledger of physical payouts. Active hydrator never produces `Refunded`; Manager refunds void receipts. | **Implemented Cashier-only wording:** open drawer is a receipt-based estimate; zero legacy refund rows are hidden; nonzero legacy rows are explicitly identified as local classification, not physical payout evidence. No formula changed. |
| **C + D — High** model/policy | A Manager-attested cash refund must target an original open shift but records no payout drawer or independent outflow. If money comes from another drawer, neither source computes that drawer correctly. | Restaurant must confirm same-drawer cash-refund procedure or approve an append-only cash-movement contract. Do not change closure formula until policy and operational evidence exist. |
| **E — Medium** stale/inconsistent input | Current-shift hydrator reads completed receipts without checking payment verified and requires receipt Cashier ID; closure requires verified and uses shift ID. Realtime refresh may lag or fail. Case 22 reproduces conditional divergence; hosted aggregate has zero such rows and zero cross-Cashier shift receipts. | Keep backend authority; consider a separately reviewed read-model alignment and explicit refresh/freshness state. No client formula/predicate change in FIN-01. |
| **E — Low** legacy local branch | Case 21 reproduces subtraction in a `Refunded` local row that hosted enum cannot store. | Preserve compatibility; do not treat it as live financial defect or rewrite historical data. |
| **E — Medium** history protection | Hosted has no noninternal `cashier_shifts` trigger or snapshot-protection function; authenticated role lacks direct UPDATE/DELETE grants and close targets open only. | Separate database security review if stronger protection against privileged/internal writes is required. No historical row changed. |

**Recommended current contract:** call the active figure a *receipt-based expected cash estimate*; call the saved figure *server-recorded expected cash at closure*. Count physical drawer cash separately. GCash remains outside expected cash. A Manager refund is a full, already-executed refund attestation that voids the original current payment/receipt; it is not a second negative transaction. Transaction History's completed receipt total and Manager's verified fulfilled revenue are separate measures. Do not label either a generally approved “net sales” total.

**If the restaurant confirms refunds can leave a different drawer, post-close cash refunds are needed, or cash drops/paid-outs occur:** propose a separately authorized append-only `cash_drawer_movements` contract, with immutable movement ID, exact shift/terminal identity, signed numeric(12,2) amount, movement type, linked cancellation/payment/receipt, performed-by and occurred-at, and idempotency key. Manager refund and movement recording must be one transaction or otherwise guarantee a recoverable outcome; close must lock the relevant shift and sum only movements for that shift exactly once. Preserve existing completed/verified receipt sum and add authorized movement sum; do not backfill historical cash movements from voids without evidence. Expose role-scoped read access and an audit trail. Validate cash refund in same/different shift, concurrent close/refund, replay, post-close policy, GCash, partial refunds if approved, RLS/ACLs, and Manager reporting. Roll back by disabling new movement-writing workflows before closure-formula cutover; retain append-only records and never rewrite old shift snapshots. This is an **implementation specification, not an authorized migration**.
