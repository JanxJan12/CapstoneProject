# Production / formal Manager request integration assessment

**Date:** 2026-10-14. **Scope:** current worktree and the new isolated slot 3 only. Hosted Supabase was not changed. This is an evidence-backed design proposal, not an implementation or a new business approval policy. It continues the [inconsistency register](FULLSTACK-INCONSISTENCY-REGISTER.md) H-06 and [workflow architecture](FULLSTACK-WORKFLOW-ARCHITECTURE.md), without reopening the 34-table normalization work.

> **Decision update, 2026-10-14:** The restaurant owner confirmed model **A**. Formal Manager requests remain externally dispatched; no in-app formal Production queue or Production-role access to formal requests will be added. The former model B recommendation and implementation proposal below are retained only as historical analysis and are **not an active plan**. Current traceability work is in [External formal request traceability](EXTERNAL-FORMAL-REQUEST-TRACEABILITY.md).

## Decision

**Recommend model B as the target operating architecture if the restaurant owner wants Production to work in the application.** Keep `inventory_request_documents.id` / `request_number` and `current_revision` as the only formal request identity. Add a narrow Production projection and, only after the owner defines actions, audited Production-specific event transitions. Keep the Phase 7B queue exclusively for historical requests. No second formal request row or stock writer is needed.

**Model A remains the currently executable process and the safe interim choice.** The Manager exports a revision and transmits it externally; optional Manager attestations record dispatch or a response. Production completes only historical Phase 7B items in its in-app queue. A frontline user cannot currently see formal requests in `/production`. Model B **cannot be implemented solely with existing executable database contracts**: the available formal register and event RPCs require an active Manager, and the formal event/status vocabulary has no Production preparing/ready actions. A read-only Production view alone needs an approved permission/RPC migration. This assessment authorizes no migration.

## Capability and state matrix

| Question | Current result |
| --- | --- |
| Can Production access the formal request? | **No through the current UI or RPC.** `/production` loads only `get_replenishment_requests`. Formal tables have RLS enabled with direct `authenticated` table privileges revoked. `get_inventory_request_register` calls `inventory_request_manager_required()`. In the isolated slot, the synthetic Production role received HTTP 403 from that RPC and `get_receiving_policy_evidence`; navigating to `/manager` redirected to `/production`. |
| Can Production distinguish issued/revised/acknowledged/preparing/ready/partial/closed formal documents? | **No in the current UI.** `inventory_request_documents.status` has `issued`, `partially_received`, `fulfilled`, `closed_short`. `inventory_request_revisions` and `issued`/`revised` events distinguish revisions. `dispatch` and `acknowledgment` events can show Manager-recorded external handoff for a revision. There is no formal `preparing` or `ready` state/event and no Production actor transition RPC. |
| Do events already cover some states? | **Yes:** `issued`, `revised`, `dispatch`, `acknowledgment`, `delivery_started`, `delivery_cancelled`, `delivery_posted`, `closed_short`. They carry revision and actor. “Acknowledgment” is currently a Manager attestation of an external response, not a Production sign-off. |
| Does frontend show status/revision truthfully? | **Manager yes within current contract:** current revision, previous snapshots, current-revision sent/reply badges, document fulfillment status, receipts and event history. **Production no:** its labels and buttons refer only to the legacy queue. It explicitly says formal requests use a separate document. |
| Can frontend-only work implement full integration? | **No.** Reusing `get_inventory_request_register` from Production fails the Manager guard and would expose a broad Manager projection if opened indiscriminately. Formal prepare/ready actions have no authorized RPC or agreed state semantics. |

## Models compared

| Model | Practical benefits | Cost / risk | Recommendation |
| --- | --- | --- | --- |
| **A — external formal document; in-app Production queue historical only** | Already works with current role contracts; preserves Messenger handoff and avoids migration before release gates. Clear separation from the Phase 7B queue. | Production cannot verify current revision or request status in-app. Manager-entered “reply” can be mistaken for a Production acknowledgment; external transmission/revision supersession requires disciplined operations. | Retain as interim process and label it explicitly in training and UI. |
| **B — formal documents visible/actionable to Production** | Shared numbered/revisioned identity, current-line visibility and audit trail; less manual handoff ambiguity. Existing document, revision, event and Receiving link tables can be reused. | Requires narrowly scoped backend authorization and an owner-defined formal Production action model; incorrect reuse of legacy transitions could create two competing statuses. Broader register access could expose Manager-only data. | Target architecture **after** owner decisions and controlled migration/recovery gates. Start with read-only projection, then add approved actions. |

## Minimal feasible implementation proposal — no execution

1. **Decide the role workflow.** The owner defines whether Messenger remains required, whether an in-app view itself counts as dispatch, who may acknowledge or mark preparing/ready, how revisions invalidate prior acknowledgments, and what “ready” means before physical delivery. Keep `issued` and stock posting independent; do not infer an approval gate from current events.
2. **Add a limited Production read contract** over the existing formal tables after separate migration approval: current `request_id`, `request_number`, `current_revision`, current snapshot/lines, needed time, priority, fulfillment status, revision-aware event summary and receipt summary. Enforce active Production role inside a `SECURITY DEFINER` function and grant only its execute privilege. Do not grant direct table access or simply weaken `inventory_request_manager_required()` on the broad Manager register.
3. **If actions are approved, add a revision-checked, idempotent formal Production event RPC** with active Production actor identity and explicit allowed transitions. Extend the event vocabulary only as needed by owner-approved semantics. Keep delivery/Receiving and fulfillment status owned by the existing Manager Receiving path. No new formal request table or legacy request mirror.
4. **Add a separate formal-document section/tab in `/production`** that reads the new projection, visibly shows revision and state, refreshes after actions, and leaves `ProductionQueuePage`’s historical cards and `advance_replenishment_request` behavior intact. Preserve historical finalization and label the two families.
5. **Link back by existing FK.** Manager opens a linked `receiving_reports` draft through `start_inventory_request_receiving`; post through `post_receiving_report`. Display the same `request_number`/revision and posted acceptance balances. Do not create a second request or a stock movement on Production action, dispatch, acknowledgment or draft opening.

The read-only projection requires a new migration/permission change. Formal Production actions require a later migration or approved expansion of event types/RPC behavior. Neither is part of this task; the original 51 files remain intact. For a read-only projection, rollback would revoke/drop only the additive RPC after client rollback. For action events, rollback must retain already written audit history and define a forward-compatible consumer or reviewed restore path; it cannot erase events. No hosted deployment until the existing replay/recovery and approval gates are met.

## Compatibility, security and regression gates

- **Identity and revision:** current revision only for new action; stale revision rejection; immutable previous snapshots; concurrent Manager revision and Production action; no revision after a linked receipt; events always carry actor and revision. Never treat a prior-revision acknowledgment as current.
- **Role security:** Production can see only the approved projection and take only approved actions; Manager remains issuer/Receiving poster; inactive/anonymous/Customer/Cashier/Rider roles denied; direct formal-table access remains denied. Avoid leaking private records, recipes or unrelated Manager notes through a broad register.
- **Legacy coexistence:** Phase 7B requests remain readable and finishable with their own transitions and one-report Receiving link. No new normal legacy request creation, no conversion/mirroring of historical rows, and no duplicate queue card for one formal document.
- **Receiving/stock:** formal FK and revision are stable, one open linked draft at a time, line inventory IDs match request lines, accepted posted quantities stay within requested quantities, partial/full/short closure remains authoritative, and opening/refreshing/action events leave batch, aggregate stock and movement ledger unchanged. Only `post_receiving_report` adds accepted stock.
- **Failure behavior:** loading/empty/error/retry states, lost connection, duplicate click/retry IDs, stale status, out-of-order events, and mismatch between external Messenger response and in-app actor state. Run browser role tests plus same-database API/RPC tests in a newly isolated synthetic stack before any hosted acceptance.
- **Release boundary:** local source/build/synthetic browser evidence is distinct from hosted parity. The hosted policy RPC mismatch and migration/DR NO-GO findings in the existing reports remain unresolved.

## Restaurant-owner decisions needed

1. Should formal requests stay Messenger-only, or should Production see and act on them in-app? If both, which action is the authoritative acknowledgment?
2. Must a revised request be resent and explicitly reacknowledged, and by whom? What happens to work already preparing when revision occurs?
3. Are “preparing” and “ready” needed for formal documents, and what staff role may assert each? Is a Manager dispatch attestation still required?
4. Which fields may Production see, including Manager reason, issuer identity and event details? What retention/audit record is required for external communication?
5. How should a short delivery, cancellation and closure be communicated to Production without implying stock moved before Manager posting?

**Conclusion:** Existing tables provide a sound formal document identity, revision history, event trail and Receiving FK. **Existing permissions/RPCs do not allow a Production integration today.** Model B is feasible as an additive, narrowly authorized workflow after owner decisions; model A remains the current operating contract.
