# CASHIER-SS-01 — Shift Settlement investigation

**Date:** 30 October 2026 (Asia/Manila). **Scope:** read-only active-source, prior-QA, hosted catalog/aggregate, and local regression review. **Decision:** preserve the server-authoritative settlement contract; simplify the Cashier workflow in a later SS-02 only after the stated policy questions are answered. No application code, database object, migration, financial contract, or hosted business record was changed.

## Executive summary

Shift Settlement supports the essential sequence: the active Cashier opens one shift with terminal and float, takes sales, sees a provisional receipt-based cash estimate, counts the physical drawer, reviews any variance, confirms closure, and later retrieves the saved settlement. `close_cashier_shift` recomputes the final expected amount from **verified, completed Cash payments on that exact shift**; it does not trust the browser's expected amount or a client-supplied shift ID. GCash is separate. A restaurant-wide pending online GCash payment blocks closure through a serialized server check. Closed shifts store expected, counted, variance, notes, reason, timestamps, and closing actor as snapshots.

Current read-only hosted aggregates show **one open and five closed shifts**, **one pending online GCash payment**, **zero** mismatched transaction/shift owners, **zero** completed receipts linked to unverified payment, and **zero** invalid closed variance snapshots. The open shift had reached about **236 hours at query time**. These are point-in-time observations, not an instruction to close or repair it. Local logic tests pass. No current hosted closure, cross-Cashier authenticated run, actual drawer count, or physical refund payout was executed. There is no demonstrated hosted settlement formula error. The main unresolved financial requirement is whether cash refunds, drops, or paid-outs can come from a different drawer; the database currently records no independent physical cash movement.

The Dashboard has another end-shift entry point using the same action. `services/shiftService.ts` computes the browser estimate. `ShiftAuditTable` and `ShiftReportDialog` exist in source but are **not mounted by the active Shift Settlement page**; their copy and print path are not current-workspace behavior. A Manager route separately reuses `ClosedShiftHistory manager`.

## Financial source-of-truth map

| Metric | Authority, formula, inclusion/exclusion, precision | UI and historical meaning / risk |
| --- | --- | --- |
| Opening cash | `cashier_shifts.opening_cash numeric(12,2)` entered at start, nonnegative. | Fixed shift fact. The dialog's ₱4,000 default is UI convenience, not a verified float. |
| Cash / GCash receipts | `cashier_transactions.shift_id` → linked `payments.amount numeric(10,2)`; server counts `t.status=completed AND p.status=verified`, split by payment method. One transaction has one payment ID and shift FK. | Cash belongs in expected drawer; GCash does not. Tender `cash_received` is not sales revenue and change must not be added. Current-shift UI counts completed hydrated transactions; that estimate may be stale or include an inconsistent unverified record. |
| Voids and refunds | Voided transactions excluded from completed server sums; Manager full paid cancellation separately records `paid_order_cancellations` and voids original payment/receipt. | A void is not itself a physical payout record. The legacy local `Refunded` branch cannot arise from hosted transaction enum (`completed`,`voided`) today. No independent cash paid-out/drop table exists. |
| Expected cash | Open browser: `opening + completed Cash − legacy locally classified Cash refunds`. Server final: `round(opening + verified completed Cash, 2)` under locked own shift. | Browser explicitly says estimate; saved `cashier_shifts.expected_cash numeric(12,2)` is closure authority. Other shifts and GCash excluded. Current hosted data has no supported mismatch condition. |
| Actual cash | `p_actual_cash` entered from physical count; server finite/nonnegative and rounds to 2 decimals; saved `actual_cash numeric(12,2)`. | The count is an attestation by Cashier, not an automated sensor; no denomination capture. Optional notes do not prove a payout. |
| Variance | Server saves `round(actual−expected,2)` and requires nonempty reason when nonzero; zero clears reason. | Positive = over, negative = short; no automatic tolerance or Manager approval. Browser preview uses estimate and may differ at commit time. Saved `variance`, `variance_reason`, `notes`, `closed_by`, `ended_at` are closure snapshot fields. |
| Transaction counts/discounts | Open UI derives count, discounts and void amount from hydrated shift transactions; close RPC returns completed+verified transaction count and split totals but stores only expected/actual/variance, not as-closed Cash/GCash components. | A historical row cannot reconstruct exact as-closed component mix from today’s mutable receipts. Do not label a current re-sum as old audit fact. |
| Manager revenue | `get_manager_sales_report` uses restaurant-wide verified payment on successfully fulfilled orders by fulfillment date. | Different population/time axis from a Cashier shift's payment collections. A paid unfulfilled order can be in the drawer estimate yet absent from fulfilled revenue. |

### Proposed CASHIER-SS-02 implementation scope, in priority order

1. **P2, Cashier UI only:** require a deliberate opening-float entry/confirmation and explain the supplied float and terminal. Preserve `start_cashier_shift` and its backend validation. This removes the unsubstantiated ₱4,000 prefill only after the owner confirms the handoff practice; it does not set a new default amount.
2. **P2, Cashier UI only:** clarify the restaurant-wide pending-payment blocker, provide a direct Pending Payments path and an escalation message for a request this Cashier cannot resolve. Keep server closure eligibility unchanged.
3. **P2, Cashier UI only:** improve stale-estimate, committed-but-response-lost, and server variance-reason recovery copy. Re-read the own open/saved shift before a retry; retain the server's final calculation.
4. **P3, Cashier UI only:** simplify the count/review hierarchy and put component totals in expandable details. Preserve exact/short/over, reason, notes, and all validation.
5. **Verification gate:** disposable direct-RPC owner/role, duplicate terminal, pending-payment race, close retry, and concurrent receipt/refund scenarios; current signed-in desktop/mobile Cashier and Manager read screens; keyboard/count inputs; saved closure after receipt changes. Label physical drawer and printer evidence separately.

**Separate owner decisions before financial or authorization changes:** Who assigns and verifies the terminal and opening float? Can a Cashier use another terminal? May a shift cross days, and who resolves an old pending online payment? Do cash refunds, drops, or paid-outs leave the same drawer, and who attests the movement? Does a discrepancy require Manager approval or a denomination count? Must the closed snapshot store as-closed Cash/GCash components? None of these policies is established by the current columns or UI. SS-02 should not add schema/RPC changes, alter hosted records, or auto-close an old shift on the strength of this report.

## Proposed target workflow and SS-02 boundary

1. Cashier enters Shift Settlement and sees *their* active shift, terminal, start time, age warning, expected **estimate**, and whether closure is blocked. Existing behavior.
2. If no shift exists, Cashier enters a deliberately checked opening float and available terminal. Existing RPC; SS-02 can remove the unsubstantiated ₱4,000 prefill and explain who supplied the float after policy confirmation. Duplicate/start-retry errors should guide refresh to own active shift.
3. Cashier reviews opening + completed Cash receipt components; GCash stays separate. Existing source. SS-02 may collapse secondary metrics, preserving access to audit facts.
4. If pending online GCash blocks closure, Cashier follows Review Payments or escalates an inaccessible/stale case. Existing link; escalation path needs restaurant decision. Do not bypass the server guard.
5. Cashier counts physical cash, enters a two-decimal nonnegative amount, sees exact/short/over against the estimate, selects a reason for a discrepancy, optionally records notes, and reviews. Existing behavior; no tolerance/approval rule added.
6. Cashier confirms once. Server locks own shift, checks pending payments and verified receipts, saves its final expected/count/variance. On stale/rejected RPC result, dialog shows error; recheck shift and count. On uncertain network result, read own open shift and saved history before retrying. Existing authority, proposed clearer recovery copy.
7. Cashier views persisted closed snapshot in Saved closed shifts, filtered by Manila closure date, with expandable notes/audit IDs. Existing behavior. Never replace it with a live recomputation.

Alternative flows: **exact balance** saves zero variance with no reason; **short/over** saves signed variance with reason; **long shift** warns but remains valid until authorized close; **no active shift** offers Start; **unauthorized/other shift** is rejected by role/owner checks; **pending payment** blocks close restaurant-wide; **stale estimate or RPC failure** requires review/refresh and a possible server-required variance reason; **historical lookup** reads own saved rows without opening a new shift. These paths require browser and isolated-RPC acceptance before production claims.
