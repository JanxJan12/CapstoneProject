# CASHIER-DATA-01B — predeployment Cashier History read review

**Date:** 30 October 2026, Asia/Manila. **Decision: NO-GO for the prepared migration as written.** This was a read-only hosted review and disposable local test. The hosted function does not exist, and no hosted schema or data was changed. The migration and Cashier application code were left untouched.

## Scope and evidence

Reviewed `supabase/migrations/20261030034730_cashier_owned_transaction_history_read.sql`, `qa/CASHIER-DATA-01-20261030.md`, the active `historyReadApi.ts` / `useTransactionHistory.ts` / filters / page, hosted `profiles`, `cashier_transactions`, `cashier_shifts`, `orders`, `payments`, related enums, RLS policies, grants, indexes, foreign keys, and the existing `get_cashier_sale` and `get_current_shift_cashier_sales` definitions. Hosted inspection used catalog queries and counts only. At inspection, the target RPC and migration-history entry were absent. The hosted sample contained 42 transactions and six shifts, with transactions belonging to one cashier; it cannot prove cross-cashier isolation in production.

## Findings and checklist

| Check | Result | Evidence / consequence |
| --- | --- | --- |
| Hosted column, enum, and join compatibility | **PASS** | All referenced columns exist with compatible types. Hosted enums contain `cashier`, `completed`, `voided`, `cash`, and `gcash`. Transaction order, payment, shift, and cashier links have foreign keys. |
| Cashier-only authorization and receipt isolation by SQL predicate | **PASS locally; NOT RUN hosted** | The function checks `auth.uid()` against an active Cashier profile, then requires both transaction and shift cashier IDs to equal that UID. Disposable tests denied inactive and anonymous callers and excluded the other cashier's receipt. Hosted authenticated A/B calls are pending deployment; hosted data currently has only one cashier with transactions. |
| Function privilege and definer setup | **PASS locally; BLOCKED hosted** | `SECURITY DEFINER` is needed because hosted `payments` has no Cashier direct SELECT policy. The function has `search_path = ''`, schema-qualified relations, `PUBLIC` execute revoked, and `authenticated` execute granted. Disposable `has_function_privilege` returned anon=false, authenticated=true. Deployment must use an owner with SELECT on all joined tables; inspect the actual owner and ACL after deployment. |
| Page bound | **FAIL** | `if p_limit < 1 or p_limit > 100 ...` does not reject SQL `NULL`. PostgreSQL treats `LIMIT NULL` as no limit. In disposable PostgreSQL 17, `get_cashier_transaction_history(NULL,0,'{}')` returned both matching rows while the normal limit-1 call returned one. Any authenticated Cashier can call the RPC directly, so the advertised at-most-100 server cap is not enforced. `p_offset = NULL` also bypasses validation and acts like zero. |
| Row order and filter/count population | **PASS locally** | `created_at DESC, id DESC` is deterministic, including timestamp ties; count and page use the same filtered CTE. The disposable fixture passed status, method, search, receipt, voided, fee, and page checks. Invalid date/UUID casts fail closed. Wildcards in text filters can broaden a search within the caller's own rows. |
| No open shift / closed shift | **PASS locally; NOT RUN hosted UI** | SQL does not require an open shift. The disposable test returned two historical rows from a closed shift when the cashier had no open shift. |
| Screen and CSV population | **PASS by code/fixture; NOT RUN hosted** | Screen uses 50-row pages; CSV calls the same RPC with the same mapped filters, requests 100-row pages, and refuses totals above 5,000. The code checks row ownership and total stability. Equal-count insert/delete or reorder between CSV page calls can still duplicate or omit rows; there is no snapshot cursor. The Cashier selector only offers the signed-in cashier and is intentionally omitted from the server filter. |
| Hosted cost and indexes | **NOT RUN performance timing; REVIEW as volume grows** | Hosted has 42 transaction rows. There is no index on `(cashier_id, created_at DESC, id DESC)`, so a growing history could require a sort and full scan for each page/count. This review did not run a production `EXPLAIN ANALYZE` or add an index. |
| Existing RPC compatibility | **PASS by definition; NOT RUN browser** | New name/signature does not replace `get_cashier_sale` or `get_current_shift_cashier_sales`. History detail still uses own-sale RPC and validates transaction/payment/shift links. The active History UI has no broad-read fallback when the new RPC is missing, so it cannot pass hosted runtime acceptance until a separately approved deployment. |
| Migration-history safety and rollback | **BLOCKED pending corrected SQL and authorization** | Hosted history is divergent from local history. Apply only the exact reviewed migration, never an unscoped `supabase db push`. This function is currently absent, so database rollback would be `DROP FUNCTION public.get_cashier_transaction_history(integer, integer, jsonb)` after reverting the dependent frontend; dropping it while the frontend is active would break History. Recheck dependencies and migration bookkeeping at deployment time. |
| Authenticated browser, receipt preview/print, and hosted CSV | **NOT RUN** | The prior browser target was unreliable, and this review made no hosted runtime call or business transaction. |

## Required correction and bounded deployment proposal

1. Before seeking deployment approval, change the prepared function's page guard to reject nulls explicitly: `p_limit IS NULL OR p_offset IS NULL OR p_limit < 1 OR p_limit > 100 OR p_offset < 0 OR p_offset > 10000`. Keep the existing ownership predicates, qualified names, grant, and search path. Add disposable assertions that null, zero, 101, negative, and over-10,000 page inputs fail with `22023`, then rerun all checks above. This is a proposed change; it was **not** made in this review.
2. Reconfirm the hosted function is absent and the referenced schema, enum, ACL, and migration state have not drifted. Record the exact reviewed SQL hash and a rollback copy. Review the expected future row volume and decide whether a separate index is needed; do not combine unrelated migrations.
3. After **separate explicit authorization**, apply only `20261030034730_cashier_owned_transaction_history_read.sql` to hosted Supabase using a migration-aware, bounded operation. Verify its owner, `SECURITY DEFINER`, empty search path, `PUBLIC`/anon denial, authenticated grant, and migration-history entry. Do not run an unscoped migration push.
4. With authorized test accounts, verify Cashier A/B isolation, inactive/anonymous denial, closed/no-open shifts, page order and bounds, filter/count/CSV parity, selected detail/reprint, and responsive print. Use reversible test data only if separately authorized. If verification fails, revert the frontend that requires the RPC, then drop only this function and correct its migration bookkeeping using the same bounded deployment channel.

The current go/no-go gate is the null-limit failure. Passing local checks after the correction would make this **eligible for a separate deployment approval**, not a claim of hosted acceptance.
