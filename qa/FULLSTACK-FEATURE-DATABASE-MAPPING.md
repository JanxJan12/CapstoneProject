# Full-stack feature → database mapping

**H-09 continuation (2026-10-15):** The focused [ordering map](H09-ORDER-FLOW-DATABASE-MAPPING.md) traces Customer → Cashier → Kitchen → Rider and distinguishes current source contracts from hosted parity. The saved-cart Checkout timing guard is a frontend change only; it does not alter server price, snapshot, payment, or stock authority. Fresh synthetic API/Customer Chrome proof passed in [H-09 regression](H09-ORDER-FLOW-REGRESSION.md); broader browser and hosted acceptance remain open.

**Snapshot:** 2026-10-14. This is an active-route inventory of the canonical React app and standalone Rider `App.tsx`, not an inventory of every file in the repositories. `src/app/routes.tsx` mounts `/auth`, `/authenticating`, `/customer`, `/cashier`, `/kitchen`, `/rider`, `/manager`, and `/production`. Manager and Cashier child pages are state-selected within their mounted module. Rider Android has four `App.tsx` tabs. Table/column groups below identify the business fields used by the projection or writer; an RPC can internally read additional tables. Status is based on source wiring and the dated [defense rehearsal](DEFENSE-DEMO-READINESS-20261014.md), not on an unperformed hosted UI test.

**Classification key:** `V` connected and verified for the named *isolated local* path; `C` connected, further scenario testing needed; `I` connected with a confirmed inconsistency; `R` intentionally read-only/derived; `L` legacy/dormant; `U` UI-only/disconnected. A source-connected row does not mean its active RPC exists on hosted. Auth gating in `RequireAuth` and SQL role/ownership checks are separate controls.

## Production and compatibility inventory

`/production` mounts only `ProductionQueuePage`: active/closed/all search; historical single-item item/quantity/priority/status/event history; acknowledge → prepare → ready. It calls `get_replenishment_requests` and `advance_replenishment_request` against `production_replenishment_requests` and events. Only Manager Receiving can close/post accepted stock. This page intentionally finishes Phase 7B requests and does **not** display the newer formal Manager request register; the printed/sent formal document is an external Production handoff. Classification `L` for historical queue, still live and connected. The embedded Manager `ReplenishmentPage` is the corresponding historical view. `PurchaseOrdersPage.tsx` imports `prototypePurchaseOrders` but is absent from active Manager navigation: `U/L`, not a production purchase-order UI. Database `purchase_orders` and `purchase_order_items` remain legitimate Receiving compatibility records, and the direct-supplier branch remains conditionally connected in Receiving.

## Distinct records and authority

| Records | Why both exist / source of truth |
| --- | --- |
| `payments` / `cashier_transactions` | Payment submission, method, proof and verification versus Cashier receipt/shift journal. Reconcile by order/payment identity; do not infer one table is redundant. |
| `orders.current_status` / `order_status_history` | Fast current projection versus append-only transitions. Current order state controls screens; history explains how it got there. |
| `inventory_items.quantity_on_hand` / `inventory_batches.quantity_on_hand` / `inventory_transactions` | Item aggregate, physical lot balance and movement journal have different grains. Allocation rows link a movement to consumed batches. Audit compares them without treating a bounded client history as complete. |
| Formal `inventory_requests` / `production_replenishment_requests` | Versioned multi-line Manager document/external dispatch versus historical single-item Production state queue. Receiving can link either but cannot merge their identities. |
| Receiving draft / posted report | Draft records inspection only. `post_receiving_report(uuid)` is the accepted-stock boundary and owns item/batch/movement effects. |
| Current `menu_items.price` / `order_items.unit_price` | Today's catalog versus sold-time snapshot; historical receipts/reports must keep purchase-time price and modifiers. |
| `kds_terminals` / kitchen queue | Device credential authorizes reads/transitions; order status and items form the queue. The terminal is not a queue row or individual kitchen user. |
| `delivery_assignments` / private `delivery-proofs` bytes | Assignment/status/proof path is relational metadata; the private object is evidence and must be verified separately in recovery. |

**Evidence limits:** prior local demonstration verifies selected end-to-end paths, not every button or condition above. Hosted relationship checks covered 16 populated predicates and 16 empty branches. Read-only hosted catalog inspection this phase found `get_customer_menu_modifiers`, `get_kds_queue_v2`, `get_receiving_policy_evidence`, `get_receiving_policy_classes` and `create_emergency_production_receiving` absent. No hosted feature was exercised or changed.
