## 3. Exact deployed object inventory and dependencies

`pg_trigger`, `pg_proc`, `pg_policy`, `pg_class`, privilege, `pg_depend`, migration-ledger and Edge Function queries were read from hosted. All four named triggers are enabled (`tgenabled='O'`), BEFORE UPDATE FOR EACH ROW, without visible WHEN clauses, and call the **same** `public.set_updated_at()` object. That PostgreSQL-owned, invoker-mode PL/pgSQL trigger function has `search_path=''`; its body is only `NEW.updated_at = now(); RETURN NEW;`. It changes no other column, audit row or related record. Trigger names sort so the unprefixed trigger runs before `trg_`; both assign the same transaction timestamp, making the second assignment idempotent. The function remains necessary after either drop and is **not** proposed for deletion. Both tables also have other business relationships, so the trigger decision is shared across Auth/Customer/Cashier/Manager and Rider, not Cashier-only.

The same `set_updated_at()` function has **15** hosted trigger callers, including **11** on other tables; after the proposed pair of drops it would still have **13**. It cannot become orphaned from this batch.

`public.profiles` has RLS enabled, not FORCE RLS. Its complete policy set is:

| Policy | Command, role, mode | Deployed predicate |
| --- | --- | --- |
| `managers_view_profiles` | SELECT, authenticated, permissive | `current_user_role() = 'manager'::user_role` |
| `profiles_select_own` | SELECT, authenticated, permissive | `(SELECT auth.uid()) = id` |
| `profiles_view_own` | SELECT, authenticated, permissive | `id = (SELECT auth.uid())` |
| `profiles_update_own` | UPDATE, authenticated, permissive | own-id USING and WITH CHECK |

The two own-id SELECT expressions are commutative equality on the same UUID operands; both give NULL/false without a claim. SELECT policies combine by OR, so removing one duplicate leaves `own OR manager` unchanged. `current_user_role()` is a SECURITY DEFINER, stable, empty-search-path SQL function reading the caller's active profile and returning its `user_role`; inactive users get NULL from that helper. The inactive user's direct own-profile SELECT is nevertheless still allowed by both before and after policy configurations. This is current deployed behavior, not a recommendation to change it. Authenticated has table SELECT; anon has no table SELECT grant. Authenticated has column-level UPDATE only on `contact_number` among profile columns; the update policy still applies. The retained own policy and manager policy are necessary. The manager policy allows reading inactive/other profiles and must remain.

The legacy RPC has exactly one deployed overload: `public.get_current_shift_walk_in_sales() RETURNS jsonb`, owned by `postgres`, PL/pgSQL, SECURITY DEFINER, `search_path=public, pg_temp`. It authorizes an active Cashier via `auth.uid()` and `profiles`, selects the current open shift, and builds JSON for walk-in transactions with order/items/payment/transaction/history. `authenticated` can EXECUTE; `anon` cannot. `pg_depend` found no catalog object depending on its function OID; other deployed function bodies did not text-reference it; `cron.job` has no command referencing it. These searches do not clear dynamic or external calls. The active `get_current_shift_cashier_sales()` differs: it includes completed transactions across channels and additional fields, so it is **not** a drop-in compatibility replacement for a client expecting only walk-ins.

## 7. Proposed first migration batch — QA-only design, DO NOT EXECUTE AS A FILE

**Prerequisites:** separately authorize a new exact migration; reconcile the existing local October 13 cleanup file and divergent hosted ledger; take approved recovery snapshot/rollback plan; verify the named triggers, common `tgfoid`, `tgtype=19`, enabled status, no WHEN/UPDATE OF restriction, exact `set_updated_at()` body, all four deployed policy definitions, grants and manager helper; ensure no other migration already removed/renamed an object. Review the database owner privileges and deployment lock window. A migration should fail closed on unexpected catalog state, use one transaction, and avoid `CASCADE` or unrelated history repair. The SQL below illustrates the **three exact elimination statements only** after those assertions; it is not an active migration.

```sql
-- QA proposal only. A reviewed migration must execute these guards and drops
-- in one transaction, aborting on any unexpected catalog state.
DO $guard$
BEGIN
  IF (SELECT count(*) FROM pg_trigger t
      WHERE t.tgrelid IN ('public.profiles'::regclass,'public.riders'::regclass)
        AND t.tgname IN ('profiles_set_updated_at','trg_profiles_set_updated_at',
                         'riders_set_updated_at','trg_riders_set_updated_at')
        AND NOT t.tgisinternal AND t.tgenabled='O' AND t.tgtype=19
        AND t.tgqual IS NULL AND t.tgnargs=0
        AND t.tgfoid='public.set_updated_at()'::regprocedure) <> 4 THEN
    RAISE EXCEPTION 'Timestamp trigger pre-state drift';
  END IF;
  IF (SELECT count(*) FROM pg_policy p
      WHERE p.polrelid='public.profiles'::regclass
        AND p.polname IN ('profiles_select_own','profiles_view_own')
        AND p.polcmd='r' AND p.polpermissive
        AND p.polroles=ARRAY['authenticated'::regrole::oid]) <> 2 THEN
    RAISE EXCEPTION 'Own-profile policy pre-state drift';
  END IF;
  IF NOT EXISTS (SELECT 1 FROM pg_policy p
      WHERE p.polrelid='public.profiles'::regclass
        AND p.polname='managers_view_profiles' AND p.polcmd='r') THEN
    RAISE EXCEPTION 'Manager profile policy missing';
  END IF;
  -- Separately compare pg_get_triggerdef, pg_get_expr, grants and the
  -- captured set_updated_at/current_user_role bodies against this report.
END $guard$;
DROP TRIGGER trg_profiles_set_updated_at ON public.profiles;
DROP TRIGGER trg_riders_set_updated_at ON public.riders;
DROP POLICY profiles_view_own ON public.profiles;
```

Expected postflight: `profiles_set_updated_at` and `riders_set_updated_at` still enabled with `public.set_updated_at()`; each table has one timestamp trigger rather than two; `profiles_select_own`, `managers_view_profiles`, `profiles_update_own` still present; same grants and role matrix; no financial table/function/column count change. Exact read-only verification shape:

```sql
SELECT c.relname,t.tgname,t.tgenabled,t.tgfoid::regprocedure,pg_get_triggerdef(t.oid)
FROM pg_trigger t JOIN pg_class c ON c.oid=t.tgrelid
WHERE c.oid IN ('public.profiles'::regclass,'public.riders'::regclass)
  AND NOT t.tgisinternal ORDER BY c.relname,t.tgname;
SELECT polname,polcmd,polpermissive,pg_get_expr(polqual,polrelid)
FROM pg_policy WHERE polrelid='public.profiles'::regclass ORDER BY polname;
```

**Restoration definitions captured from hosted:**

```sql
CREATE TRIGGER trg_profiles_set_updated_at BEFORE UPDATE ON public.profiles
  FOR EACH ROW EXECUTE FUNCTION public.set_updated_at();
CREATE TRIGGER trg_riders_set_updated_at BEFORE UPDATE ON public.riders
  FOR EACH ROW EXECUTE FUNCTION public.set_updated_at();
CREATE POLICY profiles_view_own ON public.profiles AS PERMISSIVE FOR SELECT
  TO authenticated USING (id = (SELECT auth.uid()));
```

Within an uncommitted failed transaction, `ROLLBACK` restores the pre-state automatically. After commit, use a separately reviewed forward restoration transaction with the above exact definitions and verify catalog plus real role matrix. Restoration changes future updates/reads; it does not reverse any timestamps or access decisions made while the simpler configuration was active. No `DROP FUNCTION` or RPC grant change is part of this batch. Required acceptance after a later deployment: authenticated Customer/Cashier/Manager/Kitchen/Rider profile reads and contact update, Manager profile review, Rider onboarding/approval and push eligibility, Auth identity resolution, Cashier/Manager shift and transaction/history workflows, and current-shift RPC recovery. Hosted deployment needs its own explicit authorization.
