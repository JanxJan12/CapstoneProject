## 7. Focused implementation batches and recommended order

### Batch 1 — Dashboard usable-stock attention (**recommended first; do not implement yet**)

**Objective:** Let a Manager see a usable-out/low-usable condition from Dashboard without confusing it with the existing recorded-physical low-stock count. **Exact scope:** `src/modules/manager/dashboard/ManagerDashboard.tsx`, a small derived helper near `src/modules/manager/inventory/inventoryOverview.ts` if useful, existing `inventory/inventoryApi.ts` read interface only as needed, and one focused verifier/browser fixture. Read the existing guarded summary; do not add a writer, migration, new role, or direct recipe disclosure. Keep the current Dashboard/Reports financial RPC outputs unchanged. Use an independent loading/error/refresh state so a stock-summary failure cannot erase otherwise valid Dashboard data. Link to existing Stock Overview/Item Stock context. **Expected benefit:** actionable expired/usable shortage visibility. **Effort:** Small–Medium.

**Acceptance:** A synthetic item with physical quantity above minimum but usable quantity below the approved threshold appears in the new, accurately labeled cue; the existing physical count remains unchanged. Empty, loading, failed, stale, and refreshed states are distinguishable. A Customer/Cashier cannot obtain Manager stock details through the new UI path. Desktop/mobile render without clipped actions. Dashboard and Inventory verifiers, TypeScript, 11 quality checks, production build, and focused isolated role/read checks pass. **Regression risk:** extra read, stale partial data, double counting across inventory categories, and changing financial-card behavior; explicitly test each.

### Batch 2 — Shared desktop horizontal-pan correction

**Objective:** Remove measured 80 px horizontal document panning at 1024/1440 px on the four currently rendered Manager pages. **Scope:** smallest identified `AppShell` or theme CSS rule plus focused fixture metrics. Preserve visible sidebar, focus ring, desktop tables with local scrolling, mobile drawer, and all navigation. **Effort:** Small–Medium. **Acceptance:** `documentElement.scrollWidth <= innerWidth` and `scrollX` remains 0 after attempted pan at 1024/1440, with no new 360/390/768 overflow, clipping, or broken table scroll. Verify the cause before editing; do not blanket-hide overflow without checking content.

### Batch 3 — Menu administration decision and conditional implementation

**Objective:** Align the Menu Management promise with the restaurant's authorized operating model. **Scope A (if technical maintenance remains intentional):** update title/help to state current availability/meal/drink configuration and document the approved external master-data process. **Scope B (only with owner-approved self-service):** design narrow product/category fields and guarded backend mutations, validation, audit, image handling, and isolated Customer/Cashier/KDS/stock regression. Do not assume all fields or allow unreviewed recipe/rice quantities. **Effort:** Small for A; Medium–Large for B. **Acceptance:** the active UI truthfully describes its capabilities; any approved editor rejects invalid/unauthorized changes, updates future menu/quotes, and preserves historical order snapshots. A reviewed migration and deployment would require separate explicit approval.

### Batch 4 — Request History scaling, only if measurement warrants it

**Objective:** Keep formal Request History responsive as documents/revisions/events accumulate. **Scope:** establish an agreed synthetic large-history threshold and measure the existing response/UI; if exceeded, add cursor paging to the guarded register and its UI while retaining full selected-document detail and event ordering. **Effort:** Medium. **Acceptance:** measured response and interaction meet the agreed target; no dropped revision/receipt/attestation; stale-page and role-denial tests pass. Defer if present loads are acceptable.

## 8. Technical boundaries

Preserve `post_receiving_report(uuid)` as accepted-stock authority, batch and ledger linkage, FIFO/FEFO eligibility, server-calculated menu availability and pricing, immutable request revisions, historical receipt/order snapshots, and all Customer/Cashier/Kitchen/Rider contracts. Keep the seven drink choices and Fixed Meal Options; do not restore retired generic modifier objects. No production order, payment, stock, request, receipt, staff, or menu mutation is part of audit follow-up without a separately approved execution step.

## 9. Regression requirements

Run the focused Manager shell/navigation, Dashboard/Overview, Requests/Receiving, meal/drink, inventory/FIFO, Rider guards as applicable to the batch, plus `npm.cmd run typecheck`, `npm.cmd run verify:quality`, `npm.cmd run build`, and scoped whitespace. For an operational write, execute real role/JWT RPC tests with synthetic records in an isolated database and assert before/after stock, batches, ledger, and idempotency. For UI changes, capture actual five-width screenshots and keyboard/focus/error states. A source assertion is never a substitute for a rendered or authenticated test.

## 10. Acceptance criteria and 11. Definition of Done

Each batch has one reviewed scope, clear positive and negative tests, exact PASS/FAIL/NOT TESTED results, and evidence that existing uncommitted work and hosted business records were preserved. Claims state whether evidence is current source, synthetic browser, disposable Auth/RPC, hosted read-only catalog, or real authenticated hosted browser. If a dependency or approval is missing, stop that dependent work and keep its status **BLOCKED**, not PASS. A batch is done only when its own acceptance checks pass and no new high-severity regression remains.

## 12. Explicitly deferred outside Manager scope

Customer Batch 1–4 rework, general Cashier/Kitchen/Rider redesign, unapproved staff-account administration, financial-definition invention, physical inventory counting, external Messenger transmission, historical migration replay/repair, disaster recovery, hosted schema/data changes, and full project-wide audits. The outstanding current authenticated Manager and same-period financial acceptance are separately identified verification work, not permission to mutate real records.

## 13. Recommendation

Approve **Batch 1 only** if the restaurant wants the Dashboard usable-stock cue. It has a clear operational benefit and can be planned against an existing guarded read. Keep Batches 2–4 separate. This document stops at the audit boundary; no implementation or deployment was performed.
